# アーキテクチャ

## コンポーネントの流れ

~~~text
CLI / ローカルHTTPサーバー
        |
Project、Scenario、Inspector、Demoサービス
        |
Scenario + Policy設定 -> WorldState -> 決定的tick engine
        |                            |                |
地域・Provider adapter             |             EventQueue
任意LLM adapter                    |             EventLog
        |                            |
ProjectStore / TimelineStore <- Checkpoint / BranchRuntime
        |
Run成果物、履歴index、Inspector projection、比較レポート
~~~

Python標準ライブラリのHTTPサーバーがローカルブラウザーアプリを配信します。ブラウザーは型付きrequestを送信し、simulation stateを直接書き換えません。保存済みRunのInspectorはread-onlyです。Project操作は別の検証済みcommandを使います。

## モジュールの責務

| 領域 | 主な責務 |
|---|---|
| core | WorldState、simulation clock、keyed RNG、tick engine、Checkpoint |
| domain | 人物、施設、Zone、route、資源、職員、運営規則 |
| events | 予定・実行済みevent、型付きhandler、EffectProgram |
| policies | 行動、ニーズ、空間、心理、社会、情報モデル |
| experiments | Scenario、Run、Branch、timeline、metrics、evaluation |
| inspection | 証拠検索、Run projection、trace要約 |
| region | 地域データ、geometry検証、施設図面取込 |
| llm | Provider adapter、型付き出力、cache、応答再生、利用額記録 |
| storage | Project、asset、Run、Checkpoint、履歴indexの永続化 |
| web | ローカルHTTP route、Project API、Inspector、Demo、ブラウザーasset |

実装の正本はパッケージ構成です。公開入力・状態契約はsrc/sheltersim/contracts、event/world model、およびserializationと互換性を確認するテストにあります。

## シミュレーションと状態境界

- 時刻は整数分です。event順と同順位の決着は、固定IDと明示的なsort keyで決めます。
- WorldStateが変更可能なsimulation stateの正本です。Policyとadapterは型付き提案を作り、controllerが検証して適用します。
- controller（`experiments/runner.py`の`OfflineSimulationController`）がtickの入口です。各段階の処理は`experiments/phases/`の`dispatch`、`update`、`propose`、`arbitrate`、`sample`、`metrics`に1モジュールずつあり、controllerが継承します。`_run_*_phase`がその段階の手順の並びで、手順は名前付きのメソッドなので、1つの手順だけを別の実装（Rustなど）に差し替えられます。移動の経路と予定の処理（`_route`、`_schedule_travel`）は、他の段階からも呼びますが、主に使う`propose`にあります。`segments.py`の`KERNEL_ONLY_SEGMENTS`にある手順（dispatchの段階の全体、`_route`、`_schedule_travel`、`_schedule_staff_support_travel`、`_replan_journeys`、`_assign_staff_support`、`_consider_due_complaints`、`_sample_proximity_contacts`、社会と情報の接触）はPythonの本体がなく、controllerの手順がkernelそのものです。段階のmixinのメソッドは本体のない契約の文書だけで、kernelの断り（`Unsupported`）は`KernelRefusal`になります。driver（`native/src/rules/tick.rs`）も、手順のkernelが断ると、Pythonに戻らずに同じ`KernelRefusal`（kernelの名前と断った理由）を出します。
- `TickEngine.step`は`controller.run_tick`（`experiments/phases/driver.py`）を先に呼び、`native/src/rules/tick.rs`がtickの段階を順に動かします。kernelは直接呼び、Pythonの部分（指標の`capture_metric`、苦情を方策に聞く`consider_complaint_response`など）は部分ごとに1つの入口で呼びます。`phase_handler`の差し替えがある、`rule_shadow`がある、driverが飛ばす手順や規則がpatchされている、のどれかなら、何も変える前に断り、`phase_handler`の経路が動きます。`TickEngine.phase_observer`は、どちらの経路でも段階の前後に呼ばれ、`tick_probe`と`PhaseProfiler`とengineの完全なtraceはこれを使います。traceの文書（判断、接触、心理の寄与）はkernelが`native/src/rules/trace.rs`などで作り、形は変えず、書き出しと`_sanitize`はPythonの`RunArtifactWriter`のままです。Providerを呼べるrouterもdriverで動き、hookはkernelからPythonの同じ場所を呼びます。LLMの入力、Provider、応答テープ、スキーマと意味の検証はPythonのままです。tickの検証（`validate_after_tick`）は、下のとおり`native/src/rules/after_tick.rs`の1回の呼び出しです。
- dispatchの段階は、`native/src/rules/dispatch.rs`のループが動きます。段階の手順`_run_dispatch_phase`にPythonの本体はありません（`KERNEL_ONLY_SEGMENTS`）。ループは適用されたイベントの後の処理（行動の完了、学習、ケアの記録、空間の更新、閉じた経路の中断、戻りと到着の受け入れ、移動の同期、社会的な接触の判断）を、controllerと`experiments/phases/dispatch.py`の同じ名前の関数から呼びます。`social_interaction`、`agent_travel_complete`、`toilet_service_complete`、`resource_service_complete`、`support_request_timeout`、`staff_support_complete`はRustの関数です。ほかのhandlerもEffectProgramの印がないイベントはループが直接呼び、`apply`のkernel（`rules/handlers.rs`、`rules/information_events.rs`、`rules/staff_operation_events.rs`）が動きます。これらのhandlerと`social_interaction`、`agent_travel_complete`、`toilet_service_complete`、`support_request_timeout`、`staff_support_complete`のhandler、EffectProgramのすべてのhandler、ガードは、Pythonの規則を消しました（`kernel_only`）。kernelは抑止と失敗の文を自分で出し、断ると`KernelRefusal`になります。歩きの到着で断られたトイレの依頼は、依頼の`ValueError`の文が失敗の文になります。人口のhandlerの中の人口の規則（`domain/population.py`、`domain/population_lifecycle.py`。これも`kernel_only`です）のkernelが断ると、その規則の`KernelRefusal`になります。ループが事象の後の処理のkernelを直接呼んで断られたときも、Pythonの入口を呼び直さず、その入口の`KernelRefusal`を出します。EffectProgramの印のあるイベントは、ループがガードをRustで確かめてから（偽と失敗はPythonの規則の文で記録します）、印のないイベントと同じように進みます。表のRustの関数を持つ型の印のあるイベント、差し替えられたhandlerと、列で置き換わったイベントは、`EventDispatcher.dispatch_one`（イベント1件分のPythonのdispatcher）が処理します。イベントの順序、同順位の解決、`id_counters["event"]`は同じです。Rustの関数が処理したイベントの記録は、Pythonが読むときに`EventLogRecord`になります（[lanes/m3-dispatch.md](rust-port/lanes/m3-dispatch.md)、[lanes/m6-handlers.md](rust-port/lanes/m6-handlers.md)、[lanes/m6-handlers-rest.md](rust-port/lanes/m6-handlers-rest.md)）。
- Rustの接触のkernelは、社会の伝播が`native/src/rules/social_propagation.rs`、情報が`native/src/rules/information.rs`、共通の抽選が`native/src/contacts.rs`にあります。社会の伝播は更新の段階の手順`_social_propagation`、情報は標本の段階の手順`_sample_information_contacts`そのものです（`experiments/phases/segments.py`の`KERNEL_ONLY_SEGMENTS`）。この2つの手順と`policies/social.py`、`policies/information.py`、`policies/alternatives.py`の接触の規則は、Pythonの規則を消しました。方策のクラスは設定と`policy_version`を持ち、kernelがクラスの同一性で見分けます。Scenarioが`0`や`1`と書いた係数や、64 bitを超えるseedもkernelが扱います。kernelが断る入力（`CounterRNG`でない乱数、方策の派生クラス、壊れた名前空間）は`KernelRefusal`になります。
- 世界はRustの状態を`world.__dict__["_core"]`（`WorldCore`）に持ちます。`WorldCore`は1つの世界のもので、その世界を弱い参照で持ちます（`WorldCore.adopt`。`state_mirror.start_core`と`deepcopy_world`が呼びます）。`with_world`は、渡された世界が自分の世界でないと`RuntimeError`にします。写しが世界の場所を取る差し替え（`world.__dict__.clear()`・`update()`。`transaction_or_copy`とRustの規則の写しの道だけです）の後は、`state_mirror.owned_again`が写しの中核を世界のものにします。世界がなくなると（弱い参照のcallback）、中核は世界のオブジェクトを手放します：実体のオブジェクトとその`IdMap`は今の値を持つ素のオブジェクトになり、EventQueueとEventLogは自分の列と記録を持ち直します。`WorldCore`は、PyO3に依存しない中核の`World`（`native/core/src/world.rs`：スカラー（`scenario_id`、`seed`、`duration_minutes`、`minute_index`、`schema_version`。`WorldState.__setattr__`が書きます）、実体の行（区域と区域の辺も含みます。区域の側は taint が別です）、Rustが持つ項目・名前空間ごとの`Slot`（行、taint、切り離しの印、世代、数を持ちます）、予定のイベントの列（`Queue`）とEventLog（`EventLog`））を持ちます。Pythonの`EventQueue`・`EventLog`のRustの側（`QueueStore`・`EventStore`）は、その列と記録を指す窓で、イベントと記録のPythonのオブジェクトだけを持ちます。どの世界のものでもない`EventQueue`・`EventLog`は自分の列と記録を持ち、世界に代入されると（`WorldState.__setattr__`、`WorldCore.attach_events`）中核へ移り、世界が手放すと戻ります（写しはしません）。ほかの生きている世界の中核にあるもの（`_effect_candidate`と`canonical_copy("effect")`の写しが持つ元の世界のEventLog）は、元の世界に残ります。`NamespaceMirror`（木と節点の表）と`EntityStore`（保存に渡したbytes、数、付いた実体のオブジェクトとその`IdMap`）も、その`World`を指す窓です。実体は行が本体で、Pythonのオブジェクトは行の写し（view）です。Rustの規則は行だけを書き、行をキーで足したり除いたりします。借りが終わるとPythonが動く前に、オブジェクトが行に従います：違う欄だけをオブジェクトに書き、足した行からは`__init__`を通さずにオブジェクトを作ってキーの場所に入れ、除いた行のオブジェクトには最後の値を書いて切り離します（`EntityStore::flush`）。付いたオブジェクトの`__dict__`に直接書いても行には届きません。窓は`WorldCore`を共有で借り、使う部分（1つの`Slot`か実体の行）だけを借ります。同じ部分を二重に借りると、panicではなく`RuntimeError`です。Rustが持つのは`psychological_distress_v1`、`social_propagation_v1`、`information_spread_v1`、`staff_dynamics_v1`、`agent_dynamics_v1`、`movement_v1`（規則はRustです）、`body_state_v1`（`record_social_event`と毎tickの書き込みはRustです。Pythonの規則の書き込みは1項目ずつ転送します）、`staff_operations_v1`、`shared_operations_v1`、`population_presence_v1`、`population_lifecycle_v1`、`population_dynamics_v1`、`temporary_spaces_v1`、`geometry_overlay_v1`（この5つは`V`の行です。`docs/rust-port/lanes/m6-population.md`）、`metric_state`、`model_configs`、`resources`、`id_counters`です（`core/state_mirror.py`の`OWNED_NAMESPACES`・`OWNED_FIELDS`。`resources`と`id_counters`は、丸ごと代入しても新しい木になります（`WHOLE_FIELDS`））。`model_state`のほかのキー（`operational_events_v1`、`infrastructure_v1`、`zone_environment_v1`、LLMの`social_runtime_v1`・`support_priority_runtime_v1`、Scenarioが持つ知らないキーなど）も、名前が`str`なら、初めて入れたときに`V`の行（`ValueRow`）の`Slot`を持ちます（`NamespaceTable`の`_value_mirror`）。キーを消すと行と木を捨て、`Slot`とミラーは次に入れるときのために残ります。木は切り離さずに持ち続けるので、読み手には今までどおりの木です。`V`に入らない値（tupleなど）は、そのキーの行だけをtaintします。持っている項目は`TrackedDict`・`TrackedList`の木になり、`model_state`自体は`NamespaceTable`になって、Pythonからの書き込みはRustの行へ、Rustからの書き込みは木へ届きます。`Slot`の行も本体です（#152 のPR P8-0c）：中核のkernelが行だけを書くと（`World::row_mut`）`Slot`に印が付き、`with_world`の借りが終わるとPythonが動く前に、付いている木が行に従います（`NamespaceMirror::follow_row`）。根と、行がまだ同じ種類の入れ物を持つ場所の入れ物は同じオブジェクトのままで、dictには値の変わったキーだけを書き、行が除いたキーは除き、新しいキーは最後に入れ、キーの順が行の順と違えば、キーと値を同じオブジェクトのまま行の順に並べ直します。リストは残る項目を残します（前から除いて後ろに足す履歴の形か、項目ごとにその場で）。切り離した名前空間には木がないので、何もしません。デバッグの実行では、tickの終わりごとに付いている木と行を、値とキーの順で比べられます（`watch_entity_rows`、全経路のゲートの`--verify-rows`）。ただし`DETACHED_NAMESPACES`に挙げた名前空間（どれを切り離したかは[docs/rust-port/step4-plan.md](rust-port/step4-plan.md) 5節）は木を持たず、行だけが状態です。`model_state`はその名前に印を持つ`_DetachingTable`になり、kernelは印を見て行を読みます。世界全体を読むもの（正規のJSON、`same_state`、検証、Checkpointの保存と復元、forkの`deepcopy`）も行のbytesか行から作った文書を読み、木を作りません（`plain_model_state`、`read_only_state`）。Pythonから名前空間を読むと行から木を作り直し、その木への書き込みは行に届きます。木は次のtickの終わりに`TickEngine`が捨てます（`detach_unread`）。捨てる前から持っていた節点に書くと`DetachedNodeError`になります（[docs/rust-port/step4-plan.md](rust-port/step4-plan.md) 5節）。行に合わない値が書かれると行を捨て（taint）、kernelは`Unsupported`を返します。tickの規則にPythonの本体はないので、それは`KernelRefusal`になります（検証の`validate_*`はPythonが木の上で、木のない名前空間では行から作った文書の上で読みます）。kernelが素の入れ物と同じように読むのは、この追跡する型だけです（`native/src/core/tracked.rs`）。ほかの派生型はPythonの処理に任せます。Pythonの規則が自分のエラー（`ValueError`、`StateInvariantError`など）を出す入力では、移したkernelは`Unsupported`ではなく同じクラスと同じ文の例外を、規則と同じ検査の順で、何も変える前に出します（`native/src/core/errors.rs`。[docs/rust-port/lanes/l8-texts-rest.md](rust-port/lanes/l8-texts-rest.md)）。名前空間の検証をRustに任せる登録（`register_rust_validator`）と、段階の手順をkernelにする登録（`experiments/phases/segments.py`の`KERNEL_ONLY_SEGMENTS`）、ほかのモジュールが関数として呼ぶ規則をkernelにする印（`core/kernels.py`の`kernel_only`。kernelが断ると`KernelRefusal`（`ValueError`の派生）になり、文はkernelの名前と断った理由です）があり、移植の作業は`core/world.py`を編集しません。手順は`docs/rust-port/lanes/p5-template-namespace.md`と`docs/rust-port/lanes/p4-world-core.md`にあります。
- 世界をその場で変えて、検証に通ったときだけ残す処理のために、トランザクションがあります（`core/state_mirror.py`の`transaction(world, "full"|"effect")`、中核の`native/core/src/txn.rs`）。始めに世界を検証し、中核の部分の snapshot を取り（`CowShard`：書くときに写します）、世界を正規のJSONを通した写し（`WorldState.from_dict(world.to_dict())`）と同じ順に並べ直し（実体はIDの順、辞書のキーはbytesの順、予定のイベントは待つ順に新しいserialで入れ直します）、Pythonの入れ物（実体の`IdMap`、名前空間と持つ項目の木、`model_state`の表、`rng_state`）を写しと同じ順と型で作り直してから、写しと同じ包み方でもう一度検証します。取り消すと、snapshot（列を含みます）、EventLogの印（`EventLog::mark`・`rollback`）、列のイベントと記録のオブジェクト、古い入れ物とオブジェクトをすべて戻します。入れ子にはできません。Branchのコマンド（`BranchRuntime.apply`、`"full"`）とEffectProgramの予定（`schedule_effect_program`、`"effect"`）がこれを使います。世界の中核がトランザクションを持てないとき（`Unsupported`：中核がない、実体の行がtaintしたなど）だけ、`state_mirror.transaction_or_copy`が以前の写しを作って差し替えます。Pythonで`WorldState`の`__dict__`を書き換えて差し替えるのはそこだけで、`tests/unit/repo/test_world_swap_lint.py`が`src/`のほかの場所を見つけると失敗します。tickの中で世界を写して変え、検証して差し替えていた規則（EffectProgramの5つのハンドラーの書き込み、運営のイベントのトランザクション、人口の増減、人の出入りのコマンド）も、写しの代わりにこのトランザクションを使います（`native/src/rules/transaction.rs`の`RuleTxn`。開くときに`Unsupported`なら、`transaction_or_copy`と同じく今までの写しを変えて差し替えます。ほかの規則のトランザクションの中で呼ばれた規則（補給路の途絶の配送の遅れ）は、始めの検証をしてから世界にそのまま書き、外のトランザクションが残すか取り消します）。デバッグの実行では、トランザクションを断らせたり（`core/txn_checks.py`の`refuse_transactions`）、世界から外したオブジェクトを使うと例外にしたり（`poison_replaced`）できます（全経路のゲートの`--refuse-transactions`、`--poison`）（[docs/rust-port/step5-plan.md](rust-port/step5-plan.md)、PR 6-2、PR 6-4、PR 6-3）。`deepcopy(world)`は、中核の`World`を fork します（`WorldCore.fork`、`World::fork`）。新しい世界は、状態のすべての部分をどちらかが書くまで元の世界と共有し、実体のオブジェクトは行からキーの順に作り、名前空間と持つ項目の木も行から作ります（切り離した名前空間は切り離したままです）。行が持たないもの、列、EventLog、ほかの属性は今までどおり写します。行が世界の`IdMap`と食い違う世界（taintしたストア、`IdMap`を通らずに置いた値）と、トランザクションの中の世界は、前の写し方です。捨てる下見（追加するトイレの図面の確かめ、モデルの状態の提案）は、`canonical_copy(world, kind)`で、forkした写しをトランザクションで正規の順に並べて commit したものを使います。世界そのものは並べ直しません（PR 6-6）。
- イベントの抑止と失敗（`EventSuppressed`、`EventApplicationError`）は、kernelが自分でPythonの規則と同じ文、同じ検査の順序で出します（`native/src/core/errors.rs`）。文はイベントの記録の`detail`として保存されるからです。移していない枝は今までどおり`Unsupported`でPythonの規則が出します。規則を消したもの（`kernel_only`）は、テストが規則から書き写したクラスと文と比べます（[docs/rust-port/lanes/l8-texts-events.md](rust-port/lanes/l8-texts-events.md)）。

TickEngineは毎分の終わりに、現在の状態と、その分に追記された履歴記録（直前の1件を含む）を検証します。追記専用の履歴（共有運用、生活状態の社会履歴、給水・配食の依頼と停止の履歴、資源台帳の監査記録）とEventLogの全体の再生、共有運用の支援ライフサイクルの再構成は、Runの開始・終了とCheckpointの作成・復元で行う完全検証で確認します。毎分の検証が履歴全体を再走査しないため、1分あたりの検証時間は履歴の長さに比例して増えません。TickEngineの毎分の検証（`WorldState.validate_after_tick`）は、前の分の検証から変わっていないと示せるものをさらに省きます（`native/src/rules/after_tick.rs`の冒頭）。根拠は次のとおりです。規則そのものは減らしていません。省いたものは完全検証がすべて確かめ、検証に失敗した世界は覚えていたことを捨てます。(1) 設定の検証は、`model_configs`に書き込みが届いていない間（Rustの`NamespaceMirror`の世代が同じ）は省きます。世代の比較なので124 KBのJSONを読みません。丸ごと代入されてミラーのない設定は、毎分Pythonの検証です。(2) 解決済み・未解決になった支援の依頼（`support_requests`）は、自分の項目、人のIDの集合、そして「今の分より後でない」という形でしか時刻に依存しません。`SupportRequestState`は項目への代入を知らせるので、代入された依頼と新しい依頼、まだ終わっていない依頼だけを確かめます。辞書の値が同じオブジェクトのままかも毎分確かめ、人のIDが変われば全部を確かめ直します。tickの途中で終わっていない依頼を探す走査（`WorldState.unsettled_support_requests`）も同じ記憶と知らせを使い、確かでないときは全部を読みます。(3) `population_presence_v1`、`population_lifecycle_v1`、`population_dynamics_v1`、`geometry_overlay_v1`は、書き込みが届いておらず（世代が同じ。Rustが持たない世界では正準JSONが同じ）、規則が読むほかの状態（人のID、区域のID、設備の区域）が変わらなければ省きます。時刻や他の状態と比べるもの（`archive_path`、保留の移動、到着待ち、仮設の部屋、経路の変更）があるときは省きません。(4) 共有運用の記録は、追記したkernelか、通ったPythonの検証が確かめたものを確かめ直しません。職員の作業の記録だけは、残っている作業の完了と毎分比べます。(5) 資源台帳は行のkernelが確かめます。(6) 社会関係・体調の関係の記録は、Rustの行が、書かれた記録を自分で控えます（転送も規則の書き込みも通ります）。毎分はそれだけを確かめ、人のIDが変われば全部を確かめ直します。行がtaintしたときは、Pythonの規則が毎分全部を読みます。大きな辞書の走査（人、社会関係・体調の関係、体調、行動の記憶、位置）は、すべて規則を満たすと分かったときだけ`true`を返すRustの確認を先に通します。それ以外（型が素でない値を含む）はPythonの規則が判定するので、受け入れる範囲とエラーは変わりません。Rustが持つ名前空間（`psychological_distress_v1`、`information_spread_v1`、`staff_dynamics_v1`）は、行を読むkernel（`register_rust_validator`）だけが規則の前に立ちます。行に入らない値はtaintに、入るが規則に合わない値はkernelの`false`になり、Pythonの規則が木を読んで同じエラーを出します。`rust_validated`は、世界がその行の木と、行が従う`IdMap`を今も持っていることも確かめるので、`world.__dict__["model_state"]`への代入や`dict.__setitem__(world.model_state, ...)`、`dict.pop(world.staff, ...)`もPythonの規則に届きます。実体の規則は、行を信じずオブジェクトを読みます。`agent.__dict__`への書き込みが行に届かないからです。追跡する木の節点への`dict.__setitem__`だけは行にもkernelにも届きません（`src/`にはありません。`test_tracked_write_lint.py`が見ます）。どの規則を何が証明するかは`docs/rust-port/lanes/t-tick-validation.md`にあります。完全検証のうちEventLogについては、次のように読む量を減らしています。EventLogは、記録を足すときに作る索引（IDと順序番号、イベントの種類ごと、来歴に介入（EffectProgram）の印を持つ記録）を持ちます。運営イベント・介入・環境・インフラの完全検証は、確かめるイベントの種類の記録だけを索引から読み、IDによる参照も、EventLogを写した辞書ではなく索引（`EventsById`）で引きます。ほかの種類の記録は、これらの確認を素通りするだけなので、確かめる範囲は変わりません。EventLogはIDか順序番号が重なる記録の追記を断り、記録の差し替えも削除もできないので、EventLog自体の監査は実現時刻だけを確かめます。前の監査と同じかそれより後の時刻で、同じ期間の監査なら、増えた記録だけを確かめます。前より早い時刻や別の期間での監査なら、全体を確かめ直します。
- Checkpointの保存の前の完全検証（`world.validate()`）は、書き手の履歴キャッシュ（`CheckpointHistoryCache`）があるとき、追記専用の履歴の古い項目を読み直しません（`core/save_validation.py`）。読まないのは次の5つの履歴の、前の保存で通った項目だけで、他のものはすべて保存のたびに読みます。読まない根拠は次のとおりです。(1) 保存のたびに、各履歴の全項目が前の保存の文書のままかを確かめます。項目を文書と比べる比較（`sheltersim_native.same_json_items`）は`==`より厳しく、型まで見ます（`1`・`1.0`・`True`は別、タプルとリストも別、`0.0`と`-0.0`も別）。一度この比較を通った項目は、同じオブジェクトを同じ順で持ち続けていることで確かめ（`HistoryPins`。中のオブジェクトへの参照を持つので、同じアドレスに別の値が来ることはありません）、そう言えなければ文書と比べます。項目の変更・削除・差し替えがあれば、同じ保存でその履歴全体を読み直し、規則が今までどおり判定します。Runの終わりまで待つものはありません。(2) 古い項目の規則が読むほかの状態も比べ、違えば履歴全体を読み直します。`request_history`・`queue_stall_history`は既知の人のID・区域のID・設備の種類、`body_state_v1.history`は過去の人を含むID、`resource_ledger_v1.audit`は倉庫IDと既知の人のID、`shared_operations_v1.history`は保持中の職員の運営履歴（`staff_operations_v1.history`）の正準JSONです。(3) 時刻が戻るか`event_log`が別のオブジェクトになると、覚えていることをすべて捨てます。(4) 資源台帳の監査の再生と共有運用の支援ライフサイクルの再生は、前の保存の途中状態から続けます。先頭の項目が落ちた履歴（`history_truncated`）は再生の始点が変わるので、毎回全体を読みます。(5) 覚えたことは書き手のキャッシュが持ちます。読み込み・分岐・再開の世界は新しいキャッシュで始まるので最初の検証は完全です。失敗したCheckpointの作成は覚えたことを捨てます。Runの開始・終了（`TickEngine.run`）、読み込み、`to_dict`などの完全検証は、これまでどおり全項目を読みます。
- 資源台帳への操作（納入、損失、予約、解放、消費）と毎分の指標集計は、現在の残高・予約と、直前の監査記録・各資源の最新の監査記録を確認します。Pythonの規則の操作は変更する口座だけを複製した候補に適用し、確認を通ってから差し替えます（Rustの規則は、確認を通ってからその場で書きます）。監査記録の全件の再生は完全検証で行います。
- Checkpointは対応する復元に必要なstateとruntime情報を含みます。BranchRuntimeは分離したstateを復元し、兄弟Branchで可変queue、RNG状態、actor objectを共有しません。
- 1 tick の中と tick の間で、次のものを作り直しません。結果を変えない根拠と入力の一覧は`docs/rust-port.md`のB4にあります。提案の段階の`WorldView`（`policies/world_view.py`。`policies/behavior.py`からも読めます）は更新の段階のものから作り、更新が書く項目だけを読み直します（`native/src/rules/world_view.rs`の`view_for_proposals`）。解析した設備の形状、`selected_models`、部屋の中の経路、区域の環境は、コントローラーごとに持ちます（`ContextVar`のscopeか引数で渡すので、スレッドや分岐をまたぎません）。`model_configs`は分の最初に、書き込みが届いていなければ（世代が同じ）そのまま使い、届いていれば写しと値で比べて、違えば全部を捨てます。Rustのkernelが読む設定の節（選ばれたモデル、職員の疲労と作業の式、支援の時間、情報の拡散、体調の演算子とケアの式、行動の記憶の方針と設備の認知、区域の環境、インフラ、近接の接触、移動のモデル、経路の容量、待ち行列の方針、上書きのschema、資源サービスの設定、人口の必要な配慮、シミュレーターの拡張の有無）は、`model_configs`のslotのstampごとに最初に読んだときに1回だけ解釈して中核の`Configs`に持ちます（`native/src/core/configs.rs`）。誤りは解釈のときに出さず、読む場所が今までと同じクラス、文、時点で出します（[docs/rust-port/step5-plan.md](rust-port/step5-plan.md)の方針E7・E14）。経路と環境は、読む`model_state`の項目を呼ぶたびに値で比べます。`EventQueue`は索引を持ちますが、`pending()`の順と保存の形は変わりません。`EventQueue`は世界の中核が持ち（`World::queue`、`native/src/state/events.rs`）、Rustの規則が予定したイベントの`ScheduledEvent`は、Pythonが読むときに作ります。行動の周期の記録（`agent_action_lifecycle`）はRustの規則がbyte列として追記し（`native/src/rules/action_lifecycle.rs`）、`EventLogRecord`はPythonが読むときに作ります。開いている行動はコントローラーの`ActiveActions`がRustの行で持ちます。保存はされず、復元のときにイベントログから作り直します。
- 計算を進めるworker（`TimelineStore`の継続計算）は、Checkpointを保存するたびに、前の保存で変換した追記専用の履歴（EventLog、KPIと資源の標本、上の追記専用の履歴）の文書と正準JSONのbyte列、EventLog記録の復元結果を再利用し、新しく増えた分だけを変換・復元します（`core/checkpoint_cache.py`、#44）。保存されるCheckpointのbyte列、hash、archiveのchunkは、全体を変換した場合と同じです。chunkのhashは、chunkの最初と最後の項目のbyte列（同じオブジェクト）と項目数で覚えます。覚えておくのは、直前の保存が読んだか足したものだけです。古い項目を先頭から捨てる履歴では、捨てた項目のchunkを二度と読まないので、そのhashと項目のbyte列を持ち続けません（#138）。世界の文書の各フィールドの正準JSONは1回だけ作り、文書・hash・chunkで使い回します。Checkpoint v2のhashはchunkのhashの木なので（`docs/project-persistence.md`）、保存は新しいchunkだけをhashします。項目は同一性で照合し、古い項目を先頭から捨てる窓にも対応します。凍結されていない履歴の項目は保存済みの文書と等しい間だけ再利用し、書き換えられていれば変換し直します。保存前の完全検証は、従来どおり保存のたびに行います。復元の確認では、保存した文書から世界を復元し、それが直前に完全検証した世界と同じ状態か（`WorldState.same_state`）を比べます。同じなら、同じ検証を通るので、復元した世界の完全検証は省きます。違えば、従来どおり復元した世界を完全検証します。EventLogの記録のbyte列は、追記のときに凍結された値からRustが書きます（Rustの規則の記録は最初からbyte列だけです）。すべての記録のbyte列をRustが書いたか確かめたログ（`EventLog.all_encoded`）は、復元してもそのログ自身になるので、復元の確認はそのログをそのまま読み、byte列の解析も比較もしません。Rustが書けない値（`str`の派生クラスなど）を持つ記録があるログは、次のとおりです。前の保存の確認で同じと分かった記録を比べ直さず、増えた記録だけを比べます。増えた記録は、保存したbyte列を読み、live の記録の各フィールドが、そのbyte列から復元する値と型まで同じかをRustで確かめます（`same_saved_records`）。復元した記録を作らずに同じことを確かめるためで、同じと言い切れないもの（`1`と`1.0`の違い、凍結されていない値など）は、従来どおり復元した記録を`==`で比べます。復元の確認で作る世界は比べたら捨てるので、保存した文書を写さずにそのまま使って組み立て、EventLogは前の保存の確認で作ったものに増えた記録だけを足して使います（索引もそのまま保ちます）。計算を再開したときと分岐したときは、読み込んだ（または分岐で作った）CheckpointのEventLogのbyte列を、そこから組み立てたEventLogが持つので、最初の保存はそのbyte列を再利用し、増えた記録だけを確かめます（`CheckpointHistoryCache.seed_events`）。復元の確認のKPIの標本も、前の確認で作った分を再利用して増えた分だけを読み、`model_state`の追記専用の履歴は、この保存で文書と等しいと確かめた項目を比べ直しません。分岐と再開では、活動中の行動を決める記録だけをRustのEventLogの索引から読むので（`active_action_index`）、記録を全件作りません。保存ごとのframeのケア履歴も、EventLogに持たせた前回の結果（`EventLog.derived`）に増えた記録だけを足します。
- 計算を進めるworkerは、Checkpointを保存するたびに、EventLogの記録の`EventLogRecord`のオブジェクトを手放し、記録のbyte列だけを残します（`EventLog.release_records`、#138）。次に記録を読むと、byte列から同じ値のオブジェクトを作り直します。手放すのは、byte列をRustが書いたか読み込んで確かめた記録だけです。`str`の派生クラスなどを持ち、byte列をPythonが作る記録は、オブジェクトを残します。完全検証が種類ごとに全件を読む記録（`EventLog.of_types`で求められた種類）も、保存のたびに作り直すことになるので残します。読むのは保存と保存の間に数百件程度で、100人・7日分では計算中の最大RSSが約1.53 GBから約1.06 GBになりました。オブジェクトとbyte列の両方を持つと、記録1件あたり約4.1 KB（オブジェクト約45個で約2.9 KB、byte列約1.2 KB）です。
- `WorldState.canonical_json()`（`to_dict()`もこれを読みます）は、`event_log`の部分を、EventLogが持つ記録のbyte列（Checkpointが保存するものと同じ）をつないで作り、記録ごとの`to_dict()`を作りません（#138、#134）。最上位のキーは`json.dumps`の`sort_keys`と同じ順に並べ、ほかの値はそれぞれ今までどおり`json.dumps`で書くので、文字列は1文字も変わりません。Rustが書けない値（`str`の派生クラスなど）を持つ記録があるログ（`EventLog.all_encoded()`が偽）は、従来どおり記録ごとの`to_dict()`から全体を書きます。
- 計算を進めるworkerの保存は、Rustの行が持つもの（人、設備、職員、支援の依頼、活動中のタスク、Rustが持つ名前空間と`metric_state`）を、Pythonのオブジェクトを読まずに行から正準JSONにします（`core/state_mirror.py`の`owned_row_bytes`、`EntityStore.rows_json`、`NamespaceMirror.row_json`）。byte列は`_canonical_data`のものと同じなので、hash、archiveのchunk、packは変わりません。実体のリストは文書の中で`SavedItems`です。行を持つものは`state_row!`と`OWNED_NAMESPACES`・`OWNED_FIELDS`の1行だけで、この経路に入ります。taintした行、丸ごと代入された項目、正準JSONが断る値（NaN）は、これまでどおりPythonのオブジェクトから作るので、エラーの文も同じです。hashの木が項目を分けて持つ名前空間（`_WORLD_TREE`）は、Rustが持ってもPythonの経路のままで（`body_state_v1`）、全体のbyte列も作りません。復元の確認の世界は、Rustの行を持たない素の世界です（`WorldState._bare_world`）。実体の行は、書かれていない限り同じbytesオブジェクトを返すので（行に書ける道はすべて印を付けます）、前の確認で等しいと示した行と同じオブジェクトなら、復元も比較もせず、前の確認のオブジェクトを使います。復元の結果は入力のbyte列だけで決まるからです。変わった行だけを今までどおり復元して比べます。Rustが持つ名前空間は、行のbyte列から読んだ文書を木と今までどおり比べます。
- 新しいchunkの秘匿情報の確認（`_reject_sensitive_checkpoint_content`）は、保存した1回分のchunkのbyte列をまとめてRustで読みます（`sensitive_candidates`）。Rustが返すのは、異なるキーのすべてと、パターンに一致しうる異なる文字列だけで、判定はPythonの同じ関数が行います。すでに保存したchunkは確認しません（それらは最初の保存で確認済みです）。byte列が1つでも違えば新しいchunkなので確認します。
- 計算を進める間（`TimelineStore`の継続計算）とCheckpointの読込の間は、Pythonの循環参照の回収（gc）の頻度を下げます（`core/collection.py`の`fewer_collections`、#234）。最も若い世代の回収を、新しいコンテナオブジェクト700個ごとから200,000個ごとにし、最後の区間が終わると元の閾値に戻します。閾値はプロセスに1つなので、区間が有効な間は同じプロセスのほかのスレッドにも効きます。Webサーバーでは計算が別プロセスで動くので、サーバーのプロセスに効くのはCheckpointの読込の区間だけです。1日分の計算（100人）ではCPU時間が約9%短くなり、ピークRSSが約47 MiB増えます。
- Webサーバー（`serve_inspector`）の`ProjectAPI`は、計算1回（`POST R/resume`）と分岐1回（`fork`、intervention-apply）ごとに別プロセスを起動して処理します（`web/worker_process.py`、`ProjectAPI(worker="process")`、#48）。起動はWindowsと同じspawn方式です。子プロセスがRunの書込権（`claim_run`）を自分で取り、取れたことをサーバーに知らせてから計算します。取れなければ従来どおり`run_worker_busy`で断ります。中止は`multiprocessing.Event`で伝え、サーバーのプロセスがなくなった場合も、子プロセスは次の保存境界で止まります。子プロセスが結果の状態を書かずに終わった場合（強制終了など）、サーバーはRunを`interrupted`にします。分岐の間はRunを`running`にし、サーバーが結果（`last_fork`）を記録してから元の状態に戻します。分岐の子プロセスが強制終了した場合も、Runは元の状態に戻ります。分岐の間も、サーバーはほかのHTTP要求に応えます。計算中もサーバーのプロセスはHTTPの応答でGILを取り合わず、計算が終わると子プロセスが使ったメモリはOSに戻ります。telemetryの`run_peak_memory_bytes`には、子プロセスのピークRSSを記録します。同じBranchの計算と、そのBranchからの分岐は1つずつですが、同じRunのほかのBranchや異なるRunは、上限（`sheltersim web --max-parallel-runs`、既定2）まで同時に、それぞれ別プロセスで計算・分岐します（#48）。書込権はBranchごとです。計算はそのBranchの、分岐は作る子Branchの書込権（`ProjectStore.claim_branch`、`branches/{branch}/worker-lock`）を取ります。Branchの書込権は、Runの入口のロック（`runs/{run}/worker-lock`）を一瞬だけ取ってから取ります。Runの削除・履歴索引の作り直し・回復のようなRun全体の操作（`claim_run`）は、入口のロックを持ち続けたうえで、どのBranchも書かれていないことを確かめます。占有ロックだけを使うので、Linux・macOS・Windowsで同じ組み方です。上限に達しているときの要求は、`background workers are busy` で断ります。計算1本で、1日分のRun（100人）なら約0.5〜0.9 GBのメモリを使うので、上限はCPUの数ではなくメモリに合わせて決めます。テスト、CLI、計測器（`benchmarks/investigate_performance.py`）は、同じプロセスのスレッドで計算します（`worker="thread"`、既定）。
- Branchの分岐（`TimelineStore.fork`）は、分岐する時刻の状態からCheckpointを1回だけ作ります。そのCheckpointが分岐の記録（`fork_origin`）の`state_hash`と`checkpoint_hash`になり、作成時の復元検証で組み立てた世界と指標が、そのまま子Branchになります（`Checkpoint.capture_restored`、#46）。この世界と指標は、Checkpointとも分岐元とも何も共有しません。子Branchに引き継ぐ応答テープは、分岐元のhead Checkpointの`runtime_state`だけを読みます。
- inspection、描画、metrics、trace levelはWorldStateを変えず、simulation乱数も消費しません。

ScenarioSpec、WorldState、Checkpoint、EffectProgram、Project recordはそれぞれ個別に版管理します。state変更には互換性テストが必要です。古い永続データを読み続ける場合は明示的な移行を用意します。

モデルの版は、Checkpointの`model_versions`に`model_signatures()`として記録します。Policyと状態契約ごとの署名のほかに、モデル全体の版`engine:model`とRNGの`engine:rng_algorithm`（`CounterRNG.algorithm_id`）の2項目があります（`core/model_version.py`）。全体の版は、Scenarioごとの署名を変えずにすべてのScenarioの結果が変わる変更（libm、RNGのキー、規則の順序）で1か所（`ENGINE_VERSION`）だけ上げます。今は版2です（exp、expm1、pow、fmaを固定した`libm`のcrateにし、情報のイベントの抽選のキーからイベントのIDを外しました）。`engine:rng_algorithm`はseedとキーから値を引く方法で、Scenarioを作る抽選と共有するので、規則のキーを変えても上げません。2項目がない保存（2項目を記録する前の保存）は、版1と`sha256-keyed-v1`で計算されたものとして扱います。これは明示的な規則で、`fixtures/saved_runs/engine-v1-small`で確かめます。

記録した版が今のモデルと違うRunは**閲覧のみ**です。保存した時点はそのまま表示し、保存の間の時刻は直前の保存の時点に丸めて、丸めたことを応答に出します（`saved_point_rounding`。今のモデルで計算し直しません）。続きの計算、分岐、submit、EffectProgramの適用はエラーコード`run_model_view_only`と日本語の説明で止めます。閲覧用に復元した世界には印（`SavedPointView`）があり、`TickEngine`、コントローラー、`BranchRuntime`、`Checkpoint.capture`は印のある世界を受け付けません。閲覧はProviderを呼ばず、乱数も使いません。詳細は[project-persistence.md](project-persistence.md#旧モデルのrun閲覧のみ)です。

## 永続化とインターフェース

ProjectStoreとTimelineStoreは、ローカルProject、承認済みScenario、Run、Branch、Checkpoint chunk、asset、index付き証拠を保持します。CLI Run成果物にはmanifest、凍結Scenario、event記録、metrics、任意のモデル利用記録が含まれます。formatは有効化した機能によって異なります。APIリファレンスを参照してください。

HTTP APIは次の3領域を分けています。

- /api/v1/projects: 永続Projectと状態変更操作。
- /api/v1/runs: 保存Run成果物の上限付きread-only参照。
- /api/v1/demo: process内のデモBranch。

HTTPサーバーは既定で127.0.0.1にbindします。認証機能がないため、信頼できないネットワークへ公開してはいけません。

## 外部接続との境界

地域データProviderと任意Anthropic adapterはsimulation coreの外側にあります。Providerから得たデータは信頼せず、sourceと適用範囲を保持します。offline replayは保存済み応答か決定的fallbackを使い、過去時点の参照でlive Providerを呼びません。

モデル仮定と検証範囲はsimulation-models.mdとmodel-validation.mdを参照してください。
