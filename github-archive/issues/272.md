## 計測（100人・7日間）

develop `4a3c553` で、100人・7日間（10,080分）の生成Scenarioを offline で1回ずつ計算しました。

- 環境：WSL2、16コア、48 GB。
- 計測：`benchmarks/investigate_performance.py --scenario generated --duration 10080`、`/usr/bin/time -v` でピークRSS。

| 経路 | 計算時間 | ピークRSS | 保存されるデータ |
|---|---|---|---|
| バックエンドのみ（`--route library`、`run_scenario()`、保存なし） | 659.8秒（約11分）、CPU 641.8秒 | 2,878 MiB | なし |
| フロントエンドから（`--route project`、画面の「計算」と同じ `ProjectAPI` の計算、30分ごとに保存） | 1,553.4秒（約26分）、CPU 1,347.8秒 | 5,660 MiB | 5.1 GB（うち履歴索引 `history.sqlite` 4.9 GB） |

- 2つの経路の最終の world のハッシュ（`69aba6590f6b`）は同じでした。
- `--route project` は、ProjectAPI のスレッド方式で測っています。Web サーバーは別プロセス（#260）で計算しますが、計算中に読み取りがなければ、計算の時間は同じです（#260 の計測）。HTTP の受け渡しは含みません。

### 1日（1,440分）あたりの計算時間

| 日 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| バックエンドのみ | 41秒 | 53秒 | 69秒 | 89秒 | 111秒 | 127秒 | 147秒 |
| フロントエンドから | 77秒 | 123秒 | 170秒 | 215秒 | 267秒 | 323秒 | 369秒 |

後の日ほど遅くなります。7日目は、バックエンドのみで1日目の約3.6倍、フロントエンドからで約4.8倍です。

## 気づいたこと

- **保存の時間**：フロントエンドからの経路の約3分の2は、30分ごとの保存です。保存のたびの検証と索引への登録が、たまった履歴の量に応じて重くなります。
- **tick の時間**：tick の時間も日を追って伸びます（#45）。
  - バックエンドのみの経路の tick の時間（637秒）は、フロントエンドからの経路（466秒）より長くなりました。理由はまだ調べていません。
- **容量**：7日分の Run 1つで約5 GB を使います。既定の容量上限（10 GB、`ProjectStore(max_bytes=…)`）では、7日分の Run は2つまでしか保存できません。ほとんどが履歴索引です（#256）。
- **メモリ**：フロントエンドからの計算は、ピークで約5.7 GB を使いました。#271 で、異なる Run を既定2本まで同時に計算できるようにしたので、7日分を2本同時に計算すると 10 GB を超えます。`--max-parallel-runs` の既定値や文書の目安（「1本あたり0.5〜0.9 GB」は1日分の値）を見直す必要があります。

## 確かめていないこと

- 1回ずつの計測です。揺れは測っていません。
- 7日分の Scenario は `--scenario generated --duration 10080`（生成Scenario）です。デモの `fixtures/scenarios/baseline_100_7d.json` では測っていません。
- Windows・macOS では測っていません。CI の Windows では、テストが Linux の約3.6倍遅いことが分かっています（#48 の CI の作業中）。

### Rust の試作（ブランチ `experiment/rust-native`、develop には入れていません）

- **正規化した JSON とハッシュ：** Python と1バイト違わず同じ出力になりました。ただ、Python の json がもともと C で書かれているため、1日分の計算は約1%しか速くなりませんでした。

- **分かったこと：** 大きく速くするには、人ごとの状態を Rust 側に持たせる必要があります。移植は、新しいブランチで続けます。
