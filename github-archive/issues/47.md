## 元の本文

## 現状

100人・生成Scenario・360分・ProjectAPI経路（main `b6a9a3e`、WSL上で1回）では、保存処理 `TimelineStore.record`（12回で17.1秒）のうち、`HistoryIndex.ingest` が12回で5.6秒を占めます。累積値なので、他の内訳とは足し合わせられません。

### 1. 索引登録（`src/sheltersim/storage/history_index.py` の `ingest`）

- 新しいイベント・行動・会話などの記録を、保存のたびにSQLiteへ登録しています。
- チームメンバーの1日分の計測では、49回で約85秒（うちCPU 50秒）でした。CPU時間との差から、SQLite内部の同期待ちも含まれると考えられます。
- 案: 書き込みをまとめる、またはトランザクションの粒度を見直す。
- 索引の内容と意味は変えません。同期設定を弱めるかどうかは、クラッシュ時の安全性と合わせて判断してください。
- まず内訳を測ってください（SQLの実行、同期、記録の組み立て）。

### 2. 容量チェックのための全ファイル走査（`ProjectStore.usage()`）

- `_write` のたびに `root.rglob("*")` で全ファイルを走査しています。保存1回につき数回呼ばれ、ファイル数とともに遅くなります。
- チームメンバーの1日分の計測では、300回で約16秒でした。
- 案: 書き込み量の台帳と組み合わせて走査を減らす。
- 他のプロセスによる更新や容量上限との整合を弱めないでください。

## 完了の条件

- 索引の全記録（`kind`・`key`・`payload_hash`）が修正前と一致すること
- 容量上限・pending ledger・クラッシュからの回復のテストが成功すること
- offline全体テストが成功すること

### 2026-10-28T16:08:10Z — WaTeR-7

元コメント: https://github.com/jphacks/tkb_2615/issues/47#issuecomment-6474144733 / 更新: 2026-10-28T16:08:10Z

PR #217（develop、マージコミット 7b6afbd）で対応しました。索引登録をまとめて行い、書き込み用のSQLiteキャッシュを16 MiBにし、容量チェックの走査を os.scandir にしました。100人・1440分では ingest が 33.96→21.24秒、usage() が 6.50→2.65秒です。索引の全記録と world・events・metrics のハッシュは修正前と一致しました。保存1回あたりの走査回数は、ロックを取らない書き込みとの整合を保つため減らしていません。
