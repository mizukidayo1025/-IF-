## 元の本文

## 現状

容量の確認（`ProjectStore.usage()`）は、呼ばれるたびにストア全体（すべての Project と Run）のファイルを数え直します（#47 で `os.scandir` にして1ファイル1回の stat にしたもの）。Checkpoint の保存1回で約7回呼ばれます。

- JSON の書き込みごと
- archive の新しい chunk の上限
- history index の書き込み後
- frame のキャッシュ

ストアにある Run の数に比例して遅くなります。1440分まで計算した Run（約3,400ファイル）を複製して、`usage()` 1回の時間を測りました（WSL上、5回のうち最短）。

| ストアにある1日分の Run | ファイル数 | `usage()` 1回 |
|---:|---:|---:|
| 1 | 3,441 | 9.6ミリ秒 |
| 5 | 17,205 | 49.2ミリ秒 |
| 10 | 34,410 | 99.2ミリ秒 |

Run が10あるストアでは、保存1回あたり約0.7秒、1日分の計算（保存48回）で約33秒増える見込みです。ベンチマーク（Run 1つ）では1日1.9秒なので、これまでの計測には表れていませんでした。

## 決めること

#47 では、別のプロセスが鍵なしで書くファイルとの一貫性を保つため、保存ごとの走査を減らさないと決めました。減らすには、その一貫性をどこまで保つかを決める必要があります。

- 1回の保存の中では、最初に数えた値に、その保存が書いたbyte数を足して使う（保存の途中で別のプロセスが書いた分は、次の保存まで数えない）
- Project・Run ごとの使用量を記録して足し合わせる（別のプロセスの書き込みも記録に残す仕組みが要る）
- 容量の確認を、保存の前に1回だけ行う

## 確かめること

- Run を複数置いたストアでの、保存1回の時間
- 容量を超える書き込みを拒否し、書く前の状態に戻すこと（既存のテスト）

## 判断：保存1回の中では最初に1回だけ数える（PR #243）

「決めること」の1つ目の案を採用し、#47 の「保存ごとの走査を減らさない」という決定を変えます。

### 変える点
Checkpoint の保存（`ProjectStore._save_branch`）の中では、容量を確かめるたびにストア全体を数え直すのをやめます。最初に1回だけ数え、それ以降の確認では、その値にこの保存が書いた byte 数とファイル数を足して使います。保存の外での確認（履歴索引、frame のキャッシュ、画面の使用量表示）は、これまでどおり毎回数え直します。

### 影響の見積もり（コードから）
- **ふつうの使い方では今と同じです。** サーバー1つで Run を計算する場合、履歴索引と frame のキャッシュは保存が終わったあとに同じスレッドで書きます（`experiments/timeline.py`）。計算 worker も1つずつしか動きません。保存の途中で書く人がいないので、確認の結果は変わりません。
- **容量上限を超えうるのは、保存の途中に別のスレッドや別のプロセスが同じストアに書いた場合だけです。** 2つの保存はプロセス間のロックで重ならないので、ここには入りません。
- **超える量は、保存1回分の書き込みまでです。** 別の書き手は、書く前に自分でディスクを数え直します。その値には、この保存がすでに書いた分が入っています。漏れるのは、その確認のあとにこの保存が書いた分だけです。1日分の Run（100人）では、Checkpoint は全部で約23 MB、保存48回なので、1回あたり平均約0.5 MB です（既定の上限は 10 GB）。
- **超えても、データは壊れません。** 次に数え直す書き込みが拒否されるだけで、上限にちょうど達したときと同じ動きです。たとえば次の保存は `StorageError` になり、Run は `failed` になります。
- 今の develop も厳密な上限ではありません。frame のキャッシュは、ロックを取らずに確認してから書くので、確認から書き込みまでの間に別のプロセスが書く余地があります。この PR は、その隙間を保存1回の長さに広げるものです。

### テスト
`tests/unit/storage/test_projects.py` に次の2つがあります。
- `test_a_save_counts_its_own_writes_onto_one_measurement`：保存1回でディスクを数えるのは1回だけです。保存の終わりに、足し合わせた使用量が、そこで数え直した値と一致します。
- `test_another_writer_during_a_save_overshoots_by_at_most_that_save`：保存の途中に、同じフォルダーを開いた別の `ProjectStore` が、自分で数え直してから書き込みます。このとき、保存は通り、上限を超える量は0より大きく、その保存が書いた量以下です。さらに、次の保存は数え直して拒否されます。develop では、この場面で保存が拒否されることを確かめました。

### 効果（develop `1aecb2b`、WSL2、交互に3回ずつ）
1日分の Run を10個置いたストア（34,410ファイル、6.4GB）で、新しい Project を360分計算しました。

| | 1回目 | 2回目 | 3回目 |
|---|---:|---:|---:|
| develop | 30.8秒 | 30.1秒 | 30.3秒 |
| develop + #243 | 25.4秒 | 25.0秒 | 24.6秒 |

head の Checkpoint のハッシュは同じでした。Run が1つだけのストアでは、ほとんど差が出ない見込みです。

`docs/project-persistence.md` の容量の説明も、同じ PR で更新しています。
