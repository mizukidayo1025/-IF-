## 現象

`tests/integration/test_resume_checkpoint_loads.py::test_resume_loads_the_head_checkpoint_once` が、offline 全件（`-n auto`）を10回続けて実行したうち2回失敗しました（2026-10-28、Ryzen 7 9800X3D、WSL2、PR #144 のブランチ）。2回とも同じ箇所です。

```
        api = ProjectAPI(store)
        try:
            api.submit("p", "r", "main", 5)
>           assert loads == []
E           AssertionError: assert ['0cd93a5c52e...e428008ad37f'] == []
E             Left contains one more item: '0cd93a5c52ee6ed97f5deebad9cd68c28481cf7f5adca7d296ede428008ad37f'

tests/integration/test_resume_checkpoint_loads.py:32: AssertionError
```

ほかの8回は通りました。この10回では、ほかのテストは失敗していません。

## 原因（コードを読んだ範囲）

`assert loads == []` は、「`submit()` は head checkpoint を読まない（読むのはworkerだけ）」ことを確かめる意図です。`ProjectAPI.submit()`（`src/sheltersim/web/projects.py`）は、`branch_reference`・`run`・`scenario` だけで範囲を確かめ、`self._pool.submit(self._advance, ...)` でworkerに渡して戻ります。`load_checkpoint` を呼ぶのは `_advance` です。

ところが、workerのthreadは `submit()` が戻る前後にすぐ動き出せるので、テストのthreadが `assert loads == []` に着く前に `_advance` が `load_checkpoint` を呼ぶことがあります。並列実行でCPUが混むと、threadの切り替えの時機がずれて起きやすくなると考えられます。製品コードの不具合ではなく、テストがthreadの実行順に頼っていることが原因です。

## 直し方の案

workerが動き出せない状態で `submit()` を呼び、確かめてから放します。`ProjectAPI` のpoolは `max_workers=1` なので、例えば次の形にできます。

1. `api.submit` の前に、`threading.Event` を待つだけのtaskを `api._pool` に入れて、workerを止めておく。
2. `api.submit(...)` のあと `assert loads == []` を確かめる。
3. Eventを立ててworkerを放し、今と同じく `api._pool.submit(lambda: None).result(timeout=60)` で完了を待つ。

`loads` に記録したthreadを見て「`submit()` を呼んだthreadからは読んでいない」と確かめる形も考えられます。

## 完了の条件

- 修正後に、offline の全件（`-n auto`）を繰り返し実行して、このテストが失敗しないことを確かめる（回数と結果を記録する）。
- 確かめる内容（`submit()` は読まず、workerが1回だけ読んで検証する）は変えない。
