## 起きること

`policy_registry` がモデル一式（`suite_id: core-model-suite-v2`）だけで、領域ごとの指定がないScenarioがあります。このScenarioでは、manifestに記録する宣言上のモデルと、実行時に実際に使うモデルが違います。

- 宣言上のモデル：`selected_models` と `model_signatures` が返すもの。manifestの `policy_implementations`・`policy_versions` や、Checkpointの署名に入る
- 実行時のモデル：一部のコードが `policy_registry` の個別のキーを直接読み、キーがなければsuiteではなく昔の既定に戻る

旧UIのdemoのプリセット8つ（`scenario_editor.build_scenario_preview`）は、すべてこの形でした。

| 領域 | 宣言上のモデル | 実行時に使われるもの | 読んでいる箇所 |
|---|---|---|---|
| relationship | `distance-duration-repeat-trust-v1` | `DurationOnlyTrustPolicy` | `policies/relationships.py` の `create_relationship_policy` |
| queue | `need-weighted-physical-queue-v1` | `StrictFIFOQueuePolicy`（図面なし）／`NeedWeightedPhysicalQueuePolicy` の直接生成（図面あり） | `policies/queueing.py` の `create_queue_policy` |
| psychology（誤情報の圧力だけ） | `mean-reverting-life-state-v1` | `causal-stress-v1` とみなし、誤情報の圧力を0にする | `policies/behavior.py`（`psychology_model_id` の取得） |

psychologyのモデル自体は、`selected_models` で選ばれます（`domain/simulator_state.py`、`contracts/runtime.py`）。ずれるのは、行動の判断に渡す誤情報の圧力の計算だけです。

UIの生成Scenario（`initial_scenario.py`）は、suiteの領域をすべて個別にも書いているので、この問題は起きません。

## この形を書く入口

- `experiments/model_suite.py` の `install_default_model_suite`。suiteの領域のキーを外して `{schema_version: 3, suite_id: ...}` にする
  - `scenario_editor.build_scenario_preview`（`force=True`。旧UIのdemo `web/demo.py` から使う）
  - `sheltersim prepare`（入力に `policy_registry` がないとき）

## 再現

```python
from sheltersim.experiments import scenario_editor as se
from sheltersim.contracts.policies import selected_models
from sheltersim.policies.relationships import create_relationship_policy
from sheltersim.policies.queueing import create_queue_policy

scenario, _ = se.build_scenario_preview(
    se.ScenarioEditorRequest(schema_version=1, preset_id="baseline_100_7d")
)
configs = scenario.model_configs
selected_models(configs)["relationship"]           # distance-duration-repeat-trust-v1
type(create_relationship_policy(configs)).__name__  # DurationOnlyTrustPolicy
selected_models(configs)["queue"]                  # need-weighted-physical-queue-v1
type(create_queue_policy(configs)).__name__         # StrictFIFOQueuePolicy
```

同じScenarioで、`with_behavior_policy_variant` を使ってsuiteを個別の指定に展開すると、`create_relationship_policy` は `DistanceDurationRepeatTrustPolicy` を返します。宣言上のモデルは変わらないのに、実行時のモデルが変わります（#157 の比較では、このため拒否するようにしました）。

## 期待すること

manifestとCheckpointに記録するモデルと、実行時に使うモデルが一致すること（AGENTS.mdの「provenanceをRun成果物に残す」）。

直し方の候補は次の2つです。
- 実行時の解決を `selected_models` に揃える。suiteが宣言したモデルを、実行時も使う。
- suiteを書く側（`install_default_model_suite`）で、suiteの領域を個別にも書く。生成Scenarioと同じ形にする。

どちらの場合も、旧UIのdemoのプリセットなどで、実行時のモデルが変わります（relationship、queue、誤情報の圧力）。結果も変わるので、保存済みのRun・Checkpointの再生と、回帰の契約（`fixtures/regression-contract.json` など）への影響を確かめる必要があります。どのモデルを既定として使うかは、モデル担当と相談して決めます。モデルの係数は変えません。

## テスト

`selected_models` が返すモデルと、実行時に生成されるPolicyが一致することを確かめるテストを足します。対象は、suiteだけを指定したScenarioの relationship・queue と、誤情報の圧力を使うかどうかの判定です。
