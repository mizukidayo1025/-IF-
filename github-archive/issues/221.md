## 元の本文

## 現状

Checkpoint保存のたびに、履歴索引（SQLite）へ新しい記録を登録しています。同じ計測（100人・生成Scenario・1440分・ProjectAPI経路、develop `92695f8`、WSL上で1回）で、保存1回あたりの登録時間は次のとおりでした。

| 時刻 | 30分 | 1440分 |
|---|---:|---:|
| 履歴索引への登録 | 約0.17秒 | 約0.5秒 |

索引が大きくなるほど、書込み中のページがキャッシュに収まらなくなり、時間が伸びます。

## 経緯

#47（PR #217）で書込みキャッシュを16 MiBにしました（`storage/history_index.py` の `_WRITE_CACHE_KIB`）。64 MiBにするとさらに速くなりましたが、ピークRSSが約55 MiB増えるため保留にしました。#44（PR #219）でも、計算中にキャッシュを持ち続けるためピークRSSが約62 MiB増えています。

## 提案

次のどちらにするかを決めます。

- 書込みキャッシュを大きくする（メモリ使用量との兼ね合いを決める）
- キャッシュの大きさに頼らず、1回の登録で触るページを減らす方法を検討する

## 完了の条件

- 書込みキャッシュの大きさ、または別の方法が決まっていること
- 変える場合は、1日分の計測で保存1回あたりの登録時間とピークRSSを修正前と比べて示し、offline全体テストが成功すること

## 現在の値（実時間、100人・生成Scenario・1440分・ProjectAPI経路、develop `4bd949e`、WSL上で1回）

1日分の history index への登録は計17.3〜17.8秒で、内訳は次のとおりでした。

| 処理 | 時間 |
|---|---:|
| SQLite への書き込み（`executemany`） | 8.0〜8.5秒 |
| commit と close | 約2.7秒 |
| 行ごとの Python 側の処理（個人情報の検査、正準JSON、ハッシュ、IDと検索語の収集） | 約5〜6秒 |
| 行ごとの「同じキーの行があるか」の問い合わせ | 0.3秒 |

1日で、記録 約11.5万行、関係するID 約127万行、検索語 約84万行を登録します。

SQLite 側（約11秒）を減らすには、次のどちらかの判断が要ります。

- 書込みキャッシュを大きくする
- 索引の中身や張り方を変える

Python 側の処理は、#224 で個人情報の検査を速くしました。IDとイベント参照の収集を1回の走査にまとめる実装も試しましたが、全体の時間は計測の揺れの範囲でした。

## 判断：書き込みキャッシュは 16 MiB のままにする（PR #244 は見送り）

PR #244（64 MiB にする）を、今の develop（`82d96cd`）で測り直しました。100人・生成Scenario・1440分・ProjectAPI経路、WSL2 上で、順番を入れ替えて4回ずつ測っています。

| | 索引への登録（実時間） | 索引への登録（CPU時間） | ピークRSS |
|---|---|---|---|
| 16 MiB（develop） | 19.6 / 18.8 / 19.4 / 20.0秒 | 15.1 / 15.0 / 15.0 / 15.0秒 | 829 / 852 / 853 / 843 MiB |
| 64 MiB（#244） | 35.2 / 18.3 / 19.3 / 18.2秒 | 14.9 / 15.1 / 14.9 / 14.8秒 | 837 / 865 / 888 / 854 MiB |

- 登録時間は、1日あたり約0.9秒（1日の計算の約1%）しか短くなりませんでした。平均で約19.5秒 → 約18.6秒です。
  - この平均は、64 MiB の1回目（35.2秒）を除いています。この回は CPU 時間がほかの回と同じなので、ディスクの待ちによる外れ値と見ています。
  - 短くなったのはディスクへの書き出しの待ちで、CPU時間は変わりません。
- PR 作成時（19.1秒 → 16.5秒）より効果は小さくなりました。実時間の揺れ（数秒）に埋もれる大きさです。
- ピークRSSは平均で約17 MiB 増え、最大は 888 MiB でした。上限が増えるため、最大で約48 MiB 増えるおそれがあります。#242 で計算中のメモリを約47 MiB 増やしたばかりなので、これ以上は増やさないことにしました。

残る案は、キャッシュの大きさに頼らず、1回の登録で触るページを減らす方法です。たとえば、索引の中身や張り方を変えるものです。上の計測では、登録の約15秒が CPU 時間で、その内訳は SQLite への書き込みと行ごとの Python の処理です。
