## 背景

#136 で、実時間の期限つきで待つテストを見直しました。期限を延ばすのではなく、完了そのものを待てる形にできるものを、ここにまとめます。

| 場所 | 今の待ち方 | 待つ相手 |
|---|---|---|
| `tests/conftest.py` の `_wait_for_job`（fixture `wait_for_job`。`tests/integration/test_demo_jobs.py` と `tests/e2e/test_demo_jobs_http.py` で6か所） | 5秒の期限で0.01秒ごとに状態を読む | `DemoJobManager` のjob。期待する状態はどれも終わりの状態（`completed`・`cancelled`・`failed`） |
| `tests/integration/test_demo_live_recompute.py` の `_wait_for_completion` | 10秒の期限で同上 | `DemoJobManager` のjob（終わりの状態） |
| `tests/integration/test_scenario_editor.py::test_frozen_scenario_restores_its_run_id_with_a_saved_job_checkpoint` | 5秒の期限で同上 | `DemoJobManager` のjob（`completed`・`failed`） |
| `tests/integration/test_llm_outcomes.py::test_project_report_exists_before_the_run_is_marked_completed` | 0.1秒ごとに600回（約60秒）状態を読む | `ProjectAPI` の実行（`running` でなくなるまで） |

`DemoJobManager`（`src/sheltersim/web/jobs.py`）も `ProjectAPI`（`src/sheltersim/web/projects.py`）も、`max_workers=1` の `ThreadPoolExecutor` でjobを順に実行しており、`submit` が返すFutureは捨てています。

## 期限の余裕（2026-10-28 の計測）

#136 の結果ファイル（`.test-results/`）で、`-n auto` の全件11回分のcall時間を見ると、上のテストはどれも期限の3分の1以下でした（テスト全体の時間で、待ちの部分はその一部です）。

- `test_demo_live_recompute`：最大1.62秒（期限10秒）
- `test_scenario_editor` の該当テスト：最大1.32秒（期限5秒）
- `test_demo_jobs.py` の各テスト：最大1.02秒（期限5秒）
- `test_llm_outcomes` の該当テスト：最大0.78秒（約60秒）

Ryzen 7 9800X3D（16スレッド）での値です。遅いPC（`docs/testing.md` にある Ryzen 5 5625U では全件が数倍かかります）では、5秒の期限に近づくおそれがあります。この11回で、これらのテストは失敗していません。

## やること

1. 終わりの状態を待つ箇所は、実時間の期限ではなく、jobの完了を待つ形にします。案は次のどちらかです。
   - テスト側：workerが1つなので、`manager._executor.submit(lambda: None).result(timeout=...)`（`ProjectAPI` は `api._pool`）でそれまでのjobが終わるのを待ってから状態を確かめる。`tests/integration/test_resume_checkpoint_loads.py` と `tests/unit/web/test_projects.py` が `api._pool` ですでにこの形を使っています。
   - 製品側：jobのFutureを保持し、完了を待つ手段を用意する（公開の契約が変わるので、`docs/` の更新が要ります）。
2. `timeout` は、止まったときにテストが終わらなくなるのを防ぐためだけに残し、通常の実行時間とは無関係な大きさにします。

## 対象外にしたもの（見直した結果）

- `tests/integration/test_demo_jobs.py` の `Event.wait(timeout=3)`（6か所）：すでにイベントで待っており、期限は止まったときの安全のためです。ただし `entered.wait(timeout=3)` はworkerが動き出すまでの待ちなので、上のjob待ちを直すときに、同じ大きさの期限でよいかを確かめます。
- `tests/e2e/test_project_scenario_to_results.py` の300秒の期限：HTTPの外側から状態を読むe2eで、完了を通知する経路がありません。計測では最大56秒で、余裕があります。

## 完了の条件

- 上の表の待ちが、実時間の短い期限に頼らない形になっている。
- offline の全件（`-n auto`）で、待ち方を変えたテストが通る。
