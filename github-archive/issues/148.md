## 現象

`tests/live/test_live_api.py::test_live_opus_sonnet_and_haiku_calls_are_durably_capped_and_replayable` を、利用者の承認を得て1回だけ実行すると失敗しました（2026-10-28、上限 3 call・0.15ドル）。

```
SHELTERSIM_ALLOW_LIVE_API_TESTS=1 scripts/test-live-api.sh -k opus_sonnet_and_haiku
```

```
        outputs = [router.complete(task) for task in tasks]
>       assert [output for output in outputs if '"ok":true' in output] == outputs
E       assert ['{"ok":true}', '{"ok":true}'] == ['{"ok":true}...{"ok":false}']
E         Right contains one more item: '{"ok":false}'

tests/live/test_live_api.py:165: AssertionError
```

- PREPARE（Opus）と INTERVENTION（Sonnet）は実際に呼ばれ、`{"ok":true}` を返しました。利用記録（task-global-v1）の receipt は2件、推定費用は合計約0.0011ドルです。
- RUNTIME（Haiku）は Provider を呼ぶ前に断られ、fallback の `{"ok":false}` になりました。receipt は作られていません。

## 原因（コードを読み、APIを呼ばずに確かめた範囲）

`AccountedProvider`（`src/sheltersim/llm/accounting.py`）は、RUNTIME の呼び出しを予約するときに `keep_calls_free=ANALYSIS_RESERVED_CALLS`（3）を渡します。`UsageLedger.reserve`（`src/sheltersim/storage/usage.py`）は、`spare = min(keep_calls_free, limits.max_calls - 1)` 件を後の作業のために残し、`使った件数 + 1 > max_calls - spare` なら `usage_runtime_share_exhausted` で断ります。

このテストの台帳の上限は3件なので、`spare = min(3, 2) = 2` です。runtime を呼ぶ時点で2件を使っているので `2 + 1 > 3 - 2` となり、毎回断られます。この規則は `ced1c5b`（2026-10-24「Keep calls for the report when runtime decisions share a Run allowance」）で入りました。このテストはそれ以前の上限と順番のままなので、そのときから必ず失敗する状態だったと考えられます（それ以降にライブ実行した記録は見つかっていません）。

製品の規則（runtime が分析用の枠を残すこと）は意図どおりで、テストの呼ぶ順番と上限の組み合わせが合っていません。

## 直し方の案

どちらも、テストを直したあとのライブ実行に、その時点の承認と予算が要ります。

1. **呼ぶ順番を変える（上限は変えない）：** RUNTIME（Haiku）を最初に呼びます。最初の1件なら `0 + 1 > 1` にならないので予約できます。PREPARE と INTERVENTION は枠を残す必要がないので、そのあとの2件も3件の上限に収まります。テストの `router.records` のモデル順の確認（`[opus, sonnet, haiku]`）も合わせて直します。
2. **上限を増やす：** 台帳の `max_calls` を、runtime が残す枠を足した数にします。予算と上限の変更になるので、`docs/llm-integration.md` の「モデル別確認：3 call、0.15ドル」も直す必要があります。

1は、上限を変えずに済みます。

## 未確認のこと

- ほかの3件のライブテスト（PDF、公式ドメイン検索、機能の通し確認）は実行していません。runtime の呼び出しを含むものが、同じ規則で断られるかは確かめていません。
- 修正の案を、偽のProviderでのoffline再現で確かめてはいません（新しい状態ディレクトリでは、campaign の台帳の準備が違うので、別の理由でも断られました）。

## 完了の条件

- モデル別確認のライブテストが、上限の中で3つのモデルを1回ずつ呼んで通る（実行の承認・予算・費用を記録する）。
- 確かめる内容（3モデルの呼び出し、上限、再生）は変えない。
