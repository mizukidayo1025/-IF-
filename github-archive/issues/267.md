## 背景

#35（介入の対象候補の整理）は PR #266 で対応して閉じました。そのとき扱わなかった次の3つを、この Issue にまとめます。

## 1. 設備の停止を、AI 経路でトイレ以外に広げてよいか

- ルール処理（`llm/natural_language.py` の `_resolve_target`）では、設備の停止（`facility_outage`）の対象はトイレ設備だけです。
- AI（Opus）経路では、対象の種類（設備）が合っていれば、受付・救護の窓口・食事配布などトイレ以外の設備も対象にできます。
- どちらにそろえるかを決める必要があります。トイレ以外の停止を許す場合は、停止したときに何が起きるか（各設備の利用者の扱い）をモデルとして確かめる必要があります。

## 2. 選んだ対象を専用の項目で渡す（#35 の案C）

- 今は、聞き返しの選択肢を押すと、指示文の末尾に `zone_id: <ID>`（Project 画面では Zone 以外は `対象ID: <ID>`）の行を足して、もう一度 Preview します（/demo-v2、Project 画面）。
- ルール処理はこの行を明示された対象として使いますが、Opus 経路では自由文の一部です。追加先として使わせる仕組みはありません。
- `intervention-preview` に、選んだ対象を渡す専用の項目を足す案です。API 契約の変更になります。

## 3. ライブ API での Opus の聞き返しの確認

- PR #266 では実 API を呼ばず、偽の応答で確かめました。
- Opus が実際にどう聞き返すかは、まだ確かめていません。選択肢の有無、内容、`zone_id:` を足したあとの挙動です。
- 確かめる場合は、呼出し回数と予算の上限の承認が必要です（AGENTS.md）。

## 完了の条件

- 1 と 2 は、進めるかどうかと方式が決まり、進める場合は offline のテストとともに実装されていること
- 3 は、確かめるかどうかが決まり、確かめる場合は承認された予算の中で結果が記録されていること
