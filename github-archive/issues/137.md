## 背景

UIで作るScenarioは、必ず図面（`facility_geometry`）と認知（`agent_dynamics`）を持ちます。一方、`fixtures/` のScenarioはどちらも持ちません（`docs/testing.md`「利用者の経路を通る共通fixture」）。#88 では一部のテストを共通の生成Scenarioへ移しましたが、#126 では置き換えを範囲外にし、「移すときに置き換えが必要だと分かったテストは、別のIssueにする」としていました。#126 が終わったので、ここで洗い出します。

図面と認知があると通る処理が変わるのは、`src/` で確かめると次のところです。

- 画面のframe（`inspection/frames.py`）：人と施設の位置を図面から取る。図面がないときは `display_x`・`display_y` を使う。
- Checkpointと保存（`core/checkpoint.py`、`core/world.py`、`storage/history_index.py`）：移動の状態（`movement_v1`）と図面の重ね合わせを持つ。
- 移動・待ち行列・職員・施設の利用（`domain/movement.py`、`queueing.py`、`facility_queues.py`、`staff.py`、`staff_operations.py`、`experiments/runner.py`）：図面上の経路、サービス地点、職員のところまで歩くこと。
- 社会・情報：生成Scenarioでは既定で `social_propagation` と `information_spread` が有効で、関係のPolicyは距離を使う `distance-duration-repeat-trust-v1` です。

## 洗い出し

統合・e2eで fixture のScenarioを実行するファイルは48本あります（`docs/testing.md` の地図で「Scenario」に fixture を含むもの）。確かめている振る舞いで、次の3つに分けました。

### A. 置き換えが必要

確かめている振る舞いが、図面と認知の有無で通る処理が変わるものです。

| ファイル | 理由 |
|---|---|
| `integration/test_checkpoint_resume.py`、`integration/test_branch_forks.py`、`integration/test_exact_timeline.py`、`integration/test_trace_level.py` | 再開・分岐・seek・trace level の再現性（AGENTS.md の不変条件）を、移動の状態と図面の重ね合わせを持たないWorldStateでしか確かめていない。Project画面では生成Scenarioをseekし、分岐させる |
| `integration/test_timeline_frame_cache.py`、`integration/test_replay_frames.py` | frameの一致を、図面から位置を取らない経路でしか確かめていない（図面ありの描画は `integration/test_installed_facility_rendering.py` が一部だけ確かめている） |
| `integration/test_resource_service.py` | 給水・配食への移動・待ち・職員つきのサービスを、サービス地点も部屋内の移動もない状態で確かめている（生成Scenarioでの待ち行列は `integration/test_queue_service.py` などが一部確かめている） |

### C. 要確認

置き換えが要るかを、読むだけでは決められなかったものです。

| ファイル | 確かめること |
|---|---|
| `integration/test_information_spread.py`、`integration/test_stress_propagation.py`、`integration/test_research_psychology.py`（fixture分） | 生成Scenarioでは既定で有効で、距離を使う関係のPolicyと組み合わさる。接触の選ばれ方が変わり、確かめている振る舞いに影響するか |
| `integration/test_support_priority.py`、`integration/test_llm_outcomes.py` | 支援の優先度をLLMに尋ねる契機（ストレスの高い人の支援要請）が、職員のところまで歩く生成Scenarioでも同じように起きるか |
| `integration/test_multi_plan.py`、`e2e/test_multi_plan.py`、`integration/test_nl_demo.py`、`e2e/test_nl_demo_branching.py`、`integration/test_timed_branch_plan.py` | demo の経路（`web/demo.py`）だけを通る。Project画面に同じ機能があるなら、その経路を生成Scenarioで確かめるテストがあるか |
| `integration/test_pdf_report.py`、`e2e/test_pdf_download.py` | 12人・40分のfixtureのRunでレポートを作っている。生成ScenarioのRunだけにあるKPI（運営の指標など）がレポートに入るか |
| `integration/test_web_inspector.py`、`e2e/test_web_inspector_http.py`、`integration/test_behavior_policy.py` | inspectorの地図は、図面がないとき合成のgym配置を使う。behavior variantの再生は、生成ScenarioのRunでも同じように確かめるべきか |

単体の51本は、部品の検査として fixture を使ってよい（`docs/testing.md`）ので、上の手書きKPIの1件を除いて対象にしていません。時刻を手で動かす単体テストに、対になる統合テストがないこと（地図の「見えた穴」2）は別の課題です。

## 進め方

1. A を先に行います。#88 と同じく、共通fixture（`generated_scenario` など）を使う形にし、生成器が作らない形が要る場合は、理由を書いて fixture に手で足します。
2. C は、まず生成Scenarioで同じテストを実行してみて、結果が変わるかで A か B に振り分け、このIssueに記録します。
3. 置き換えで見つかった不具合は、テストで隠さず別のIssueにし、`xfail(strict=True, raises=…)` とIssue番号を付けて置きます。
4. PRは、A の行ごとにまとめます。各PRで offline の全件と `ruff check .` の件数を確かめ、`docs/testing.md` の地図（Scenario欄）を直します。

## 完了の条件

- A のテストが生成Scenarioで確かめている（または、置き換えられない理由がテストに書かれている）。
- C のすべてが A か B に振り分けられ、その結果がこのIssueに記録されている。
- 地図の「Scenario」欄が実態に合っている。
