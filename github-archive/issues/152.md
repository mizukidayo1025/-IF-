## 元の本文

## 現象（コードを読んだ範囲。ライブ実行はしていません）

`tests/live/test_live_api.py::test_live_official_domain_search_returns_only_verifiable_source_candidates` は、台帳の口座を毎回同じIDで開きます（2026-10-28 の `develop`、`7ab019d`）。

```python
local = UsageLedger(store, "runtime-accounts", "live-source-search-stream-qa")
local.create(usage_limits(settings))
```

- `UsageLedger.create`（`src/sheltersim/storage/usage.py`）は、口座のファイルがすでにあると何もしません。receipt は `runs/.projects/runtime-accounts/usage/live-source-search-stream-qa.json`（`runtime_usage_store()` の既定の場所、gitには登録されない）に実行をまたいで残ります。
- このテストの上限は `max_api_calls=2`（予算10ドル）です。予約は1回につき1 call と数えられ、このテストは1回の実行で1回呼ぶので、2回実行するとこの口座の上限に達します。3回目からは Provider を呼ぶ前に断られ、`router.records[-1].outcome == "recorded"` の確認で失敗すると考えられます。
- つまり上限が「1回の実行ごと」ではなく「このPCで通算」になっています。#148 では、モデル別確認が同じ理由で、2回目の実行から必ず断られていました。

このPCには、この口座のファイルはまだありません（このテストはここでは実行されていません）。2回で上限に達するという見立ては、実行して確かめてはいません。

## 直し方の案

PR #151 と同じく、実行ごとに別の口座を開きます。同じファイルの `test_live_scenario_intervention_runtime_review_and_results_question` は、すでに `f"live-feature-{run_tag}"`（`run_tag = uuid.uuid4().hex[:12]`）で実行ごとの口座を使っています。

- 口座IDを `live-source-search-stream-qa-<乱数>` にします。全実行の合計は、これまでどおり端末の共有上限（task-global-v1、既定50ドル）が抑えます。
- できれば、#148 の `live_model_check` と同じように、設定と口座の準備を fixture にまとめ、offline のテストで「同じ記録先で2回続けても予約できる」ことを確かめます。web検索の呼び出しを偽の Provider でどこまで再現できるかは、調べる必要があります。
- `docs/llm-integration.md` の「公式ドメイン検索：2 call分の枠」に、上限が実行ごとであることを書き足します。

## 範囲外

- 上限（2 call、予算10ドル）や、確かめる内容（候補が検証できる出典だけであること）を変えること。

## 完了の条件

- 公式ドメイン検索のライブテストが、実行ごとの口座で予約する。
- 修正を確かめるライブ実行をする場合は、その時点の承認と予算を得て、回数・結果・費用を記録する。
