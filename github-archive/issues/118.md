## 元の本文

## 現象

1つの給水所・配食所に提供地点が複数あり、それぞれが独立した列を持つ場合に起きます。施設の容量が提供地点の数より小さいと、2本目の列の先頭は「容量」の理由で止まったと記録されます。その直後の状態の検証が `resource queue stall must describe the current facility queue head` で失敗し、シミュレーションが止まります。

## 再現

#88 のテスト移行中に確認しました（`develop` の `c8e8481`）。

1. 共通fixtureの生成Scenarioで、`water_station_main` の提供地点を左右2つに分け、それぞれに列（`water_station_main-left-fifo`・`-right-fifo`）を持たせる。施設の容量は1のまま。
2. 給水所の区画に3人を立たせ、左の列に2人、右の列に1人で給水を頼む。
3. TickEngine で進めると、3分目に止まる。

止まったときの状態:

| 項目 | 値 |
|---|---|
| 止まった記録（`stall_state`） | `{"water_station_main": {"agent_id": "A003", "reason": "capacity"}}` |
| 施設全体の列（`resource_queue_agent_ids`） | `["A002", "A003"]` |
| サービス中 | `["A001"]` |
| 左の列 | 待ち `A002`、サービス中 `A001` |
| 右の列 | 待ち `A003` |

## 原因（コードで確認済み）

- 独立した列では、列ごとの先頭が止まった理由を記録します（`domain/resource_service.py` の `_arbitrate_independent_facility`）。ここでは右の列の先頭 `A003` が記録されます。
- `WorldState.validate`（`core/world.py` 430行付近）は、止まった記録が施設全体の列の先頭（`resource_queue_agent_ids[0]`、ここでは `A002`）を指すことを求めています。独立した列を考えていません。

## 影響

生成Scenarioは施設ごとに提供地点を1つしか作らないので、画面から作ったScenarioでは起きません。提供地点を複数持つ図面（図面の取り込みなど）で、容量が提供地点の数より小さいと起きます。

## 関連

- #88：`tests/integration/test_facility_queues.py` に、期待する振る舞いを `xfail(strict=True)` で置きます。移行したテストの共通fixture（`generated_scenario_with_split_queues`）は、提供地点の数に合わせて容量を2にしています。

元コメント: https://github.com/jphacks/tkb_2615/issues/118#issuecomment-6445317329 / 更新: 2026-10-27T14:57:22Z

#123 を develop にマージしました。既定ブランチが main のため、PR の Closes では自動で閉じないので手動で閉じます。

- **検証の修正**：止まった記録の検証と、古くなった記録の掃除で、独立した列がある施設ではどの列の先頭を記録していても認めるようにしました。再現条件（容量1・提供地点2・3人）でも止まらず、3人とも給水を受けます。
- **あわせて直したこと**：2本の列が同時に待つ間、施設の停止記録が分ごとに入れ替わり、停止の履歴と待ちの理由ごとの回数（断水・在庫不足は KPI にも出ます）を数え直していました。いまは、記録中の人が同じ理由で待ち続けていればそのまま、そうでなければ列IDの順で最初に止まった列の先頭を記録します。保存する状態の形は変えていません。
- **テスト**：`tests/integration/test_facility_queues.py` の xfail を外し、停止の履歴が待った2人について1件ずつであることも確かめるようにしました。検証の単体テストは `tests/unit/core/test_world.py` に足しました。
