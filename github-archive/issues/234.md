## 元の本文

## 現状

100人・生成Scenario・1440分・ProjectAPI経路（develop `4bd949e`、WSL上で1回）で、Python の循環参照の回収（`gc`）に計7.6秒かかっていました。1日分の計算は112.0秒なので、約7%に当たります。

| 世代 | 回数 | 時間 |
|---|---:|---:|
| 0 | 39,041 | 1.22秒 |
| 1 | 3,549 | 0.55秒 |
| 2 | 59 | 5.88秒 |

- 世代2の回収は、1回あたり約0.1秒です。生きているオブジェクト全体（WorldState、履歴キャッシュ #44、保存した文書など）をたどるため、履歴が長くなるほど重くなります。
- 計測は `gc.callbacks` で回収の開始から終了までの時間を足したものです。

## 案

いずれもプロセス全体の実行時の設定を変えるもので、Webサーバーのスレッドにも効きます。メモリ使用量との兼ね合いがあるため、**チームで決めてから**進めてください。

- `gc.set_threshold()` で世代2の回収の頻度を下げる
- 計算を進める間だけ `gc.freeze()` で、長く生きる確定済みの履歴を回収の対象から外す（外したものは循環参照でも回収されなくなるため、凍結する範囲に注意が要ります）
- 計算を進める間は自動の回収を止め、保存ごとに明示的に回収する

## 確かめること

- 1日分の計算の時間と、世代2の回収の回数・時間
- ピークRSS
- 計算中のWeb応答の時間
- 結果（WorldState・イベント・KPIのハッシュ）が変わらないこと

関連: #44、#48

## 設定を変えた場合の計測（develop `4bd949e`、コードは変えず、ベンチマークの起動時だけ設定）

100人・生成Scenario・1440分・ProjectAPI経路、WSL上で1回ずつ。world・events・metrics のハッシュはすべて同じでした。

| 設定 | 全体 | 回収の時間（世代0 / 1 / 2） | 世代2の回数 | ピークRSS |
|---|---:|---|---:|---:|
| 既定（`700, 10, 10`） | 114.1秒 | 1.44 / 0.79 / 8.23秒 | 68 | 897 MiB |
| `gc.set_threshold(700, 10, 100)` | 112.4秒 | 1.51 / 0.72 / 5.59秒 | 36 | （未計測） |
| `gc.set_threshold(50000, 20, 10)` | 107.3秒（RSS計測時は106.1秒） | 0.58 / 0.37 / 0秒 | 0 | 991 MiB |

- 世代0の閾値を上げる案が最も効き、1日分で約7秒（約6%）短くなりました。その代わり、ピークRSSが約94 MiB増えました。
- 回収が1日でほぼ走らないため、循環参照のごみは、閾値に達するまで溜まります。長く動くWebサーバーのプロセスで、どこまで許すかの判断が要ります。
- 設定を入れる場所（計算workerの起動時か、サーバーの起動時か）と、値の決め方も合わせて決める必要があります。

## 対応（PR #242、develop `1aecb2b`）

案のうち「`gc.set_threshold()` で回収の頻度を下げる」を、範囲を限って採用しました。

- `sheltersim.core.collection.fewer_collections()` の間だけ、閾値を `50000, 20, 10` にします。入れ子にでき、いちばん外側の区間を抜けると元の閾値に戻します。
- 使う場所は、計算を進める間（`TimelineStore._advance_locked`）と Checkpoint の読み込み中（`ProjectStore.load_restored_checkpoint`）です。
- 閾値はプロセス全体の設定なので、区間の間は Webサーバーのほかのスレッドにも効きます。この点とメモリの増加は、マージの判断として受け入れました。
- `gc.freeze()` と自動回収の停止は採用していません。
- 設計の説明は `docs/architecture.md` に追記しました。

## マージ前の計測（develop `a4d0ce3` との比較）

100人・生成Scenario・1440分・ProjectAPI経路、WSL上で2回ずつ。world・events のハッシュは同じでした。

| | 全体 | CPU時間 | ピークRSS |
|---|---:|---:|---:|
| develop `a4d0ce3` | 86.9 / 87.5秒 | 77.8 / 77.2秒 | 782 / 778 MiB |
| #242 を入れた状態 | 81.2 / 79.5秒 | 70.8 / 70.8秒 | 826 / 828 MiB |

CPU時間は約9%短くなり、ピークRSSは約47 MiB増えました。
