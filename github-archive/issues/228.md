## 元の本文

## 現状

100人・生成Scenario・1440分・ProjectAPI経路（develop `62e8b61`、WSL上で1回、cProfile）で、計算全体262秒（cProfile下）のうち、モデルの状態検証 `validate_simulator_extensions`（`domain/simulator_state.py`）が65秒を占めていました。毎tickの `world.validate()` と、保存ごとの完全検証から呼ばれます。割合はcProfile下の値で、実際の時間はおよそ半分です。

このうち、**検証する内容を変えずに**実装だけで速くできそうな箇所がありました。いずれもモデルのコード（`domain/`、`policies/`）なので、変更していません。

### 1. 体調モデルの設定の照合（`domain/body_state.py` の `validate_body_state`、30秒のうち約15秒）

- 保存された設定（`state["config"]`）が、現在の設定から「省略可能な項目」をいくつか除いたものと一致するかを確かめるために、省略可能な13項目のあらゆる組み合わせについて、設定の辞書を作って並べています（`legacy_configs`、最大 2^13 = 8192 個）。
- これを毎回の検証で作るため、1日で約1,265万回の辞書の内包表記が走っていました。
- 同じ判定は、次の3つを確かめれば足りるはずです。
  - 保存された設定のキーが、現在の設定のキーの部分集合であること
  - 足りないキーが、すべて省略可能な項目であること
  - 残りのキーの値が一致すること
  
  組み合わせを作らずに済みます。

### 2. 関係の検証（`domain/social_network.py` の `validate_social_network_state`、約27秒）

- 関係（最大9,900組）ごとに、キーを `json.loads` で解析し、`json.dumps` で書き戻して元のキーと比べています。1日で約317万回ずつです。
- 同じ判定（2つの異なる文字列のJSON配列であること）を、解析し直さずに確かめる書き方がありそうです。

### 3. 参考: 行動の入力のスナップショット（`policies/behavior.py` の `WorldView.from_world`、約16秒）

- 1tickに3回作られ、そのたびに全員分の状態を写しています。ここは検証ではなく計算の入力なので、変える場合の影響はモデル担当者の判断が必要です。

## 前提

- 検証の範囲と頻度（毎tickか、保存時だけか）は #220 で扱います。この Issue は、範囲と頻度を変えずに、同じ判定をより速く書く話です。
- モデルのコードに触れるため、係数を変えない場合でも**モデル担当者と調整**してください。
- 数式・係数・丸め・tick順序・乱数は変えません。検証が受け入れる状態と拒否する状態も変えません。
- WorldState・イベント・KPIのハッシュが修正前と一致すること、壊れた状態を拒否するテスト（既存のものと、変更する判定ごとの境界のテスト）が成功することで検証します。

関連: #45、#220

- `WorldView.from_world` で、避難者の生活の状況（`PersonContext`）の解析結果を、元の辞書と等しい間だけ再利用する実装を試しました。1回 1.32ミリ秒 → 1.10ミリ秒で、1日約1秒（1%弱）です。モジュール全体にキャッシュを持たせる割に効果が小さいので、PRにはしていません。
