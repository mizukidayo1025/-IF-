## 決めたこと（後から変えられます）

`docs/rust-port/step4-plan.md` に書きました。主なもの：
- trace の文書は形を変えずに移す（ファイルを書く `RunArtifactWriter` は storage の外枠として Python に残す）。
- 旧 Run の保存の間の分は、保存した時点に丸めて丸めたことを表示する。新しいモデルで計算し直さない。
- tick の外の `validate_*` は Python に残す。
- 乱数はキーの整理だけで、SHA-256 は残す。
- Rust で 1 バイト同じエラー文にするのは、保存されるデータ、`match=` で固定したテスト、有効な入力で届くエラーに限る。
- 3 OS のゲートは既存の CI ジョブの中に足し、トリガーは変えない。

## モデル担当の方に確認していただくこと

係数と式の意味は変えていません。各 PR と `docs/rust-port/lanes/*.md` の「モデル担当の確認事項」に、Rust に移った規則、Rust だけの条件（当たると Python が判断するもの）を挙げています。判断が必要なものは次のとおりです。

- Scenario やモデルの設定の整数の係数（`level: 1` など）：検証は通るが kernel は拒否する（D6、L11 で扱う予定）
- ASCII 以外の設備の種類（D11）
- 既存の不具合：`transfer_equipment` の `validate_geometry_change` は、設備に footprint があって障害物が 1 つでもあると `AttributeError` になる（`SpatialObstacle` に `facility_id` がない）。移植では動作を変えていません。

## 高速化の見込み

7 日間（フロントエンドからの経路）の計算は、Python 版の 1,590.0 秒から、このタグで **84.4 秒（約 19 倍）** になりました。詳しい内訳は #272 に追記しました。

内訳を見ると、残りの大半は tick ではありません。

| 処理（7 日分、実時間） | 秒 |
|---|---:|
| 保存（`TimelineStore.record`） | 64.5 |
| ├ ファイルの書き込み（`save_captured_branch`、fsync 8.7 秒を含む） | 20.5 |
| ├ Checkpoint の作成（`Checkpoint.capture`） | 19.7 |
| ├ frame のキャッシュ（`_cache_frame`） | 13.7 |
| └ frame の作成（`world_frame`） | 9.5 |
| tick（`TickEngine.step`） | 18.0 |
| 履歴索引の登録（別プロセス、計算と並行） | 83.6 |

見込みは次のとおりです。どれも推定で、まだ測っていません。

1. **保存の経路（最大の塊）：** 間隔を広げる、fsync を減らす、保存を別スレッドに出す、の 3 つは使いません。1 回の保存を軽くします。名前空間はすでに Rust の行で持っているので、正準バイト列と frame を Rust で直接作れば、Checkpoint の作成と frame（合わせて約 43 秒）の多くを削れる見込みです。
2. **履歴索引：** 別プロセスで計算と並行していますが、83.6 秒かかり、計算の後も約 45 秒動き続けます（プロセス全体は 129 秒）。計算の結果を待つ時間には入りませんが、索引を引く画面はそれまで最新になりません。索引の行を Rust で作ると縮む見込みです。
3. **Python の木と実体オブジェクトの廃止（L10、L14）：** tick に残る Python（約 210 µs/tick）と mirror の呼び出し（約 32 回/tick）がなくなり、保存側も木をたどらなくなります。
4. **並列化（L12）：** tick 全体が 18 秒なので、7 日間の計算時間への効果は最大でもその分です。大きな Scenario で効きます。

1〜3 で、7 日間の計算は 40〜60 秒程度まで縮む見込みです。着手する前に、空いた状態で内訳を測り直します。
