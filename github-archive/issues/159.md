## 起きること

高い苦痛のモニター（`domain/distress_monitor.py` の `record_distress_monitor_tick`）は、苦痛がしきい値を下回った回復を数えないことがあります。下回ったのが心理の tick の外（イベントの処理）の場合です。そのとき、高い状態の連続は閉じられず、ずっと「続いている」扱いになります。

## 再現

生成Scenario（共通fixture `GENERATED_SCENARIO_REQUEST`）を次の条件で実行します。

- `duration_minutes=60`、`social_propagation.enabled=False`
- 全員の stress を 0.8 にする
- `OfflineSimulationController` で実行する

A016 は次のように動きます。

- 38分の `DISPATCH_DUE_EVENTS` で、`staff_support_complete`（staff_001 の支援）によって stress が 0.7155 から 0.6955 に下がる。
- その後のモニターの値は、`current_run=38`、`recovered_run_count=0` のまま変わらない。
- 最後の stress は 0.649。

その結果、`completed_recovery_count` が 19/20 になります。

## 原因

モニターは、心理の tick の更新の前後の値で判定します（`runner.py` の `UPDATE_AGENT_STATE`）。

```python
was_high = previous >= threshold
is_high = current >= threshold
...
elif was_high and run > 0.0:   # 回復として閉じる
```

イベントの処理で先にしきい値を下回ると、次の tick では `previous` も `current` も低くなります。そのため、どちらの分岐にも入らず、`run` が残ります。後でまたしきい値を超えると、`run = 1`、`episodes += 1` になり、前の連続は回復として記録されないまま上書きされます。

fixture の2人の Scenario（`integration/test_research_psychology.py`）には職員の支援がないので、この経路を通りません。

## 期待すること

`run > 0` で今がしきい値未満なら、下回った経路によらず、連続を回復として閉じること。

係数は変えません。数え方だけの話です。

## テスト

#137 で、生成Scenarioで回復を確かめるテストを、このIssue番号付きの `xfail(strict=True)` で置く予定です。
