## 元の本文

## 現状

状態の整合性検証は、次の2か所で履歴全体を対象に走っています。どちらも後の時刻ほど時間がかかります。

### 1. 毎tickの検証（#45 の候補1から移しました）

- `TickEngine.step()`（`src/sheltersim/core/engine.py`）は、各tickの最後に `world.validate(validate_event_history=False)` を呼んでいます。
- tick時間に占める割合は、序盤16%から終盤25%に増えていました（100人・生成Scenario・360分、序盤と終盤を30tickずつcProfileで測定。#43 の前の値）。
- その中の `validate_simulator_extensions` は、終盤ほど重くなります（30tickあたり0.43秒 → 0.82秒）。
- `validate_body_state`（`domain/body_state.py` の内包表記）は、毎tick約8,200要素を走査しています。

### 2. Checkpoint保存ごとの検証2回

#44（PR #219）で、保存のたびに履歴全体を変換し直す処理はなくなりました。ただし、保存1回ごとに次の2回の完全検証は今も残っています。

- 保存する WorldState の `validate()`
- 保存内容から復元した WorldState の検証（`Checkpoint._validate`）

100人・生成Scenario・1440分・ProjectAPI経路（develop `92695f8`、WSL上で1回）では、1440分時点で1回あたり約0.09秒、保存1回で約0.18秒でした。

## 決めること

どちらも「確定済みの部分を検証し直すかどうか」という同じ判断です。次のような案があります。

- 前回の検証以降に増えた分だけを検証する。各ドメインの検証（10か所程度）に「この時刻以降だけを検証する」という範囲の指定を加える必要があります。
- 毎tickの検証を、保存時だけにする、または変わった部分だけにする。

## 注意点

- 「状態変更は必ず検証する」という安全設計に関わる判断です。**チームで合意してから**進めてください。
- 検証は数理モデルの状態を読むため、係数を変えない場合でもモデル担当者と調整してください。
- 数式・係数・丸め・tick順序・乱数・保存形式・Checkpoint v1 のハッシュ・保存間隔は変えません。
- 範囲を狭める前に、壊れた状態を確実に検出できることを示す不変条件テストを揃えてください。

## 完了の条件

- 検証の範囲と頻度を変えるかどうかが、チームで決まっていること
- 変える場合は、WorldState・イベント・KPIのハッシュとCheckpointのmanifest・chunkが修正前と一致し、offline全体テストが成功すること

## 現在の値（実時間、100人・生成Scenario・1440分・ProjectAPI経路、develop `4bd949e`、WSL上で1回）

1日分の計算は112.5秒で、検証にかかる時間は次のとおりでした。

- tick計算（65.3秒）のうち、フェーズの計算（行動・ニーズ・社会・情報など）の合計が約38秒、残りの約27秒の大半が毎tickの `world.validate()` です。
- Checkpoint の作成（16.1秒）のうち、保存前と復元後の完全検証が計5.2秒です。

毎tickの検証の大部分は、モデルの状態検証 `validate_simulator_extensions` です。そのうち、検証する内容を変えずに実装だけで速くできそうな箇所を #228 に挙げました（体調モデルの設定の照合、関係のキーの解析）。範囲と頻度を変える前に、#228 だけでもかなり減る可能性があります。

## 毎tickの検証を止めた場合の上限（計測のみ、コードは変えていません）

100人・生成Scenario・1440分・ProjectAPI経路（develop `b580e3c`、WSL上で1回）で、`TickEngine.step` の毎tickの `world.validate(validate_event_history=False)` だけを、計測用のスクリプトで飛ばしました。保存前・復元後の完全検証と、計算の開始・終了時の検証はそのままです。

| | 通常 | 毎tickの検証なし |
|---|---:|---:|
| 全体 | 約113秒 | 85.1秒 |
| tick計算 | 約65秒 | 35.0秒 |
| 最後の30分区間 | 約3.4秒 | 2.58秒 |

world・events・metrics のハッシュは同じでした。この入力では、毎tickの検証で拒否される状態は生じていません。

- 毎tickの検証は約30秒（tick計算の約46%）です。
- このうち約23秒は、検証の内容を変えずに実装だけで減らせます（PR #235・#236、モデル担当者の確認待ち）。
- 両方を入れたあとに残る毎tickの検証は、約15秒です（`WorldState.validate` の合計）。その先を減らすには、この Issue で範囲と頻度を決める必要があります。
