## 経緯

この Issue は当初、tick計算に残る無駄として3つの候補を挙げていました。

- 候補1（毎tickの整合性検証）: 保存時の検証と同じ判断になるため、#220 へ移しました。
- 候補2（施設形状・空間制約の直接解析）: PR #218 で済みました。1440分の単体実行で、tick計算は69.70秒から63.99秒になりました。
- 候補3（時間とともに伸びる処理）: この Issue に残します。

## 現状

100人・生成Scenario・360分の単体実行で、序盤（0〜30分）と終盤（330〜360分）を30tickずつcProfileで測ったところ、次の処理が時間とともに伸びていました（#43 の前の測定で、cProfile下の値です）。

- `resource_service.arbitrate`: 30tickあたり0.13秒 → 0.62秒
- tick内の `json.dumps` の呼び出し回数: 30tickあたり約3.9万回 → 約9.1万回
- `domain/population.py` と `domain/population_lifecycle.py`: 履歴に1件足すたびにリスト全体をコピーしています（`[*raw["history"], ...][-20_000:]`）。

いずれも、伸びる履歴を毎回走査している可能性があります。数値が古いため、着手するときに今の develop で計測し直し、プロファイルで裏付けてから直してください。

## 前提

- 数理モデルのコードに触れるため、係数を変えない場合でも**モデル担当者と調整**してください。
- 数式・係数・丸め・tick順序・乱数は変えません。
- WorldState・イベント・KPIのハッシュが修正前と一致すること、offline全体テストが成功することで検証します。

## 追加の候補: 世界の候補を作るときの余分なコピー（#228 から移しました）

`domain/population_lifecycle.py:296`（develop `a4d0ce3`）は、変更をまとめて適用するために、世界の候補を `MutableWorldState.from_dict(deepcopy(world.to_dict()))` で作っています。

- `to_dict()` は、正準JSONから読み直した新しい辞書を返します。そのため、`deepcopy` は同じものをもう一度コピーしているだけです。
- 1440分の世界では、`to_dict()` 1.27秒に対して、このコピーに1.06秒かかります（WSL上で1回）。
- 同じ書き方は、events と contracts の8か所では PR #252 で外しました。結果のハッシュは変わりませんでした。この1か所はモデルのコードなので、残しています。

`from_dict(world.to_dict())` にする1行の変更です。モデル担当者の確認が取れれば、PR #252 と同じ形で直せます。
