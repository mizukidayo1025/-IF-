## 元の本文

関連：#126（#135 の作業中に発生）

## 背景

offline の全件を実行して「1 failed」と分かっても、どのテストがなぜ失敗したかを後から確かめられないことがあります。#135 の作業中に1回起き、以前にも同じことがありました。そのあと8回続けて全件が通っており、失敗したテストは特定できていません。

調べると、原因は次の3つでした。

- **結果がどこにも残らない。** `pyproject.toml` の `addopts` に `-ra` があるので、pytest は失敗したテストの名前を出力の最後に表示しています。しかし全件の出力は長く、実行した側（人もコーディングエージェントも）が最後の数行や集計行しか見ないと、名前もtracebackも失われます。#135 では、エージェントが `| tail -1` で集計行だけを見ていました。
- **後から取り出す手段がない。** `.pytest_cache` の失敗記録（`--lf`）は、次に全件が通ると消えます。ログやjunit XMLのようなファイルも残していません。CI（`.github/workflows/ci.yml`、`long-regression.yml`）も、結果のファイルを残していません。
- **時計で待つテストがある。** 並列実行（`-n auto`）の負荷で時間切れになりうる、実時間の期限つきの待ちが次のところにあります。今回の失敗がこのどれかかは確かめていません。
  - `tests/conftest.py` の `wait_for_job`（5秒）
  - `tests/integration/test_demo_live_recompute.py`（10秒）
  - `tests/integration/test_scenario_editor.py`（5秒）
  - `tests/integration/test_demo_jobs.py` の `Event.wait(timeout=3)`（6か所）
  - `tests/integration/test_llm_outcomes.py` の `time.sleep`
  - `tests/e2e/test_project_scenario_to_results.py`（300秒）

## やること

1. **実行するたびに結果をファイルに残す。** 例えば `--junitxml` か `--report-log` で、失敗したテストの名前・tracebackとテストごとの時間を、gitに登録しない場所（例：`.test-results/`）に書きます。`addopts` に入れるか、実行用のスクリプトにするかはこのIssueで決めます。
2. **失敗の一覧を必ず目に入るようにする。** 実行の最後に、失敗したテストの名前と結果ファイルの場所を出す形にし、`docs/testing.md` の「通常のoffline確認」に結果の見方を書きます。コーディングエージェント向けに、集計行だけで判断しないことも書きます。
3. **不安定なテストを特定する。** 1を入れたあと全件を繰り返し実行して、失敗したテストを記録します。見つかったテストは、テストごとに別のIssueにします。
4. **時計で待つテストを見直す。** 上の各テストについて、期限を延ばすのではなく、完了を待てる形（イベントやjobの状態）にできるかを調べ、必要ならIssueにします。

CIで結果ファイルを保存する（artifactにする）ことは、AGENTS.md に従い、workflowを変える前にチームで合意してから行います。

## 範囲外

- 失敗を隠す仕組み（自動で再実行して通れば成功とする `pytest-rerunfailures` など）は入れません。
- 不安定だと分かったテストの修正そのものは、それぞれのIssueで行います。

## 完了の条件

- offline の全件を実行したあと、もう一度実行しなくても、失敗したテストの名前とtracebackを確かめられる。
- 結果の残し方と見方が `docs/testing.md` に書かれている。
- 全件を繰り返し実行して不安定なテストを探した結果（見つかったテストのIssue、または見つからなかった回数）が、このIssueに記録されている。
