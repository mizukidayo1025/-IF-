## 元の本文

## 起きること

EffectProgram の `population_presence` で、一時外出（`temporary_exit`）や移送（`transfer`）を指示したとします。計画の検査（`validate_effect_program`）は通り、介入として承認できます。しかし、その時刻に対象の人が作業中か支援を要請中だと、実行時にイベントが `failed` になり、外出しません。

失敗の理由の文は次のとおりです。

```
population exit is deferred while the person has an active task or support request
```

文は「延期（deferred）」と言っていますが、再試行する仕組みはありません。その人は最後まで避難所にいます。

## 再現

生成Scenario（共通fixtureの入力欄、`duration_days=1/12`）の本線を10分まで進め、10分で分岐します。

- A014（`seeking_help`）を一時外出させる → 10分のイベントが `failed`。120分の時点でも避難所にいる。
- A016（`seeking_help`）を移送する → 同じく `failed`。

10分の時点では、20人中19人が作業中（並んでいる、サービスを受けている）か、支援を要請中です。そのため、この時刻の外出・移送の介入は、ほとんどが失敗します。眠っている A019 の一時外出だけが成功します。

## 原因

`domain/population_lifecycle.py` の `_assert_can_leave` は、実行時に「作業中でない、支援の要請がない、作業を持っていない」を求めます。一方、計画の検査（`events/effects.py` の `validate_effect_program`）は、この条件を見ていません。

失敗したイベントは、記録されて終わります（`events/handlers.py` の population の処理）。延期や再試行はしません。

## 関連して：外出と帰還を1つの介入に書けない

1つの EffectProgram に「10分に一時外出、40分に帰還」と書くと、計画の段階で拒否されます（`return target must be a retained absent person`）。計画の検査は、分岐した時点の状態だけを見ていて、同じ介入の中で先に外出することを考えないためです。

`expected_return_minute`（帰る予定の時刻）を指定しても、自動では帰還しません（予定を記録するだけ）。そのため、「一時外出して40分に戻る」には、外出の介入と、40分に分岐した帰還の介入の2つが要ります。

## 期待すること

次のどれかにすること。

- 対象の人が作業を終えるまで外出・移送を延期し、その後に実行する（文が言っているとおりにする）。
- 計画の段階で、その時刻に外出できない人を、理由を示して拒否する。
- 少なくとも、失敗の理由の文を実際の動作に合わせ、介入の結果として利用者に見えるようにする。

外出と帰還を1つの介入に書けるようにするかは、あわせて決めます。係数は変えません。

## テスト

生成Scenarioで、支援を要請中の人に一時外出を指示するテストを、このIssue番号付きの `xfail(strict=True)` で置きます。どの直し方でも成り立つように、「承認した外出が、実行されるか、計画の段階で拒否されるか」のどちらかを確かめます。直したら印を外します。
