## 元の本文

## 背景

#51（介入で追加したトイレが結果に効かない不具合）では、部品ごとのテストはすべて通っていたのに、組み合わせた結果が壊れていました。テスト一式を調べたところ、整っている部分と、構造的に穴がある部分がありました。2026-10-26時点、`main` は `1e62d05`。

### 整っているところ

- `tests/conftest.py` が保存先、LLMのキャッシュ、利用記録をテストごとに分離していて、並列実行（`-n auto`）でも干渉しない。
- 有料API（`live_api`）と長時間シミュレーション（`long_simulation`）に印があり、通常の実行から外せる。
- テスト関数729件（103ファイル）が約2分で終わり、結果が決定的。
- `fixtures/regression-contract.json` が代表的なScenarioの結果をハッシュで固定している。

### 問題点

1. **テスト用Scenarioが、利用者の使う経路を通っていない（最優先）**
   - `fixtures/` のScenario 12本は、どれも `facility_geometry` も `agent_dynamics` も持っていない。UIで作るScenarioは必ず両方を持っている。
   - テストファイル103本のうち74本がfixtureを使い、生成器（`InitialScenarioBuilder`）を使うのは20本だけ。
   - #51の不具合（施設の認知の制約と、図面上の座標なし）は図面と認知がある経路でしか起きないため、大量のテストをすり抜けた。
2. **分類の軸が混ざっている**
   - 103ファイルがすべて `tests/` 直下にあり、名前がモジュール名（`checkpoint`）、機能名（`facility_awareness`）、不具合名（`resource_loss_without_operational_state`）、開発の回の名前（`round2_common_services`）で混在している。
   - 「この機能のテストはどこか」が名前から分からない。
   - `docs/testing.md` の「各packageに隣接するtest fileを参照」は実態と合っていない。
3. **準備コードの重複**：26ファイルがScenarioや保存先を作る補助関数を個別に持っている。共通fixtureは環境の分離だけ。
4. **層の区別がない**：単体、組み合わせ、利用者が見る結果、契約（再現性・API・台帳）、UIの区別がない。
5. **利用者が見る結果を確かめるテストが少ない**
   - 介入の効果は「直後に状態がどう変わるか」で確かめるものが中心（例：`docs/event-coverage-report.md` の「`toilet_working_units` +1、ストレス不変」）。
   - 「生成Scenarioで介入したら、待ち時間などの結果が本線と変わる」を確かめるテストは、トイレ追加（#51、#52）のほかにない。
6. **出典台帳とコードの対応が確かめられていない**
   - `src/` が参照する根拠ID（`ASM-...`）108件のうち61件が `fixtures/source-manifest.json` にない。
   - 一部は `fixtures/regression-contract.json` など別のファイルにあるが、行列ポリシー（`ASM-NEED-WEIGHTED-PHYSICAL-QUEUE-V1`）や実行時の図面変更（`ASM-BOUNDED-RUNTIME-GEOMETRY-V1`）の根拠はどこにも見当たらない。

## 進め方の案

一度に全ファイルを移動するのは避けます。差分が巨大になり、履歴が追いにくくなり、ほかの作業とも衝突するためです。

1. **地図を作る（コード変更なし）**
   - 103ファイルを「担当モジュール（AGENTS.mdの区分）× 層 × 使うScenario（fixtureか生成か）」で分類した表を `docs/testing.md` に置き、穴を見えるようにする。
2. **利用者の経路を通る共通fixtureを作る**
   - UIと同じ生成Scenario（小規模）を `conftest.py` の共通fixtureにする。
   - 結果のハッシュを `regression-contract.json` に加える。
   - 新しいテストはこれを使う。
3. **新しい配置を決める**
   - 例：`tests/unit/`、`tests/scenario/`、`tests/contract/`、`tests/ui/`。
   - 新しいテストは新しい配置に置き、既存ファイルは修正するついでに移す。
4. **穴を埋めるテストを足す**
   - 介入の種類（スタッフ追加、故障、断水、物資搬入など）ごとに、生成Scenarioで結果が本線と変わることを確かめる。
   - 出典台帳の整合テスト：コードが参照する根拠IDがすべて台帳にあるかを確かめる。現在の不足分は既知の例外として記録し、少しずつ減らす。台帳に足す根拠の中身は、モデル担当と相談して決める。
