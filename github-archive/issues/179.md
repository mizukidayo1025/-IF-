## 起きること

EffectProgram の `population_presence`（`action: reunite`）で再会させた人の中に、支援を要請中の人がいるとします。その人の支援が職員によって進むと、シミュレーションが例外で止まります。

```
ValueError: support request identity changed during its lifecycle
  domain/common_operations.py record_shared_operation
  ← domain/care_receipts.py append_applied_care_transition
  ← experiments/runner.py _run_phase
```

## 再現

1. 生成Scenario（共通fixtureの入力欄、`duration_days=1/12`）の本線を10分まで進める。
2. 10分で分岐し、次の効果を入れる。

   ```
   op: population_presence
   target_selector: {kind: person, candidate_ids: [A001, A006]}
   parameters: {action: reunite, household_id: H000001}
   ```

3. 分岐を120分まで進めると、途中で止まる。

10分の時点で、A001（世帯 H000001）と A006（世帯 H000003）は、どちらも `sleeping` 区画にいて、支援を要請中（`seeking_help`）です。A006 の支援の要請は、世帯 H000003 で記録されています。

支援を要請していない2人（A002 と A011）を同じように再会させると、問題なく進みます。

## 原因

`shared_operations_v1` は、支援の要請の同一性を「人・世帯・支援の種類」で確かめます（`record_shared_operation`）。再会は、`population_presence_v1` 上でその人の世帯を変えます（`apply_population_presence_command` の reunite）。そのため、要請の途中で世帯が変わり、次の段階（割り当てや完了）を記録するときに、同一性の検査に引っかかります。

再会を計画するときの検査（`validate_effect_program`）は、支援を要請中かどうかを見ていません。

## 期待すること

次のどちらかにすること。

- 開いている支援の要請は、要請したときの世帯のまま完了させる（世帯の変更は、新しい要請から反映する）。
- 支援を要請中の人がいる再会は、計画の段階で理由を示して拒否する。

どちらの場合も、シミュレーションが例外で止まらないこと。係数は変えません。

## テスト

生成Scenarioで再会させるテストを、このIssue番号付きの `xfail(strict=True)` で置きます。直したら印を外します。
