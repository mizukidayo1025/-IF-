## 元の本文

## 現状

PR #268（develop `5b95fa2`）で、履歴索引（`runs/{run}/history.sqlite`）を WAL 方式で書くようにしました。`synchronous` は FULL のまま、commit のあとに `PRAGMA wal_checkpoint(TRUNCATE)` を行います。

その計測で、1日分の計算（100人・生成Scenario・1440分・ProjectAPI 経路・同じプロセスのスレッド、`benchmarks/investigate_performance.py`）の索引への登録（`HistoryIndex.ingest`、48回）の実時間が、ときどき10〜15秒長くなりました。WSL2 上の計測です。

| | 索引への登録（実時間） | 索引への登録（CPU時間） |
|---|---|---|
| WAL の試作（checkpoint なし） | 19.8 / 30.6秒 | 16.8 / 16.8秒 |
| WAL + `synchronous=NORMAL` の試作 | 18.1 / 27.9秒 | 16.8 / 17.1秒 |
| PR #268 の最終形 | 33.2 / 18.3秒 | 16.3 / 16.8秒 |
| 同じ日の develop（WAL の前、6回） | 15.9〜17.9秒 | 14.6〜15.1秒 |

- WAL の版の6回のうち3回で、実時間が10〜15秒長くなりました。CPU 時間は変わらないので、ディスクの待ちと考えられます。
- 同じ日の develop の6回では出ていません。ただ、別の日の計測では、develop 相当の版でも1回、登録が35秒になったことがあります（#244 の測り直し）。
- world・events・metrics のハッシュは、すべて同じでした。

## 分かっていないこと

- WSL のディスク（vhdx 上の ext4）の揺れなのか、WAL 方式の書き込み（ログと本体の2回の書き込み、書き戻しのときの同期）によるものなのか。
- 遅れが、どの保存（何分目、索引の大きさ）で起きているか。
- 別プロセスで計算する Web サーバーの経路（`worker="process"`）でも起きるか。1200分から1440分への計算（4回）では、計算時間は develop と同じでした。

## 確かめ方の案

- WAL と develop をそれぞれ10回程度、交互に測り、遅れの起きる割合を比べる。
- 保存ごとに、索引への登録の時間と、`commit`・`wal_checkpoint` それぞれの時間を記録し、どこで待っているかを分ける。
- 可能なら、WSL 以外（Linux の実機、macOS、Windows）でも測る。
- WAL が原因なら、書き戻しの頻度（`wal_autocheckpoint`）や、commit のあとの `TRUNCATE` を `PASSIVE` にするなどを比べる。

## 完了の条件

- 原因（WSL の揺れか、WAL の書き込みか）が分かっていること
- WAL が原因なら、対策を入れ、1日分の計算で索引への登録の実時間が WAL の前と同程度であることを、複数回の計測で示すこと

関連: #48、PR #268、#256

## 切り分けの結果（WSL2、1日分の計算・ProjectAPI 経路・同じプロセス）

索引への登録（`HistoryIndex.ingest`、49回）ごとに、全体・commit・書き戻し（`wal_checkpoint`）の時間を記録しました。計測用の差し込みで、リポジトリのコードは変えていません。どの回も、world のハッシュ（`d1ca12438bb4`）は同じでした。

| 版 | 回数 | commit の合計（遅くない回） | 遅い回（commit の合計） | 登録の CPU 時間 |
|---|---|---|---|---|
| WAL の前（`a0e3ff6`） | 15 | 2.3〜3.4秒 | 0 | 約15.0秒 |
| WAL・`TRUNCATE`（今の develop `5b95fa2`） | 10 | 約5.4秒 | 4回（8.7〜15.7秒） | 約16.8秒 |
| WAL・`RESTART` | 6 | 約5.6秒 | 3回（12.1〜13.9秒） | 約16.8秒 |
| WAL・`synchronous=NORMAL` | 6 | 約5.5秒 | 2回（11.9〜17.6秒） | 約16.8秒 |
| WAL・`RESTART`・`journal_size_limit` 64 MiB | 6 | 約5.5秒 | 3回（8.7〜17.0秒） | 約16.9秒 |

- 遅れは commit で起きています。書き戻しは1日で0.3秒以下です。
- 1回の保存で1秒を超える待ちはありません。遅い回では、その回の保存すべての commit が少しずつ遅くなっています。
- 同期（`NORMAL` でも遅い）、ログの切り詰め（`RESTART`・上限 64 MiB でも遅い）、書き戻しの方式では解消しません。
- 見立て：WAL は同じページをログと本体に2回書くので、1日分の書き込み量がおよそ倍になります。ログのページごとの検査値の計算もあり、遅くない回でも commit は約2倍です。遅い回は、WSL の仮想マシンで書き出し待ちのデータの上限（dirty page）に当たり、書き込みが抑えられていると考えています（WSL の設定を変えての確認はしていません）。
- WSL 以外の環境では測っていません。

PR #270（develop `2b752e3`）で WAL 方式をやめ、従来のジャーナル方式に戻したので閉じます。原因は WAL の書き込み量でした。WAL は同じページをログと本体に2回書くので、commit がいつも約2倍かかり、WSL では時々10〜15秒長くなります。書き戻しの方式や同期の設定では解消しませんでした（上のコメント）。WAL のときに書いた索引は、次の書き込みで従来の方式に戻ります。分岐中の frame の読み取りの待ち（最大5〜6秒）は、受け入れることにしました。develop は既定のブランチではないため、PR の「Closes #269」では自動で閉じませんでした。
