## 対象

| 操作 | 内容 |
|---|---|
| `set_route_access` | 経路を一時的に閉じる |
| `move_facility` | 待機中の施設を同じ区画の中で動かす |
| `transfer_equipment` | 待機中の設備を、つながった別の区画へ移す |
| `set_partition` | 仕切り（障害物）を置く |
| `temporary_room_geometry` | ベッド付きの仮設の部屋を作る |

## やり方

`tests/integration/test_intervention_outcomes.py` に、ほかの介入と同じ手順で足します（#60 の最初のPRで作った仕組み）。

1. 共通fixture（`generated_scenario`、条件を変えるなら `generated_scenario_with`）の本線を分岐させ、子Branchに介入を1つ適用する。
2. 両方を `TickEngine` で同じ時刻まで進め、Project画面のKPIを比べる。
3. 変化が、記録されたイベント（介入の適用、施設や職員の動作）を通して起きていることも確かめる。KPIだけを見て判断しない。

まず、生成Scenarioにその介入を適用できるかを確かめます。#65 のように、生成Scenarioに必要な状態がなくて却下される場合は、別のIssueにします。

## 完了の条件

- 対象の介入それぞれに、生成Scenarioで結果が本線と期待した向きに変わることを確かめるテストがある。
- テストはofflineで決定的に通る。

## 範囲外

- 期待どおりに効かない介入、適用できない介入の修正。不具合として別のIssueにします。
- モデル係数の変更。
