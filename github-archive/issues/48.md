## 元の本文

## 現状

- シミュレーションのworkerは、Webサーバーと同じPythonプロセスのスレッドで動いています（`src/sheltersim/web/projects.py` の `ThreadPoolExecutor(max_workers=1)`）。
- WebサーバーはHTTPリクエストを1件ずつ処理します（`src/sheltersim/web/server.py` の `HTTPServer`）。
- PythonのGILのため、計算中にHTTP側で重い処理（frameの組み立てなど）が走ると、計算とCPUを奪い合います。
- 比較用に「両分岐を先へ計算」する処理は、branchを1本ずつ順番に計算します。

#37 と #42 で、主なHTTP読み取りは軽くなりました。ただし、保存境界以外の時刻の表示や比較など、重い読み取りは残っています（別のIssueに記録）。

## 提案

- 計算workerを別プロセスにします。
- 保存側はもともと複数プロセスを前提に作られています（`claim_run` のファイルロックによる書き込み権の管理、`transaction` のflock）。
- 効果の見込み:
  - 計算中もWeb応答がGILの影響を受けなくなる。
  - 複数のbranchやseedを同時に計算できる。互いに独立なので、並列化の効果がそのまま出る。
- 必要な作業:
  - 中止の仕組み（今は `threading.Event`）のプロセス間での実装
  - 計測値（telemetry）の受け渡し
  - 異常終了時の回復
  - Windowsでの動作確認
- tick内の並列化（避難者ごとに複数コアへ分ける）は勧めません。1tick（約40〜60ミリ秒）ごとに状態をやり取りする手間が大きく、決定的な順序と乱数の再現性を保つのも難しいためです。

## 前提

- 既存の構成を変えるため、**チームで合意してから**着手してください。
- 計算結果のハッシュ（WorldState・イベント・KPI）が修正前と一致すること、中止・再開・分岐・再生の回帰テストを含むofflineテストが成功することで検証します。

## 段階3の設計案：同じ Run の複数の branch を同時に計算する

段階1（PR #260）と分岐の移動（PR #263）で、計算と分岐は別プロセスで動くようになりました。ただ、同時に計算できるのは、サーバー全体で今も1本だけです。この案は、決めることを並べたもので、実装はまだしていません。

### 効果の見積もり（計測、WSL2・16コア）

1200分の main と、1200分で分岐した child を、どちらも1440分まで計算しました。計測用のスクリプトで、Run の書き込み権の確認を外し、別プロセスで動かしています。

| | 合計（2回） | branch ごと | プロセスごとのピークRSS |
|---|---|---|---|
| 順番に | 40.9 / 38.6秒 | 18〜22秒 | 約520 MiB |
| 同時に（2プロセス） | 21.0 / 21.5秒 | 20〜21秒 | 約520 MiB |

- 2本ならほぼ半分の時間になります。共有している履歴索引（SQLite）での待ちは目立ちませんでした。
- 両方の head の Checkpoint のハッシュは、順番でも同時でも同じでした。
- メモリは、同時に計算する本数だけ増えます。1440分では1本あたり約0.5〜0.9 GB です。

### 今の作り（変える必要がある所）

| 所 | 今 | 段階3で要ること |
|---|---|---|
| 書き込み権 | Run ごとに1つ（`runs/{run}/worker-lock`、`claim_run`） | branch ごとの書き込み権。履歴索引の作り直し（`HistoryIndex.rebuild`）、Run の削除、回復（`recover_interrupted`）など Run 全体の操作は、すべての branch の書き込みと排他にする |
| Run の状態 | Run ごとに1つ（`status.json`：running / paused / completed / failed / interrupted） | branch ごとの状態。Run の状態は branch から導くか、別に持つか |
| サーバーの受付 | 同時に1本（`ProjectAPI._active`、`_cancel`、`_watcher`） | branch ごとの job と取消し。同時に動かす本数の上限 |
| 取消し | Run 単位（`POST …/cancel`） | branch 単位 |
| 画面（Project 画面） | 計算中は、ほかの branch の計算・分岐・介入プレビューのボタンを無効にする（`data.status === "running"`） | branch ごとの状態の表示と計算のボタン。比較中の branch をまとめて計算するボタン（任意） |

保存側は、もともと同時の書き込みに耐える作りです。

- Checkpoint の chunk は content-addressed で、`os.link` で書きます。
- frame のキャッシュは、Checkpoint ごとのファイルを置き換えで書きます。
- 履歴索引の行は branch ごとで、SQLite が書き込みを1つずつにします。
- 容量の確認は、保存1回の中で1回だけです（#237。同時に書く分だけ、上限を少し超えうるのは受け入れ済み）。

### 決めること

1. **同時に計算する本数の上限**：メモリが本数だけ増えるので、上限が要ります。案：既定2本で、設定で変えられるようにします。CPU の数ではなくメモリで決める必要があります。
2. **状態の持ち方**（保存データの変更なので、スキーマ版と移行が要ります）
   - 案A：branch ごとに状態ファイルを足し、Run の `status.json` は「どれかの branch が計算中なら running」のような要約として残します。既存の画面と API の互換を保ちやすい案です。
   - 案B：Run の状態をやめ、branch ごとの状態だけにします。単純ですが、Run の状態を読む所（画面、CLI、回復、レポートの生成のきっかけ）をすべて直します。
3. **書き込み権の持ち方**
   - Linux・macOS では、Run のロックを「branch の書き込みは共有、Run 全体の操作は占有」（flock の LOCK_SH / LOCK_EX）にし、branch ごとのロックファイルを足せば足ります。
   - Windows の `msvcrt` のロックには共有のロックがないので、別の作り（branch ごとのロックファイルを全部取ってから Run 全体の操作をする、など）が要ります。Windows での確認も要ります。
4. **計算中の分岐**：ほかの branch が計算中でも、計算中でない branch からの分岐を許すか。分岐は、元の branch の書き込み権だけで足ります。
5. **完了レポートと LLM の予算**：branch が完了したときのレポートの生成（`finish_review`）と、LLM の利用の記録（Run ごとの予算）が、同時に走る場合の扱い。予算は transaction で数えているので、超えないことは保てます。ただ、同時に使い切りに近づいた場合の扱いを決めます。
6. **Demo（`DemoJobManager`、/demo-v2 の「両分岐」）を対象にするか**：Demo はスレッドで計算しているので、同時に動かしても GIL のため速くなりません。別プロセスにするのは、段階1と同じ量の作業になります。

### 作業の進め方の案

1. 段階2（異なる Run の同時計算）を先に入れます。書き込み権は Run ごとのままで足り、受付を複数の job にして上限を設けるだけです。状態のスキーマも変えません。
2. 上の 2・3 を決めて、branch ごとの書き込み権と状態を入れます（スキーマ版と移行、回復のテストを含む）。
3. 画面に、branch ごとの状態と計算のボタンを付けます（Playwright で確認）。

確かめること：

- 計算結果のハッシュ（WorldState・イベント・KPI）が、順番に計算した場合と同じこと
- 取消し・再開・分岐・再生・回復の回帰テストが通ること
- 同時に計算したときのメモリが上限の中に収まること
- Windows での動作
