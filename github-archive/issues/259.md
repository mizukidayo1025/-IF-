## 元の本文

## 現状

計算中に、保存境界の時刻の frame（`GET …/branches/{branch}/timeline?minute=`）を読むと、ときどき `TimelineError: no checkpoint exists before requested minute` で失敗します。

## 原因（コードから）

1. 保存（`TimelineStore.record`）は、Branch のポインタ（`branch.json`）を先に新しい head に書き換えます（`store.save_captured_branch`）。そのあとで、履歴索引に登録します（`HistoryIndex.ingest`）。
2. 読み取り（`TimelineStore._nearest_checkpoint`）は、ポインタの head を `anchor` にして索引を引きます（`HistoryIndex.nearest` → `ready`）。
3. 1 と 2 の間（保存1回あたり、索引への登録の約0.4秒）に読み取りが来ると、索引の head がポインタと一致しません。そのため `history_index_stale` になります。
4. すると、旧形式の Run のための互換の経路（`timeline.json` を読む）に進みます。新しい Run にはこのファイルがないので、候補は今の head（`computed_until`）だけになります。それより前の時刻では候補がなくなり、上のエラーになります。

## 再現（計測）

100人・生成Scenarioを1200分まで計算した Project で、1440分まで計算を進めました。その間、同じプロセスから 1170分と1185分の frame を繰り返し読みました（WSL2、develop `a03941a` 相当）。

| 計算の動かし方 | 読み取りの失敗 |
|---|---|
| 同じプロセスのスレッド（今の Web サーバー） | 205回、287回（2回の計測） |
| 別プロセス（#48 の PR） | 0回、25回 |

失敗した読み取りはすぐに返るので、失敗の回数は読み取りの頻度で変わります。別プロセスでも、保存の直後に当たれば起きます。

## 案

- **索引が古いときは、索引の head までの範囲で引く**：Checkpoint は変わらないので、索引が知っている head の時刻以下なら、そのまま答えられます。
- **登録の順序を変える**：索引に先に登録してから、ポインタを書き換えます。ただし、ポインタの更新が失敗したときに、索引に先の行が残る場合の扱いが要ります。

## 完了の条件

- 計算中の保存の直後でも、計算済みの時刻の frame・比較・再生の読み取りが失敗しないこと
- 結果が修正前と一致すること
- offline全体テストが成功すること
