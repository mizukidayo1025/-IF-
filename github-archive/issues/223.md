## 元の本文

## 現状

分岐を作ると、子branchの最初の保存（`TimelineStore.record`）で、履歴索引（`storage/history_index.py` の `HistoryIndex.ingest`）が子branchの行を作ります。新しいbranchには索引の行がまだないため、分岐する時刻までの全履歴（イベント、KPI、関係するIDや検索語など）を最初から登録します。分岐元の索引には、同じ記録から作った行がすでにあります。

100人・生成Scenarioを ProjectAPI 経路で1440分まで計算した Project で、介入なしの分岐を1回実行したときの時間です（PR #222 の適用後、WSL上で1回ずつ）。

| 分岐する時刻 | 分岐全体 | うち子branchの索引の作成 |
|---|---:|---:|
| 1440分 | 32.0秒 | 11.8秒 |
| 720分 | 14.5秒 | 5.3秒 |

1440分では、索引に1件ずつ登録する呼び出し（`_RecordBatch.put`）が約10万回走ります。分岐の時刻が遅いほど時間がかかります。

## 案

- **分岐元の行を写す**: 分岐する時刻までの分岐元の行を、branch名だけ変えて SQL でまとめて写し、その後の分だけを登録します。
- **系譜をたどって読む**: 子branchには分岐後の行だけを登録し、読むときに分岐元の行もたどります。索引の読み方が変わるため、影響範囲は大きくなります。

## 注意点

- 写した行が、子branchを最初から登録した場合と同じになることを確かめる必要があります。たとえば次の点です。
  - イベントの行には、体調履歴（`body_state_v1.history`）の観測された効果を結び付けています。体調履歴は2万件の窓で古い項目を捨てるため、分岐元が行を作った時点の窓と、分岐する時刻の窓では中身が違うことがあります。
  - 登録済みの件数（`heads.counts`）や `checkpoints` の行など、branchごとの管理情報の扱い
  - 会話記録など、Checkpoint から作らない行の扱い
- 履歴索引は Checkpoint から作り直せる読み取り用のデータです。それでも、索引の内容や読み方を変える場合は、索引の版と作り直し（`rebuild`）の扱いを確認してください。
- 保存形式、Checkpoint、保存間隔は変えません。

## 完了の条件

- 子branchの索引の内容（各表の行）が、最初から登録した場合と一致すること
- 分岐した子branchの検索・一覧・比較の結果が、修正前と一致すること
- 分岐1回あたりの索引の作成時間が、分岐の時刻によらず小さくなること
- offline全体テストが成功すること

## 進み具合

PR #224 で、子branchの索引作成（1440分のProjectで全履歴を新しいbranch名に登録）が 11.8秒から 9.4秒になりました（個人情報の検査と検証器の組み立てを速くしたもの、行の内容は同じ）。

## 残りの内訳（実時間、1440分、約9.8秒）

- SQLite への書き込み（`executemany`）: 約4.7秒。記録 約10万行、関係するID 約127万行、検索語 約84万行を登録しています。
- ID とイベント参照の収集（`_identities`・`_event_references`）: 計測上は約3.1秒。
  - 1回の走査にまとめる実装も試しました。行の内容は同じでしたが、全体の時間は計測の揺れの範囲で変わらなかったため、取り込んでいません。
- 正準JSONとハッシュ、個人情報の検査: 約2秒

## 分岐元の行を写す案について

確かめたところ、子branchを最初から登録した場合の行と、分岐元の行は、次の種類で一致しない場合があります。

- `dialogue`: 観測された効果を、登録時点の体調履歴の窓から作ります。
- `social`・`staff`・`transitions`: model_state の履歴の窓から作ります。窓から落ちた項目は、最初から登録すると含まれません。
- 計算中の観測（`observations`）から作った行: Checkpoint からは作れません。

一方、`events`・`social`（イベントから作る行）・`actions`・`care`・`operations`・`kpis` は、イベントと標本だけから作るので一致するはずです。

写す場合は、次のどちらにするかを先に決める必要があります。

- 一致する種類だけを写し、残りを最初から登録する（SQLite への書き込みは減らず、Python側の約3〜4秒が減る見込み）
- 分岐元の行をそのまま引き継ぐ（最初から登録した場合と中身が変わる）

## 写す方式の効果の上限（計測）

1440分の Project（main の index：記録 115,316行、関係するID 656,607行、検索語 436,812行）で、main の行をすべて別の branch 名に `INSERT … SELECT` で写しました（WSL上、書き込みキャッシュ16 MiB）。

| 表 | 時間 |
|---|---:|
| records | 1.31秒 |
| entities | 1.79秒 |
| tokens | 0.45秒 |
| 合計（commit込み） | 3.75秒 |

今の子branchの索引の作成（全履歴を最初から登録、PR #224 適用後）は約9.3秒です。写す方式で減らせるのは、分岐1回あたり最大5秒程度です（1440分の分岐 18.7秒 → 約14秒）。

一致する種類だけを写して残りを最初から作る方式では、残りの種類（`dialogue` と、model_state の履歴の窓から作る `social`・`staff`・`transitions`）の作成時間が加わります。そのため、効果はこれより小さくなります。

どちらの方式でも、写した行を今のコードの結果とみなしてよいか（上のコメントの、窓に依存する行と、古いコードで作った行）を決めないと、正しさを確かめる基準（最初から作った索引と一致すること、または分岐元と一致すること）が決まりません。そのため、実装はしていません。

## 判断：分岐元の行を写し、写した行は分岐元のコードの結果のまま使う（PR #246）

「一致する種類だけを写す」方式を採用します。写した行を、今のコードの結果とみなすことにしました。

### 写す行と作り直す行
- **写す**: 子branchが分岐元と共有するイベントと KPI の標本から作る行です。`events`、イベント由来の `social`、`actions`・`care`・`operations`、`kpis` と、その `entities`・`tokens`・件数を写します。
- **作り直す**: 体調や model_state の履歴の窓から作る行（`dialogue`、`social`・`staff`・`transitions`）と、分岐元の index に見つからない行です。

### 受け入れたこと
- 写した行は、分岐元がその行を登録した時点のコードで作られています。同じ Run の途中でアプリを更新し、行の作り方が変わっていた場合、子branchのその行は分岐元の行と同じになります。今のコードで最初から作った行とは一致しません（伏せ字の規則を変えた #187・#190 のような変更）。
- 違いが出るのは、Run の途中でアプリを更新した場合だけです。その行は分岐元の index にすでにあり、ローカルのディスクから外へは出ません。
- 補足：「既存Runの履歴索引を再構築」（`POST R/index`）は、index が先頭の Checkpoint と一致しているときは断ります（#213、計算中の判断の記録を失わないため）。そのため、分岐元と同じように、子branchも再構築で今のコードに揃えることはできません。分岐元が古いコードの行を持ち続けるのと同じ扱いです。

### 効果（develop `347e85b`、WSL2）
1440分まで計算した Project で、介入なしで分岐しました。

| 分岐する時刻 | | develop | #246 |
|---|---|---|---|
| 1440分（3回ずつ） | 分岐全体 | 20.16 / 19.66 / 19.37秒 | 16.62 / 16.50 / 16.93秒 |
| 1440分（3回ずつ） | うち子branchの index 登録 | 11.03 / 10.52 / 10.29秒 | 7.66 / 7.45 / 7.45秒 |
| 720分（1回ずつ） | 分岐全体 | 9.25秒 | 8.09秒 |
| 720分（1回ずつ） | うち子branchの index 登録 | 5.07秒 | 3.90秒 |

- 子branchの index の全表（records・entities・tokens・generations・heads）の行のハッシュは、すべての回で develop と同じでした。分岐元の index は今のコードで作ったものです。
- 子branchの Checkpoint のハッシュも同じでした。
- `tests/integration/test_exact_timeline.py` で、子branchの index の全表が、同じ head を最初から登録した場合と一致することを確かめています。

### 完了の条件について
- 「分岐1回あたりの index の作成時間が、分岐の時刻によらず小さくなること」は満たしていません。写す分の時間は、分岐の時刻に比例して残ります。
- 残りの多くは、SQLite への書き込みと、作り直す行の作成です。
