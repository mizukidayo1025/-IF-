## 元の本文

## 背景

ブラウザーで、「設置先を一意に特定できない」として、自然言語の介入指示がすぐに反映できないという報告がありました。バックエンドで調べたところ、介入の操作ごとの「対象の候補」の決め方がほとんど絞り込まれておらず、追加先が自明な指示でも聞き返しになることが分かりました。

この Issue では、現在の操作と候補の対応を整理し、どこを直すべきかと、決める必要があるルールを挙げます。

- 調査環境：main `48401a5`、生成Scenario（避難者30人・1日、Zone 8つ）
- 実APIは呼んでいません。ルール処理の結果と、Opusに渡す候補（schema）の計算だけで確認しました。
- 報告の文言「設置先を一意に特定できない」はコードにありません。Opusが自分で書いた聞き返しの質問だと考えられますが、ライブAPIでは未確認です。

## 現状1：ルール処理（offline、またはAIを使えなかったとき）

扱える操作は6つです（`src/sheltersim/llm/natural_language.py` の `_resolve_target`）。

| 操作 | 候補の決め方 | 生成Scenarioでの候補 | 結果 |
|---|---|---|---|
| トイレ追加 `add_toilet` | 全Zone | 8つ全部 | 聞き返し |
| スタッフ追加 `add_staff` | 全Zone | 8つ全部 | 聞き返し |
| 避難者の到着 `add_evacuees` | 全Zone | 8つ全部 | 聞き返し |
| 避難者の帰宅 `depart_evacuees` | 全Zone | 8つ全部 | 聞き返し |
| 設備の停止 `facility_outage` | トイレ設備だけ | `accessible_toilet_01`、`toilet_01` | 聞き返し |
| 断水 `water_outage` | 給水所のあるZoneだけ | `food` | 自動で決定 |

- 操作に合わせた絞り込みは、設備の停止と断水の2つだけです。
- 追加系の4つは全Zoneを候補にします。トイレ追加にも、`toilet` 以外の7つ（`food`、`staff` など）が候補に入ります。
- 日本語でZone名を書いても決まらない場合があります。Zone `toilet` の名前は「トイレ」ですが、この語はトイレ一般を指す語として名前の照合（`_contains_label`）から除外されています。そのため、「トイレゾーンにトイレを1基追加」「トイレに仮設トイレを1基追加」はどちらも8つのZoneで聞き返されます。

生成Scenarioの Zone：

| zone_id | 名前 | 既存設備 |
|---|---|---|
| `corridor` | 共用通路 | なし |
| `food` | 食事・給水スペース | 食事配布、給水所2つ |
| `intake` | 受付 | 受付 |
| `medical` | 救護スペース | 救護 |
| `quiet` | 静養スペース | 静養支援 |
| `sleeping` | 避難スペース | なし |
| `staff` | 運営本部 | なし |
| `toilet` | トイレ | トイレ、多目的トイレ |

## 現状2：AI（Opus）経路

この生成Scenarioでは18種類の操作が使え、それぞれ対象の種類（`target_kinds`）だけが決まっています。

| 対象の種類 | 操作 | 候補 |
|---|---|---|
| Zone | 追加系4つ（トイレ・スタッフ・到着・帰宅）、環境系（騒音・照明・温度・換気・プライバシー・仕切り・需要率・一時的な部屋形状） | 8つ全部 |
| 設備 | 設備の停止、稼働数の変更、設備の移動 | 8つ全部（受付や救護の窓口も含む） |
| 人 | 再会などの在所操作 | 30人全員 |
| 経路 | 通行の可否 | 14本全部 |
| 資源 | 物資の配送 | 2種類（食事・水） |

- 検証は「対象の種類が操作に合っているか」と「そのIDがScenarioにあるか」だけで、操作に合わせた絞り込みはありません。そのため、AI経路の設備停止は、ルール処理と違ってトイレ以外の設備も対象にできます。
- 聞き返しの選択肢（`choices`）は、これらすべての種類のID（約60個）のどれでも検証を通ります。

## 現状3：ブラウザーでの聞き返しの流れ

- /demo-v2 は、`choices` の各IDをボタンで表示します。押すと、指示文の末尾に `zone_id: <選んだID>` という1行を足して、もう一度Previewします（`src/sheltersim/web/static/demo-v2.js` の `previewIntervention`）。選んだ対象を渡す専用の項目はなく、指示文の文字列として届くだけです。
- ルール処理では、この行を明示されたZone IDとして優先して使います。offlineでは、選択後にすべて適用可能になることを確認しました。
- Opus経路では、この行は自由文の一部です。追加先として使わせる仕組みはありません。
- Project画面には選択肢ボタンがありません。

## 問題点

1. 追加先が自明な指示でも聞き返しになります。トイレ追加は、既存トイレのあるZoneが1つしかなくても、全Zoneで聞き返されます。
2. 不自然な候補が出ます。トイレ追加に `food`、避難者の到着に `toilet` や `staff` が候補に入ります。
3. Opusの選択肢がZoneとは限りません。設備IDなどが選択肢に出ても検証を通り、/demo-v2 はそれを `zone_id:` として追記します。この場合、再Previewがまた失敗する可能性があります（未確認）。
4. Opusが `zone_id:` の行を使わず、再び聞き返す可能性があります（未確認）。報告の「すぐに反映できない」に最も当てはまりそうです。
5. ルール処理とAI経路で候補が異なります。たとえば設備の停止は、ルール処理ではトイレだけ、AI経路では全設備です。

## 対応案

### A. トイレ追加（根拠をScenarioのデータから取れるもの）

- 追加先がない指示では、既存トイレ（`kind` がトイレの設備）のあるZoneに候補を絞ります。1つに決まれば自動で選び、「既存トイレのあるZoneへ追加」という仮定としてPreviewに明示します。反映には従来どおり承認が必要です。
- トイレが複数のZoneにある場合は、それらのZoneに絞って聞き返します。トイレがないScenarioでは、今と同じく全Zoneを候補にします。
- 他のZoneを明示した指定（例：「静養スペースに多目的トイレを追加」）は受け付けたままにします。屋外や福祉スペースの近くに置く運用もあり得るためです（出典は未確認）。
- 断水の「給水所のあるZoneだけ」と同じ考え方です。
- 「トイレゾーン」「トイレエリア」と書けば `toilet` Zone に決まるようにします。

### B. Opus経路の候補を、ルール処理と同じ規則にそろえる

- 案1：compilerへの指示に規則を書きます。
- 案2：Opusが追加先を聞き返し、候補が1つに決まる場合は、バックエンドで補います。決定的で、Opusの言い回しに左右されません。
- 聞き返しの `choices` は、その操作の対象の種類のIDに限るよう検証します（Zoneを聞くならZone IDだけ）。

### C. ブラウザーで選んだ対象の渡し方

- 指示文への `zone_id:` 追記ではなく、選んだ対象を専用の項目でバックエンドに渡し、対象を確定させる方式が考えられます。API契約の変更になるので、別途相談が必要です。

## 決める必要があること

- [ ] トイレ追加の既定値（対応案A）をこの形で入れてよいか
- [ ] スタッフ追加・避難者の到着・帰宅、環境系の候補をどう絞るか。Zoneに用途の種別がないため、Scenarioのデータだけでは根拠が取れません。Zoneに用途の種別を持たせるか、操作ごとの規則を決める必要があります。
- [ ] 設備の停止を、AI経路でもトイレ以外に広げてよいか（ルール処理と経路で差がある）
- [ ] Opus経路の補い方を案1・案2のどちらにするか
- [ ] 対応案C（選んだ対象を専用の項目で渡す）を進めるか
- [ ] ライブAPIで、Opusの実際の聞き返し（選択肢の有無、内容、`zone_id:` 追記後の挙動）を確認するか。確認する場合は、呼出し回数と予算の上限の承認が必要です。
