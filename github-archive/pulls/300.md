## 元の本文

Checkpoint の保存まわりを短縮します。tick の変更（#298、#299）と合わせて、**7日分が 261.0 秒**になりました。基準の 1590 秒から約 6.1 倍で、目標の約 318 秒を超えています。

## 変更
- **Checkpoint v2:** ハッシュを chunk のハッシュの木にします。履歴のリストは、項目数と 128 項目ごとの SHA-256 から作るので、保存では新しい chunk だけをハッシュします。v1 はこれまでの決まりで確かめて読めます。その続きの保存は v2 になります。
- **秘匿情報の確認:** 新しい chunk の bytes を Rust で読み、キーと、パターンに一致しうる文字列だけを Python の同じ関数で判定します。保存済みの chunk は最初の保存で確認済みなので、読みません。
- **保存の再利用:** 復元の確認で KPI の標本と確認済みの履歴を比べ直しません。frame のケア履歴と EventLog の bytes も、増えた分だけを読みます。正準 JSON は Rust で作ります。
- **索引:** 行の確認を Rust で行い、記録を bytes のまま索引のプロセスに送ります。
- **分岐・再開:** 活動中の行動を Rust の索引から見つけ、約 17.6 万件の記録を作らなくなります（約 1.55 万件）。

## 入れなかったもの
書き込みだけを別のスレッドに渡す作りも試しましたが、取り消しました（`72087ae`、`9b84d6b` の revert）。短縮は 1 回の保存あたり約 50 ms（7 日分で約 17 秒）です。一方で、強制終了のときに失う保存が最大 1 回分増え、保存の失敗も遅れて分かります。短縮に見合わないと判断しました。
