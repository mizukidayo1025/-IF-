## 元の本文

## 背景

Webや初期Scenario生成器で、水・食料の初期在庫を入力したScenarioを実行すると、Runが途中で止まっていました。在庫を入力しない場合は資源サービスが無効なので、この問題は表に出ていませんでした。設備の既定値を国の基準以上にする作業（水・食料の既定在庫と毎日の補給を含む）の前に、これを直す必要があります。

調べたところ、原因は互いに独立した3つの不具合でした。1つを直すと、それまで隠れていた次の不具合で止まる形です。

| 止まった場所 | 例 | 原因 |
|---|---|---|
| 状態検証 `resource queue stall must describe the current facility queue head` | 30人・1日・seed 7、495分目 | 止まった記録（`stall_state`）が、列の先頭が変わった後も古いAgentを指したまま残る |
| 状態検証 `resource service request history is invalid` | 同じScenario、512分目 | 施設と同じzoneから依頼したときに記録する理由値を、状態検証が許可していない |
| 室内経路の計算 `StopIteration` | 100人・1日・seed 1、151分目 | 経路網の重複除去で、出発点が近くの別の点に置き換わる |

## 変更内容

1. **止まった記録の更新**（`src/sheltersim/domain/queueing.py`）
   - 給水・配食の列で、ニーズによる並べ替え（`prepare_facility_queue`）と、待ちきれずに列を離れる処理（`_abandon_and_retry`）の後に、記録が今の先頭を指していなければ消します。
   - 次の判定で新しい先頭が止まっていれば、記録し直されます。停止の履歴（`queue_stall_history`）は消しません。
   - サービス開始など他の経路は、もともと記録を消していました（`resource_service.py`）。
2. **同じzone内の理由値を許可**（`src/sheltersim/core/world.py`）
   - runnerが書き込む`travel_scheduled`/`in_room_route_available`と`rejected`/`room_route_blocked`の2組を、状態検証で許可します。
   - 書き込む側は変えていません。記録の意味（室内経路か通路経由か）を残すためです。
   - 他の組み合わせ（例：`queued`/`in_room_route_available`）は、これまでどおり拒否します。
3. **室内経路の端点を保持**（`src/sheltersim/domain/movement.py`）
   - 経路網の点は、座標を1e-8 mに丸めて重複を除いています。後から来た点が上書きするため、角や出入口の点が出発点・目的地と丸めて一致すると、端点が置き換わって探索で`StopIteration`になっていました。
   - 重複除去の後に端点を入れ直し、丸めたキーで位置を探します。衝突がない場合は、点の並びも番号も変わりません。

## 互換性
