## 元の本文

保存の残りを減らします。同じ負荷で並走した比較で、`TimelineStore.record` は 242.1 秒から 130.4 秒に、全体は 338.8 秒から 217.9 秒になりました。

目標の「`record` 約 70 秒未満」は**軽い回で確認できていません。** 他の作業で負荷が高く、CPU の比から直した見積もりで約 71 秒です。負荷のない回での計測は、全系統の統合の後に行います。

## 内訳の分からなかった約 40 秒の正体
開始時点の軽い回で、次の2つでした。
- `BackgroundIndexer.submit` 25.8 秒（CPU 1.2 秒）: 登録のプロセスが前の登録を終えるまで待っていました。登録 1 回の CPU が約 0.5 秒あり、**このプロセスが計算全体の律速**でした。
- `_cache_frame` 16.7 秒（CPU 16.1 秒）

## 変更
- 登録を軽くしました。新しい索引に `entity_time`（読むクエリなし）を作らず、`entity_turn_order` は会話の行だけの部分索引にします。接続と 256 MiB のキャッシュを保ち、行は Rust で1回で読みます。
- 登録のプロセスは、パイプを別スレッドで読みます。
- capture: 各フィールドの JSON を1回だけ作ります。復元の確認の新しい記録を Rust で bytes と比べます（`same_saved_records`）。新しい記録の bytes を凍結のまま作ります（`record_json`）。
- chunk の圧縮を最大 4 スレッドにします。保存はその終わりを待つので、保存の確実さは変わりません。bytes も同じです。
- frame を Rust で符号化します。

## 判断をお願いしたい点: 索引の同期が1種類減ります
保存データの fsync は **3,034 回のまま**です。索引のデータのコミットの同期も変わりません。

ただし、接続を保つようにしたので、索引を開くたびに `PRAGMA user_version=2` が起こしていた**内容のないコミットの同期がなくなります。** データを守っていない同期なので残しませんでしたが、「fsync を減らさない」という方針の字義には触れます。問題があれば戻します。その場合の時間は測っていません。
