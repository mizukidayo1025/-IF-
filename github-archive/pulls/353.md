## 元の本文

## 概要

すぐ閉じられる項目（L1）と、列・資源・人口の残り（L4）を Rust へ移しました。ゲートの driver の `kernels_refused` は 3,708 → 713 回で、この範囲で有効な Run に残る拒否は 0 です。結果は変わらず、新しい係数はありません。

詳細は `docs/rust-port/lanes/l4-queues.md` にあります。

## 移した処理

- 列：`_abandon_and_retry`（両方の列、帰り道、記録）
- 資源：`cancel`、`interrupt_for_staff`、`ResourceServiceManager` の部品を行で実装
- driver：`independent` の列を含む `arbitrate` のループ
- 人口：`_defer_while_busy` と `queue_departures` の取り込み中の枝（Rust が同じ文で `EventSuppressed` を出します）、`apply_population_presence_command` の外側、`_state`、`_initial_dynamics`
- 受領：4 種類すべてと、未確認の直近の記録の扱い（契約に読ませます）
- そのほか：情報の接触の抑止 4 つ、`interrupt_staff_trips_on_closed_routes`、長期の状態がないモデルでは何もしない、`social_propagation_v1` を最初の tick で作る、`request` の `validate_state=True`、`population.rs` の部屋の読みを `overlay.rs` にまとめる、`handlers.rs` から kernel を直接呼ぶ
- 書いた後の `__wrapped__` の呼び戻し（`population.rs`、`population_lifecycle.rs`）をなくしました。先にベースの木のテストで 2 か所とも実際に通ることを確かめ、後の受け入れが読むものを書く前に確かめる形で閉じました。

## 何が何で比べられているか

`cancel`、初回の状態、`_initial_dynamics`、閉じた経路はテストだけです（閉じた経路のシャドーはゲートで 0 回）。ほかはゲートとテストの両方です。7 日間に届くのは列を離れる人の 4 回だけです。

## 分かっている弱点

- 全シャドーを同時に動かした実行は、直す前のコードの 1 回だけです。2 シナリオが落ち、差 35 件が出ましたが、どちらもシャドーの不具合でした（`sitecustomize.py` の長期の状態の扱い、`shadow_staff.py` の `record.state_changes`）。直した後に全シャドーは動かしていません。
- driver の `independent` の列のループはシャドーを通りません。`first_difference --both` と `test_tick_driver.py` だけが比べます。
- `check_relocation_completes` は書き込みの前の世界を読みます。後の kernel が違う理由で拒否すると `RuntimeError` になります。ゲートとテストでは起きていません。
- `check_waiting_for_admission` は部屋のある古い形（`room_admissions` なし）を拒否し、Python が動きます。手順 4 の前に扱いを決める必要があります。
- `care_receipts.rs` の `ingest` に書いた後の呼び戻しが 1 か所あります（文を出すための道）。通るテストはなく、回数も数えていません。
- 感度：再試行の既定 15→16 と上限の文はテストだけが検出します。帰り道 +1 分はハッシュ、シャドー、テストが検出します。`requeued` の順番は最初どれにも検出されなかったので、テストを足しました。
- Linux 以外は CI に任せます。
