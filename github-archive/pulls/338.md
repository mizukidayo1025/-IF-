## 元の本文

## 概要

`resource_service_v1` を Rust の行で持ち、サービスの `arbitrate`、`complete`、`request` と、`_apply_proposal` のうち単純な判断の効果を kernel にしました。結果は変わりません。tick 全体の差は A/A の揺れの範囲です。

詳細は `docs/rust-port/lanes/m4-service.md` にあります。

## 移した処理

- `_apply_proposal` を `_apply_effect` と `_record_outcome` に分け、`rules/proposals.rs` に `_apply_effect` の kernel を追加しました。対象は `wait`、`rest`、仮設の部屋がない `sleep`、社会的な 3 つの行動、`fetch_water`、`collect_meal`、`request_toilet` です。
- `rules/travel.rs`：すべての呼び出し元の `_route` と `_schedule_travel`、設備の選択
- `rules/service.rs`：`_serve_head`（`arbitrate` のループの 1 周分。ループ自体は Python）、`_facilities_to_serve`、`complete`、`request`、`record_request_outcome`
- `state/resource_service.rs`：型付きの行と毎 tick の検証。保存時の履歴の検証は Python です。

履歴は設計にある正準バイト列ではなく、型付きのリストのままです。7 日間で約 1 万件なので、バイト列化は後回しにしました。

## 分かっている弱点

- 感度：既定の分 5→6、区域の容量の `>=`→`>`、負荷と分の順序の入れ替えは、シャドーとハッシュでは見えません。最初の 2 つは既存のテストが検出します。順序の入れ替えはテストを足し、壊したコピーで失敗することを確認しました。
- 全シャドーのゲートは 2 つの修正の後に通しましたが、7 日間のシャドーはその修正の前です。修正した枝は 7 日間には現れません。
- 経路の Policy はクラス名で判断するので、同じ名前の別のクラスには気づきません。
- 経路の同順位での ASCII 以外の ID はテストしていません。バイト順とコードポイント順は理論上一致します。
- kernel は予定済みのイベントの順序番号を直接確かめません。列のレーンと同じです。世界の検証で排除できるはずで、起きた場合は `schedule` が同じ種類のエラーを出します。
- RSS と Rust の行の網羅は測っていません。Linux 以外は CI に任せます。
