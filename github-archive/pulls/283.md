## 元の本文

## 概要

全テストを流している途中で、`tests/e2e/test_project_scenario_to_results.py::test_arrivals_typed_on_the_project_screen_show_in_the_comparison` が1回だけ `HTTP 409` で失敗しました。単独で流すと通ります。原因はテストではなく、スレッド方式の計算（テスト・CLI・計測器が使う `ProjectAPI(worker="thread")`）の終わり方にありました。

## 原因

スレッドの計算は、終わるときに次の順で処理していました。

1. Branch の最後の状態（`paused`・`completed`・`failed`）を書く
2. telemetry を記録する（計測を求めたとき）
3. 書き込み権（lease）を手放し、ジョブの表から外す

1 と 3 の間に、状態を見た利用者（画面やテスト）がすぐ次の計算を頼むと、ジョブがまだ表に残っています。そのため `background worker is busy`（409）で断られていました。スレッド方式は同時に1つしか計算しないので、別の Branch でも断られます。

## 変更（`web/projects.py` の `_advance`）

最後の状態を書くこと、lease を手放すこと、ジョブを表から外すことの3つを、計算の受付（`submit`）が取るのと同じロックの中でまとめて行います。

- 状態を見てすぐ次の計算を頼んだ場合、受付はこのロックを待ちます。ロックが空いた時点ではジョブはもう表になく、計算を受け付けます。
- 状態を書けなかった場合（ディスクがいっぱいなど）も、lease とジョブは必ず片付けます。
- 状態の書き込みが telemetry の記録の後になりますが、報告（`report.json`）は今までどおり状態を書く前に作ります。

別プロセス方式（Web サーバー）は、計算の子プロセスが状態を書き、サーバーの見張りのスレッドがジョブを表から外すので、同じ隙間が少しだけ残ります。画面は、選んだ Branch の計算中はボタンを無効にし、状態が変わってから有効にするので、この隙間に押すことはまずありません。必要なら別の Issue にします。
