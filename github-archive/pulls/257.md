## 変更

#245 で、`ProjectStore` は読み込んだ Checkpoint の世界の複製を持つようになりました。この PR では、計算を進めるときの読み込み（`TimelineStore._advance` → `load_restored_branch`）でだけ、その複製を作らないようにします。

- 計算の先頭の Checkpoint は、計算が保存するたびに新しくなります。そのため、読み直されることはほとんどありません。複製を持っても、計算が終わるまでメモリを占めるだけでした。
- `load_restored_checkpoint` と `load_restored_branch` に `keep` 引数を足しました（既定は `True`）。計算の読み込みだけが `keep=False` を渡します。
  - `keep=False` でも、すでに持っている複製があれば、これまでどおりそれを使います。
- frame・再生・比較などの読み取りは、これまでどおり複製を持ちます。

## 結果（ローカル、WSL2）

100人・生成Scenarioを1200分まで計算した Project で、1440分まで再開しました。develop `f80ee74` と、交互に3回ずつ測っています。

| | develop | この PR |
|---|---|---|
| 再開（1200 → 1440分） | 20.62 / 20.51 / 20.59秒 | 21.71 / 20.22 / 20.13秒 |
| ピークRSS | 554 / 552 / 553 MiB | 542 / 540 / 540 MiB |

- ピークRSS は約12 MiB 下がりました。時間の差は、計測の揺れの範囲です。
- head の Checkpoint のハッシュは同じでした。
- 複製では EventLog の記録と予定イベントを共有するので、持ち続けていた量はもともと小さめでした。

0分から計算する1日分のベンチマーク（`benchmarks/investigate_performance.py`）では、ピークRSS は変わりませんでした（この PR 928 / 938 MiB、develop 922 / 935 MiB）。#245 の前は 829〜841 MiB でした。この増加は、ベンチマークが計算のあとに行う `load_branch` で、1440分の世界の複製を作るためです。つまり、#245 で受け入れた読み取りの複製によるもので、この PR の対象ではありません。

## テスト

- `tests/unit/storage/test_checkpoints.py`：計算を進めても `_copy_restored` を呼ばず、`ProjectStore` が複製を持たないこと。そのあとの読み取りでは複製を持つこと。この変更を戻すと失敗することを確かめました。
- 読み込みを数えるテストのラッパー（`tests/support/storage.py` の `no_checkpoint_decode`、`tests/integration/test_resume_checkpoint_loads.py`）が、新しい `keep` 引数を受け取ってそのまま渡すようにしました。
- #245 のテストの説明から「Draft for」を外しました。
- `docs/project-persistence.md`：計算を進めるときの読み込みでは複製を作らないことを追記しました。
