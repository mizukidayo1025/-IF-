## 元の本文

Closes #180

帰還（と到着）が、区画へ移動中の人の席を奪い、定員を超えてシミュレーションが止まる不具合を直します。係数は変えていません。

## 原因

区画への受け入れの判定が、処理ごとに違っていました。

| 処理 | 場所 | 数えていたもの |
|---|---|---|
| 移動の開始 | `experiments/runner.py` | 区画にいる人 + そこへ移動中の**全員**（出発時に席を確保する） |
| 帰還・移動（relocate） | `domain/population_lifecycle.py` の `_zone_has_room` | 区画にいる人 + **帰還の移動**で向かっている人だけ |
| 避難者の到着 | `domain/population.py` の `_zone_has_room` | 区画にいる人**だけ** |

移動は出発時に席を確保するのに、帰還と到着はその席を数えませんでした。そのため、移動中の人の席に帰還者や到着者を入れてしまい、移動中の人が着いたときに定員を超えていました。

**調べる途中で、到着にも同じ不具合があると分かりました。** #180 の再現と同じ状況で、20分に1人を `staff` に到着させると、22分に止まります。原因が同じなので、この PR であわせて直します。

## 変更

- `domain/temporary_spaces.py` に `incoming_travelers(world, zone_id, excluding=None)` を足した。移動中（`MOVING`）の人のうち、行き先がその区画か、その区画の施設である人を数える（移動の開始の判定と同じ数え方）。
- 移動の開始・帰還と移動・到着の3つの判定で、この関数を使う。
- 移動の開始の判定は、同じ数え方の置き換えなので、動作は変わらない。使わなくなった `_travel_destination_zone` は消した。

席がないときは、帰還は今までどおり `pending_returns` で待ち、空いたら `admit_pending_returns` で入ります。到着も、受け入れを待ちます。

## 確かめた結果

#180 の再現（`staff` の定員1、10分に A019 が一時外出、20分に `staff` へ帰還。A001 が `staff` へ移動中）では、次のようになりました。
- A019 は20分に「待機」になる。A001 が `staff` を出たあと、35分に入る。
- 120分まで止まらない。途中のCheckpointから再開しても、同じ結果になる。

到着の再現でも、新しく来た人は移動中の人が着くまで入らず、空いてから `staff` に入りました。

## テスト

`integration/test_population_presence.py`
- #180 の xfail を外し、`test_a_return_waits_while_someone_is_walking_to_the_full_zone` を書き換えた。帰還が待機になり、そのあと入ること、待ちが残らないこと、入った後は `staff` にいることを確かめる。
- `test_an_arrival_waits_while_someone_is_walking_to_the_full_zone` を足した（到着）。移動中の人が着いた分には、新しく来た人はまだ入っておらず、その後に入ることを確かめる。
- 2件が共有する「`staff` の定員が1の生成Scenario」は fixture にした。

直す前のコードでは、2件とも `zone 'staff' exceeds ... capacity` で失敗することを確かめました。この2件で、これまで通せなかった `admit_pending_returns` も通ります。
