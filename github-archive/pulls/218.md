Issue #45 の候補2（施設形状・空間制約の直接解析）に対応します。候補1（毎tickの整合性検証）と候補3（時間とともに伸びる処理）は扱いません。数式・係数・丸め・tick順序・乱数は変えていません。モデル担当者との調整は済んでいます。

## 計測（修正前、100人・生成Scenario・360分・単体実行、cProfile）

計30.8秒のうち、直接解析は約2秒（6〜7%）でした。いちばん大きいのは `movement.py` です。`_spatial_constraints()` が実効の空間制約を `model_dump` した dict で返すので、呼び出し側（`route_is_physically_clear` 19,042回、`plan_in_room_route`、`_queue_slot_position`、`facility_approach_route`）が、呼ばれるたびにそれを `model_validate` で解析し直していました。ほかに `runner._route` と `facility_queues.independent_queues_required` が `FacilityGeometry` を直接解析していました。

## 変更

- `movement._spatial_constraints()` は、実効の `SpatialConstraints` モデルをそのまま返すようにしました。
  - 実効の制約は、検証済みの壁・障害物・占有範囲から組み立てています。`SpatialConstraints` にはモデル全体を見る validator がありません。そのため、往復解析しても同じ値のモデルが返るだけでした。
- `geometry_overlay.parsed_facility_geometry(raw)` を追加しました。runtime の上書きを含まない Scenario の形状を返し、`geometry_config_scope` の中では `effective_geometry` と同じ解析結果を共有します。scope の外では、これまでどおり呼ぶたびに解析します。
  - 次の箇所がこれを使います: `facility_queues`（2か所）、`common_operations.operational_demand_snapshot`、`runner._route`、`population`（6か所）、`effects` の到着経路の検査。
