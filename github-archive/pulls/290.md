## 概要

#256 の「系譜をたどって読む」案です。分岐した子 Branch は、分岐元の索引の行を写さず、分岐の時刻より前の行は分岐元から読みます。5倍高速化の手順の A7（デモの体感）の2つ目で、#288 の原因の1つ（分岐のたびに容量が大きく増える）もなくします。

これまでの分岐は、子 Branch に分岐元の索引の行（`records`・`entities`・`tokens`）を SQL で写していました（#223、PR #246）。7日分の Run では1回の分岐で約3.5 GB、約55〜70秒かかり、2回目の分岐で容量の上限（10 GB）を超えて失敗していました。

## 変更（`storage/history_index.py`）

- **`lineage` 表（索引の版2）：** 子 Branch ごとに、分岐元と分岐の時刻を記録します。
- **読み方：** 履歴の検索は、次の2つをあわせて読みます。
  - その Branch の行
  - 分岐元の、分岐の時刻より前の行（分岐元がさらに分岐していれば、その分岐元の、小さい方の分岐の時刻より前の行）
  
  一覧・ページ送り・関係 ID と検索語の絞り込み・原因のたどり・件数の目安（coverage）が対象です。一覧は、Branch ごとに索引に沿って読み、順序どおりにつなぎます。
- **会話記録：** Branch ごとのもので、分岐元のものは読みません。
- **分岐のときの登録：**
  - 分岐の時刻より前のイベントと KPI の標本は、分岐元の行として読むので登録しません。
  - 体調・職員・人口の履歴は、保存の後と同じく、1分前から読み直します。
  - 分岐元がすでに持つ同じ key の行は登録しません（内容が違えば `immutable_history_record_conflict`）。計算を進めて増える行は分岐の時刻以後なので、この確認は分岐の時刻の直前の行にだけかかります。
- **作り直し（`POST R/index`、`rebuild`）：** 作り直した Branch は、すべての行を自分で作り、`lineage` の行を消して、分岐元を読まなくなります。
- **索引の版：**
  - `lineage` 表を持つ索引は版2（`PRAGMA user_version=2`）です。版2を知らない前のコードは、`history_index_version_unsupported` で読み書きを断ります。黙って子 Branch の分岐前の行を失うことはありません。
  - 版1の索引は、そのまま読めて、次の書き込みで版2になります。
  - 版1のときに分岐した子 Branch は写した行を持ち、`lineage` の行がないので、今までどおり自分の行だけを読みます。
- **`_inherit_rows`：** 使わなくなったので外しました。

## 振る舞いの違い

子 Branch は、分岐元が計算中に記録した、分岐の時刻より前の行動・会話の判断（`actions` の行）も読めるようになります。判断は Checkpoint に入らないので、これまでの子 Branch にはありませんでした（#213）。分岐の時刻より前は分岐元と同じ歴史なので、こちらの方が筋が通ると考えています。
