## 元の本文

## 概要

`staff_operations_v1` と `shared_operations_v1` を Rust の行で持ち、職員の運用で毎 tick 動く処理を kernel にしました。結果は変わりません。予算の比は 0.887（A/A 1.020）です。

詳細は `docs/rust-port/lanes/m4-staff.md` にあります。

## 移した処理

`native/src/rules/staff.rs`、`common_operations.rs`：`assign_pending`、`update_operations`、`assign_operations`、`relief`、`wait_snapshot`、`record_shared_operation`（ケアの受領のみ）。検証は `staff_operations.validate` と `shared_operations.validate_tick`（tick の経路のみ。保存時の再生は Python）です。

各 kernel は計画してから書く 1 回の呼び出しで、コールバックはありません。職員が依頼や仕事を引き受ける tick は、経路とイベントが必要なので丸ごと拒否し、その段階は Python の規則が動きます。

`support_wait_reason_codes` などの呼び出しごとの kernel は効果がなかった（`from_world` 134–141 → 135–140 µs/tick）ので、tick ごとに 1 回の `wait_snapshot` に置き換えました。このため `experiments/metrics.py` も変更しています。

## 分かっている弱点

- **壊れた状態でのエラーが変わります。** `assign_operations` は `shared_passage_edge_loads` と `_maintenance_blocked` を呼びません。壊れた状態でこれらがエラーになる場合、Python はエラーにしますが、kernel は成功します。
- 検証済みの受領は、イベントログが追記のみであることに依存し、`has_event_id` だけを確かめ直します。世界を作り直さずに `event_log` を差し替える場合は未テストです。
- 進行中の仕事は 7 日間に現れないので、ゲートとテストでしか比較していません。
- 7 日間のシャドーは `shadow_staff` だけです。全シャドーは約 2.5 時間かかるので省きました。ゲートでは全シャドーを動かしました。
- ゲートでの検証の拒否（402 件、352 件）は、kernel の範囲外（確認前の受領、進行中の仕事）と読んでいますが、シャドーは理由ごとに分けていません。
- 感度：閾値 0.85、0.45、0.6 の 1% の変更はシャドーとハッシュでは見えず、テストだけが検出します。先頭の `updated_minute` +1 はシャドーとテストで検出しますが、ハッシュは同じです。非番の被曝を数えない変更は、当時テストで検出できなかったのでテストを足しました。足したテストは正しいコードで通ることだけ確認し、壊したコピーでは再実行していません。
- Linux 以外は CI に任せます。
