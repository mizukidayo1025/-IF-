## 元の本文

#48 の段階1です。Web サーバーの計算を、計算1回ごとに起動する別プロセスで行います。同時に計算するのは、これまでどおり1本だけです。

## 変更

- `src/sheltersim/web/worker_process.py`（新規）
  - `start_worker()`：spawn 方式で子プロセスを起動します。子プロセスが Run の書き込み権（`claim_run`）を取って状態を `running` にしたという知らせを受けてから返ります。
    - 書き込み権を取れなければ、これまでどおり `run_worker_busy` などの `StorageError` を返します。
    - 起動が120秒で終わらない場合は、子プロセスを止めます。
  - `run_worker()`：子プロセスの本体です。書き込み権を自分で持つので、サーバーが異常終了しても、書き込み権なしで書き続けることはありません。
    - 計算は、これまでの `ProjectAPI._advance` をそのまま使います。
    - 中止（`multiprocessing.Event`）か、サーバーのプロセスがなくなったことを検出すると、次の保存境界で止まります。
- `ProjectAPI(worker="process")`
  - `submit` は、子プロセスの起動と知らせを待ってから返ります。
  - 見張りのスレッド（`_watch`）が子プロセスの終了を待ちます。結果の状態を書かずに終わった場合（強制終了など）は、Run を `interrupted` にします。サーバーを再起動したときの回復と同じ扱いです。
  - 中止（`POST …/cancel`）、削除・分岐の「計算中は不可」の確認は、これまでと同じ `_active` と `_cancel` で行います。
  - telemetry の `run_peak_memory_bytes` に、子プロセスのピークRSS を記録します（`memory_attribution_status: "measured"`）。画面はもともとこの値を表示できます。
- `ProjectAPI(worker="thread")`（既定）は、これまでどおり同じプロセスのスレッドで計算します。テスト、CLI、計測器（`benchmarks/investigate_performance.py`）はこちらを使います。
- `ProjectAPI.wait_idle()`：それまでに受け付けた計算が終わるまで待ちます。内部の `_pool` で待っていたテストを、これに置き換えました。
- `serve_inspector` は `ProjectAPI(project_store, worker="process")` を使います。
- `docs/architecture.md` に、計算のプロセスの扱いを追記しました。`fewer_collections` の説明も、サーバーのプロセスに効くのは読み込みの区間だけになったことに合わせて直しました。`docs/testing.md` の待ち方も `wait_idle` に直しました。

デモ用のジョブ（`web/jobs.py`）と、分岐の作成（HTTP の処理の中で計算する）は、この PR の対象外です。

## 結果（ローカル、WSL2）

100人・生成Scenarioを1200分まで計算した Project で、1440分まで計算を進めました。その間、同じプロセスから frame を繰り返し読みました（2回ずつ）。

| | スレッド（これまで） | 別プロセス（この PR） |
|---|---|---|
| 計算（1200 → 1440分） | 54.2 / 51.8秒 | 19.5 / 19.6秒 |
| 保存境界の frame（1170分、キャッシュ）の読み取り | 中央値 355 / 30 ms、最大 552 / 531 ms | 中央値 21 / 20 ms、最大 453 / 354 ms |
| 境界の間の frame（1185分）の読み取り | 中央値 3.50 / 3.61秒 | 中央値 2.72 / 2.72秒 |
| 計算後のサーバーの RSS | 709 / 701 MiB | 272 / 269 MiB |

- 計算中でない間の読み取りは、1170分が約21 ms、1185分が約2.43秒です。
- 計算を始める前のサーバーの RSS は、どちらも約400 MiB でした。
- スレッドでは、読み取りと計算が GIL を取り合うので、計算は約2.7倍遅くなり、読み取りも遅くなりました。
- 別プロセスでは、計算の時間は読み取りがない場合（約20秒）と同じでした。
- head の Checkpoint のハッシュは、4回とも同じでした。
- この計測で、保存の直後の読み取りが失敗する既存の不具合が見つかりました。スレッドでも別プロセスでも起きます。#259 に分けました。

## テスト

- `tests/integration/test_process_worker.py`（新規）
  - 別プロセスで30分計算した head が、スレッドで計算した head と同じであること。telemetry に Run のメモリが記録されること。
  - 計算中の2回目の submit は `busy` になり、中止すると `paused` で止まること。
  - 別のプロセスが書き込み権を持つ Run は `run_worker_busy` で断り、状態を変えず、子プロセスも残らないこと。
  - 子プロセスを強制終了すると Run が `interrupted` になり、書き込み権が解放されて、もう一度計算できること。
- offline全体テスト（ローカル）：`SHELTERSIM_LLM_MODE=offline .venv/bin/python -m pytest -n auto` が 1317 passed、4 skipped です。`ruff check` と `ruff format --check` も通っています。PR では CI が動かないため、結果はすべてローカルのものです。
- Windows では確かめていません。spawn 方式は Windows と同じですが、書き込み権（`msvcrt` のロック）を子プロセスで取る経路は、Windows で動かしていません。
