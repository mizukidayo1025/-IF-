## 変更

### `integration/test_comparison.py`（保存したRunの比較）→ 生成Scenario

以前は、トイレの稼働数を手で0にし、シミュレーションを実行せずに指標を書いていました（`world.minute_index = 1` も手で設定）。

今は、30分の生成Scenarioを `run_scenario` で実行して比べます。候補側は、同じScenarioの `scheduled_events` に、0分からのトイレ故障（`toilet_01`）を1件足したものです。保存したRunの比較で、違ってよいのはID・seed・予定イベントだけだからです。

- 1件目：最初に差が出る時刻が0分で、トイレの稼働数の差が −1 であることを確かめる。故障イベントが `added_event_ids` とイベント窓（適用済み・出典ID）に出ることも確かめる。CLI の `compare` も同じ。
- 2件目：seed だけを 11・22・33 に変えた3組を `compare_run_sets` で比べる。

UIの運営条件として故障を入力すると、生成時の入力（provenance）が変わります。そのため別の family になり、この比較では拒否されます。これは比較の契約どおりです。

### `e2e/test_policy_comparison.py`（行動Policyの比較）→ 不具合 #157 を見つけたので xfail

生成Scenarioと、その `with_behavior_policy_variant("priority-rule-v1")` を比べると、必ず「入力が違う」と拒否されます。原因は2つです。

1. 生成Scenarioはモデル一式（suite）を使います。Policyを差し替えると、その一式が個別の指定に展開されます。
2. v2専用の `sleep_debt_utility_weight` が消えます。

比較側はどちらも読み替えません（詳細は #157）。

- 生成Scenarioで期待する形のテストを `xfail(strict=True, raises=ValueError)` と #157 を付けて足した。xfail の原因が `comparison.py:421` の「policy comparison inputs differ」であることは `--runxfail` で確かめた。
- 期待値の妥当性も確かめた。探索用にマニフェストの2か所だけを揃えると、比較は通る。行動の回数が変わり、ストレスの差が0でなく、支援の必要度とmobilityの組の人数がどちらも0より多い。
- h00_small_replay の既存テストは、#157 が直るまで残している（件数 +1）。

### 単体の手書きKPIテスト → `integration/test_web_demo.py` へ移して、実行で確かめる

`unit/experiments/test_comparison.py` の `test_comparison_reports_movement_and_capacity_wait_kpis_with_event_evidence` は、移動完了と容量待ちのイベント記録を手で書き込んでいました（`docs/testing.md` の決まりに反する）。
