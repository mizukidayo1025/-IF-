## 概要

毎 tick の Run で動くイベントハンドラーの大部分を Rust へ移しました。7 日間で Python へ渡るイベントは 10,495 件から 8 件（すべて `resource_delivery`）に減り、新しい kernel と表の拒否は 0 件です（`seek` のみ 1 件、下記）。結果は変わらず、新しい係数はありません。

詳細は `docs/rust-port/lanes/m6-handlers.md` にあります。

## 移した処理

- ケアの受領：`append_applied_care_transition`（pydantic なし）、出典 ID、人の文脈（`rules/care_receipts.rs`）
- トイレ：`request`、`_facilities_to_serve`、`_has_room`、`_start_head`、完了と衛生（`rules/toilet.rs`）。`arbitrate` のループは Python です。
- 支援：`StaffService.request`、タイムアウト、職員の支援の完了、`_record_request_interrupted`、`_record_staff_support_started`、`support_kind_for_agent`（`rules/support.rs`）
- 判断と到着：`apply_effect` の `seek_help`、`seek_information`、`_after_arrival`、部屋への接近、帰り道
- dispatch の表に `toilet_service_complete`、`resource_service_complete`、`support_request_timeout`、`staff_support_complete` を追加。`_finish_stopped_journey` は `sleep_bed` を除いて直接呼びます。
- Python：`append_applied_care_transition` は何も返さなくなりました（結果を読む箇所がありません）。`arbitrate` をメソッドに分けました。

## 分かっている弱点

- **直接呼ぶ経路はシャドーの下で動きません。** シャドーは Python の入口を通るためです。資源の完了の行の読み取り、帰り道、`record_*`、Rust が書く職員の支援の受領は、ハッシュ、実行回数、テストでしか確かめていません。
- 最初のゲートのシャドーは 52 件の差を出しました。Provider のフックが予定するイベントをコピーが含まないためで、規則の差ではありません。その 181 回の `seek` は結果だけを比較するようにしたので、そこの状態はハッシュに頼っています。
- 既存のテストを 2 件変えました。`test_rules_over_real_ticks_keep_every_row_equal_to_its_object` は、転送の書き込みが減ったので 25 → 40 tick にしました（閾値は同じ）。古くなった `test_seek_help_goes_to_python` は置き換えました。
- 感度：衛生 0.2 の 1% はシャドーとハッシュでは見えず、テストだけが検出します。トイレの時間の 1% と部屋への接近の Policy 版は、シャドーとハッシュが検出し、テストは検出しません。
- 13 件の `a value is not a str` の拒否は、件数の一致から `sleep_bed` と `presence_relocation` の移動と読んでいますが、シナリオは追っていません。
- Linux 以外は CI に任せます。新しい C API はありません。
