Refs #178

EffectProgramの検証（`validate_effect_program`）と、実行時の guard の評価を、生成ScenarioのRunで確かめるテストを足します。この検証は、LLMのコンパイラーの出力を信頼しない入力として扱うための関門です。調べる途中で guard の不具合が3つ見つかったので、それぞれIssueにし、`xfail(strict=True)` のテストとして置きます。コードは変えていません。

## 調べたこと

### 検証の拒否の分岐：問題なし

生成Scenario（60分）の本線を10分まで進め、操作17種のそれぞれの正しい効果に、7種類の誤りを入れて分岐させました。誤りの種類は、未知の対象、対象の種類の誤り、分岐より前の開始、Scenarioの終わりでの開始、開始より前の終了、Scenarioの後の終了、未知のパラメーターです。

**すべて、契約の検証エラーか `BranchError` で理由付きで拒否され、ほかの例外で落ちるものはありませんでした。** 数値を0・負・極端に大きくした変異も試し、範囲外は拒否され、範囲内（気温−30℃など）は受け付けられて実行時に止まらないことを確かめました（この部分はテストに残していない）。

### guard の評価：不具合が3つ

| 試したこと | 結果 |
|---|---|
| 偽の guard（施設の稼働数の上限、一時的な空間、経路の通行止め） | 開始も期限切れも「抑制」（正しい） |
| `and` の guard が真（環境の変更） | 開始も期限切れも「適用」（正しい） |
| 偽の guard（環境の変更） | 開始は「抑制」、**期限切れは「失敗」（#195）** |
| 真の guard（施設の移動、間仕切り） | **開始が「guardの対象がない」で失敗（#194）** |
| `target.queue_length eq 0.0`（行列は空） | **偽になる（#196）** |

- **#194**：図面の変更の操作は、対象をpayloadの `target_id` に持つが、guard の評価は `facility_id`・`zone_id` などしか探さない。計画の検査は通るので、承認した変更が実行時に失敗する。
- **#195**：環境の変更だけが、開始が抑制されたときの期限切れを「失敗」として記録する（ほかの操作は「抑制」）。正しく動いたのに、介入の失敗の記録が残る。
- **#196**：`eq`・`ne` が値の型まで比べるため、整数の項目と小数の値（`0.0`）が一致しない。LLMの出力では小数で書かれることがある。

### 不具合ではないが気づいたこと

退出（`depart_evacuees`）は、`include_initial` を指定しないと途中参加の避難者だけを対象にします。途中参加の人がいないと、計画は通るのに実行時に「退出できる人が0人」で失敗します。設計どおりの振る舞いですが、LLMが `include_initial` を付け忘れると起きます。
