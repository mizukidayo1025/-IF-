## 元の本文

網羅率の計測（#176）で、Project画面のAPI（`web/project_services.py`、`web/project_queries.py`）にほとんどテストが届いていないと分かりました。project-round3.js が送るのと同じ要求を、生成ScenarioのRunに対して送るテストを足します。コードは変えていません。

## 調べたこと

生成Scenario（60分）のRun `r` を作り、本線 `main` と、10分にトイレを2台足す分岐 `capacity` を用意しました。そのうえで、project-round3.js が呼ぶ経路を、画面と同じ形で一通り呼びました。

- 証跡：Runの記録・根拠・利用量・監査・索引（取得と作り直し）・Checkpointの一覧、記録された履歴の全種類（10種）、人と世帯の履歴、比較、最初の差分（world・kpis・person）、条件の差
- 一覧：下書き・資産・評価・データセット・利用量・図面・実験
- 書き込み：下書きの保存・競合・更新・削除、アップロード（開始・分割送信・完了）、資産の取得・削除、Runの再実行
- 実験：作成 → cellの準備 → 実行 → 収集 → 評価への取り込み → 比較。校正ではデータセットの登録 → `fit`

**不具合は見つかりませんでした。** 確かめた主な点は次のとおりです。
- 変種で変えたqueueのPolicyが、cellのRunの結果に効いている（同じseedでトイレの平均待ちが変わる）。
- `fit` は、観測値に近い変種を選ぶ。点数は手計算と一致する。
- 再実行したRunは、元のRunと同じworldになる。
- 不正な入力は `StorageError`（HTTPでは409）か `ValueError`（HTTPでは400）になる。500にはならない。

分かりにくい点が2つありました（不具合ではありません）。
- 登録していないデータセットを観測値に使うと、エラーは「saved artifact is missing or corrupt」という一般的な文になる。
- 職員の作業の履歴（`staff`）は、清掃などの作業だけを数える。職員による支援は `care` に出る。

## 追加したテスト

### `integration/test_project_evidence_routes.py`（19件）

モジュール単位の準備で、上のRunを1回だけ作ります。

- 索引にある履歴の全種類が、両方の分岐で、それぞれの時間の意味（KPIは `end_of_tick`、ほかは `recorded_event_minute`）で答える。
- KPIの履歴は、計算済みの各分に1行ずつ（10〜59分。60分のtickはまだ実行していない）。
- 分岐より前と、計算済みの範囲より後の履歴は `history_outside_computed_range` で拒否される。
- 人と世帯の履歴は、指定した分（10・35・60分）を正確に復元する。世帯は、同じ世帯の全員を返す。
- 同じRunの2つの分岐の比較では、seed・モデル・設定・初期条件がすべて一致する。
- KPIの最初の差は分岐の時刻（10分）に出る。違うのはトイレの稼働数だけで、差は足した2台。
- worldとpersonの最初の差は、分岐の時刻以降に出る。
- 条件の差は、承認した介入（`/approved_commands`）の1件だけ。

### `integration/test_project_experiments.py`（3件）

生成Scenario（30分）を使います。

- 実験（2 seed × 2変種）
  - 各cellを準備・実行・収集し、評価に取り込む。
  - 収集した指標は最後のtick（29分）のもの。
  - 評価のRunには、変種ごとのqueueのPolicyが記録される。
  - 比較は base と fifo の対になる。
- 校正：`fit` が観測値に近い変種を選び、点数が手計算と一致する。
- 再実行したRunが、元のRunと同じworldを再現する。
