## 概要

5倍高速化（100人・7日分を画面から計算）の4つ目です。保存のたびの完全な検証（#220）で、EventLog（7日目で約27万件）を読む量を減らします。確かめる範囲は変えません。

これまでの完全な検証は、運営イベント・介入・環境・インフラのどれも、EventLog の全件をなめ、ID の辞書を作り直していました。7日目の世界で、完全な検証は1回 735 ms かかっていました。

## 変更

- **EventLog の索引（`events/queue.py`）：** 記録を足すときに、次の2つの索引も作ります。
  - イベントの種類ごとの記録（`of_types`、追加順を保ちます）
  - 来歴（provenance）にオブジェクトを持つキーごとの記録（`with_provenance_object`、介入の印 `effect_program_v1` 用）
- **`EventsById`：** 待ちのイベントと実現済みのイベントを ID で引く窓口です。EventLog を写さず、その ID 索引で引きます。これまでの辞書と同じく、実現済みのイベントが優先されます。
- **4つの検証（`domain/operational.py`、`events/effects.py`、`domain/environment.py`、`domain/infrastructure.py`）：**
  - 確かめる種類（または介入の印を持つ記録）だけを読みます。ほかの種類の記録は、これらの確認を素通りするだけでした。
  - ID による参照は `EventsById` で、実現の状態は `EventLog.find` で引きます。
- **EventLog 自体の監査（`EventLog.validate`、ID と順序番号の重複、実現時刻）：**
  - 前の監査で確かめた記録が、先頭に同じオブジェクトのまま残っていれば、増えた記録だけを確かめます。そのとき、増えた記録が ID 索引の指す記録であること、索引の数が記録の数と合うことも確かめます。記録は凍結されていて、追記しかされないためです。
  - 先頭の記録が差し替わっていた場合、前より早い時刻での監査だった場合、期間が違う場合は、全体を確かめ直します。
  - `WorldState.validate` は、監査の後に、待ちのイベントとの重複や最大の順序番号を索引で確かめます（毎 tick の検証と同じ読み方です）。
- **運営の記録とイベントの照合（`_event_payload_matches`）：** イベント全体（payload と来歴）ではなく、payload だけを JSON の形に戻して比べます（`ScheduledEvent.payload_dict`）。
- **変えないもの：** 確かめる内容・誤りのメッセージ・数式・係数・乱数・tick の順序。
