## 概要
`docs/testing.md` に「テストの地図」を追加しました。`tests/` の全テストファイル104本（直下103本と `tests/integration/` の1本）と、そこに含まれるテスト896件を分類しています。コードとテストは変えていません。

分類の軸は次のとおりです。
- **範囲**：単体・統合・e2e。テスト1件ごとに実行時の記録から決めました。
- **手で時刻**：`TickEngine` を使わず、テスト自身で時刻を動かす単体テストの件数。
- **担当**：主に確かめているモジュール。
- **目的**：結果・契約・画面。範囲とは別の印として付けました。
- **Scenarioの出どころ**：fixtureか生成Scenarioかなど。

あわせて、実態と合っていなかった「各packageに隣接するtest fileを参照」を直しました。別のPCでの所要時間も追記しています。

## 分類の方法
全件のoffline実行中に、テスト1件ごとに次の呼び出しを記録しました。
- `TickEngine.step`
- HTTPの入口：`_dispatch_api` と、request handlerの `do_GET`・`do_POST`
- CLIの入口：`sheltersim.cli.main` と、`sheltersim` を起動する子プロセス
- `EventDispatcher.dispatch_due`
- `ScenarioSpec.load`、`InitialScenarioBuilder.build`、`WorldState.from_scenario`

fixtureの準備中に起きた呼び出しは、そのfixtureを使う各テストに数えています。記録用のpytest pluginは一時領域で使っただけで、リポジトリには入れていません。担当と目的は、テスト名と本体を読んで判断しました。

## 主な発見（詳細は文書の「見えた穴」）
- 896件の内訳は、単体677・統合199・e2e 20でした。104本中57本のファイルが2つ以上の範囲を含みます。
- 22本のファイルにある126件の単体テストが、`TickEngine` を通さず、テスト自身で時刻を動かしてイベントを処理させています。比較KPIのテストの中には、イベント記録を手で書き込んでいるものもあります。
- e2eはすべてfixtureのScenarioを使います。Project画面の主な流れ（生成 → 承認 → 実行 → 介入 → 表示）をHTTPから通すテストはありません。
- 生成Scenarioを使い、介入して結果を本線と比べるテストは、トイレ追加だけです。
- experiments、storage、eventsの主担当ファイルは、生成Scenarioを実行しません。
- `regression-contract.json` が固定しているのはfixtureの2本だけです。生成Scenarioのテストは遅いのに、`long_simulation` の印がありません。

#59 は、この地図に合わせて本文を範囲（単体・統合・e2e）ベースに更新しました。ライブテストを `tests/integration/` から移すこと、時刻を手で動かすテストの扱いも加えています。#60 の「対象の介入の一覧」は、この地図では洗い出していません。
