## 元の本文

保存済みCheckpointの読込で、展開した文書のコピーと、2回目の復元をなくします。#46 の前半（保存境界以外の時刻の表示、`seek`）の一部です。

## 修正前

`ProjectStore.load_checkpoint` は、ファイルやchunkから展開したばかりの文書を `deepcopy` してから、検証のために WorldState を復元し、その世界を捨てていました。そのあと `seek` と `advance` は、`BranchRuntime.from_checkpoint` で同じ Checkpoint をもう一度復元していました。

## 変更

- `Checkpoint._load()` は、呼び出し側が渡した文書をコピーせずに Checkpoint にし、検証で復元した世界と指標も返します。`from_dict()` はこれまでどおり文書をコピーしてから `_load()` を呼びます。
- `CheckpointArchive.decode_restored()` と `ProjectStore.load_restored_checkpoint()` / `load_restored_branch()` を追加しました。展開した文書は chunk ごと・ファイルごとに新しく解析したもので、ほかと共有していません。`load_checkpoint()` と `load_branch()` もこれを通ります。
- `TimelineStore.seek` と `_advance_locked` は、読込の検証で復元した世界と指標から実行を続けます（`BranchRuntime.from_checkpoint(..., _restored=...)`、PR #222 で追加）。

## 結果（ローカル、WSL2、1回ずつ）

100人・生成Scenarioを ProjectAPI 経路で1440分まで計算した Project で、介入なしの分岐を1回実行しました（分岐元を `seek` で復元します）。

| 分岐する時刻 | develop `8d1d203` | このPR | うち `seek` |
|---|---:|---:|---|
| 1440分 | 29.8秒 | 25.4秒 | 8.6秒 → 4.2秒 |
| 720分 | 13.6秒 | 11.6秒 | 3.8秒 → 1.9秒 |

応答、`fork_origin`、子branchの保存 Checkpoint のハッシュは develop と一致しました。計算の続き（`advance`）の開始時にも、同じだけ（1440分時点で約4秒）短くなる見込みです。

## テスト

- `tests/unit/storage/test_checkpoints.py`: 保存済み Checkpoint の読込と実行の準備で、WorldState の復元が1回だけであること。読み込んだ Checkpoint が従来の読込と同じで、復元した世界と指標を変えても Checkpoint が変わらないこと。わざと2回復元する実装で失敗することを確かめました。
- `tests/integration/test_resume_checkpoint_loads.py`: 計算の開始時に head Checkpoint の検証が1回だけになったこと（これまでは「読込時の1回と実行用の復元の1回」の2回を固定していました）。
- 読込の回数を数えるテスト用の仕組み（`no_checkpoint_decode` fixture、`test_project_queries.py` の確認）は、すべての読込が通る `load_restored_checkpoint` を数えるようにしました。`load_checkpoint` だけを数えると、新しい入口を通る読込を見逃すためです。
- offline全体テスト（ローカル）: `SHELTERSIM_LLM_MODE=offline .venv/bin/python -m pytest -n auto` が 1274 passed、4 skipped。`ruff check` と `ruff format --check` も通っています。PRではCIが動かないため、結果はすべてローカルのものです。
