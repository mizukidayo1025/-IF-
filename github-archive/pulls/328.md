## 元の本文

## 概要
イベントの記録（EventLog）と予定の列（EventQueue）の正本を Rust に移します（`state/events.rs`、`eventlog.rs`、`records.rs`）。記録は追記のときに正準の byte 列にします。Rust から予定を入れる `EventWriter` も入ります（レーン F の準備）。詳細は `docs/rust-port/lanes/e-events.md` にあります。

## 判断したこと
**保存時に記録を解析し直す確認を外します。** 実験の結果、外して変わるのは「見つかる時点」だけでした。
- 今の確認は不一致で保存を止めず、`restored.validate()` が通れば保存します。この検証は読み込みでも動きます。
- 書き手をわざと壊すと、確認の有無にかかわらず同じものが見つかり、同じものが通ります（全記録の小数・文字列・整数・キー順は検出。`detail` と、1種類だけの payload の15通り中12通りは、どちらでも通ります）。
- 通るものを止めているのは開発時の確認です。`social_interaction` の小数の最後の1桁だけを壊すと、ゲートで問題58件、pytest で24件失敗しました。
- 得られるもの：7日分の実時間で 8〜23 秒（組2つの比較）。

**library 経路のメモリ増を当面受け入れます。** 保存しない経路でピーク RSS が 2,470 → 2,820 MB（+14.2%）、CPU が 4〜5% 増えます。記録の byte 列（329 MB）を持つためで、project 経路の RSS は増えません。Python の記録がなくなれば解消する見込みなので、タグごとに測り直します。解消しなければ、最初の保存まで byte 列を書かないようにします。

速さだけならほぼ差がありません。このレーンの価値は、Rust の列と `EventWriter` です。
