## 元の本文

## 背景

ランダムに作った生成Scenario（初期Scenario生成器）をofflineで実行する確認で、30件中3件が、Scenarioの生成中に次のエラーで止まりました。

```
pydantic ValidationError: 1 validation error for ScenarioSpec
  Value error, event 'region-condition-002-water_restored' references no prior water outage
```

3件とも、運営条件（`operational_conditions.scheduled`）に断水（`water_outage`）が入っていました。

## 原因

`src/sheltersim/region/conditions.py`の`add_event`は、`PlannedEventSpec`に`causation_id`を設定していませんでした。一方、`ScenarioSpec`の検証（`src/sheltersim/experiments/scenario.py`）は、`water_restored`の`causation_id`が対応する`water_outage`イベントのIDと一致することを要求しています。運用状態の検証（`src/sheltersim/domain/operational.py`）も同じ対応を確かめます。

このため、運営条件で断水を入れると、他の条件にかかわらず、Scenarioの生成が必ず`ValidationError`で失敗していました。承認ブロッカーとしては表示されず、例外として落ちます。

## 変更内容

- `add_event`に任意の`causation_id`引数を追加しました。
- 断水条件の`water_restored`には、直前に作った`water_outage`イベントのID（`region-condition-NNN-water_outage`）を渡します。
- 他の条件で作るイベントは変えていません（`causation_id`は`None`のまま）。

## 互換性

- Checkpointとartifactの形式は変えていません。
- これまで断水条件を含むScenarioは生成できなかったので、既存の保存済みScenarioやRunには影響しません。

## テスト

- `tests/test_region_water_outage_conditions.py`を追加しました（2件）。
  - 繰り返しのある断水条件で、各`water_restored`の`causation_id`が同じ`outage_id`を持つ前の`water_outage`を指すこと。
  - 断水条件を含む生成Scenario（12人・半日）が最後まで実行でき、断水と復旧の両方のイベントが適用されること。約13秒かかります。
- 修正を外すと、2件とも失敗することを確認しました。
- 失敗した3件の入力を修正後に再実行すると、例外ではなく、それぞれ別の条件による承認ブロッカー（トイレへの断水指定、終了後の復旧時刻など）として返りました。
