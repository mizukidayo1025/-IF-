支援を要請中の人を再会させると、シミュレーションが例外で止まる不具合を直します。係数は変えていません。

## 原因

支援の要請は「人・世帯・支援の種類」で同一性を確かめます（`record_shared_operation`）。再会は、`population_presence_v1` 上でその人の世帯を変えます。

要請の段階ごとの記録で、世帯の取り方がそろっていませんでした。

| 段階 | 記録した処理 | 直す前の世帯 |
|---|---|---|
| 要請（requested） | `runner.py` | その時点の世帯 |
| 割当（assigned）・開始（started） | `runner.py`（2か所） | **その時点の世帯を計算し直す** |
| 中断（interrupted、時間切れ） | `runner.py` | **その時点の世帯を計算し直す** |
| 開始（started、職員の到着） | `runner.py` | **その時点の世帯を計算し直す** |
| 完了（completed） | `events/handlers.py` | 要請に記録された世帯 |

そのため、要請の途中で再会があると、割当の記録で世帯が食い違い、例外になっていました。

## 変更

Issueの直し方の候補のうち、「開いている要請は、要請したときの世帯のまま完了させる」を選びました。家族の再会は、誰かが支援を待っていても妨げるべきではないためです。完了の記録がすでにこの扱いだったので、それに合わせる形になります。

- `experiments/runner.py`：割当・開始・中断の4か所で、`current_household_id(...)` の代わりに、要請に記録された世帯（`prior["household_id"]`）を使う。
- 要請の段階は今までどおり、その時点の世帯で記録する。したがって、再会のあとの新しい要請は新しい世帯になる。

世帯が要請の途中で変わらないRunでは、両者は同じ値です。そのため、結果は変わりません（回帰の契約のテストも通る）。

## 確かめた結果

Issueの再現（生成Scenario、10分に A001 と A006 を A001 の世帯で再会）では、120分まで止まらずに進みました。A006 の要請は、要請（0分）・割当（50分）・開始（52分）・完了（62分）のすべてが、要請したときの世帯 H000003 で記録されます。在所の記録の世帯は、再会後の H000001 になります。

## テスト

`integration/test_population_presence.py` の #179 のテストの `xfail` を外し、`test_a_reunion_keeps_an_open_support_request_in_its_household` に書き換えました。次を確かめます。

- 再会した人の在所の世帯は、新しい世帯になる。
- 開いていた要請が、再会のあとも職員に割り当てられて進む（要請と割当の両方が記録される）。
- その要請の記録は、すべて要請したときの世帯のまま。

直す前のコードでは、このテストが `support request identity changed during its lifecycle` で失敗することを確かめました。

計画の段階での拒否はもう受け入れないので、`BranchError` を許す分岐は外しました。
