## 元の本文

#48 の段階3のバックエンドです。同じ Run の複数の branch を、同時に計算・分岐できるようにします。決めたことは #48 の設計案のとおりです。

- 書き込み権は「占有ロックだけで組む案」です。Windows も対応環境に含めます。
- 状態は「branch ごとの状態を足し、Run の状態は要約として残す案」（案A）です。
- 同時に計算する本数の上限は、Run と branch を合わせた全体で共有します。
- 計算中のほかの branch があっても、分岐を許します。
- レポートと LLM の予算は、今の仕組みのまま受け入れます。
- Demo は対象外です。

画面（Project 画面）の対応は、別の PR にします。

## 変更

### 書き込み権（`storage/projects.py`）
- `claim_branch(project, run, branch)`（新規）：branch の書き込み権です。
  1. Run の入口のロック（`runs/{run}/worker-lock`）を一瞬だけ取る
  2. branch のロック（`branches/{branch}/worker-lock`）を取る
  3. 入口を外す

  違う branch の書き込みは、同時に動けます。
- `claim_run(project, run)`：Run 全体の操作（Run の削除、履歴索引の作り直し、回復）に使います。入口のロックを持ち続けたうえで、すべての branch のロックが空いていることを確かめます。どれかが書かれていれば `run_worker_busy` で断ります。
- 占有ロックだけを使うので、Linux・macOS（`flock`）と Windows（`msvcrt.locking`）で同じ組み方です。ロックの取り方は `_lock_without_waiting` にまとめました。

### 状態（保存データの追加）
- branch ごとに `runs/{run}/branches/{branch}/status.json`（`schema_version: 1`、`status`）を記録します。`set_branch_status`・`branch_status` で読み書きします。
- Run の `status.json` は要約にします（`settle_run_status`）。どれかの branch が計算中なら `running`、そうでなければ最後に止まった branch の状態です。分岐のあとは、分岐の前の状態に戻します。
- Run の参照の `branches` の各要素に、記録があればその branch の `status` が付きます。この記録より前に計算した branch には付きません。既存のデータは読み替えず、記録がない branch として扱います。
- 回復（`recover_interrupted`）：
  - 計算中のまま書き込み権を持つプロセスがいない branch は、`interrupted` にします。
  - 分岐の途中でプロセスが終わり、子 branch が作られなかった場合は、子の状態の記録を消します。残すと、Run がずっと `running` になるためです。
  - branch の状態の記録がない古い Run は、これまでどおり Run 単位で回復します。

### サーバーと計算（`web/projects.py`、`web/worker_process.py` ほか）
- `ProjectAPI` の job は、Run と branch の組ごとに持ちます。分岐の job は、作る子 branch の名前で持ちます。
  - 同じ branch の計算は、1つずつです。
  - 同じ Run のほかの branch や、ほかの Run は、上限（`--max-parallel-runs`、既定2）まで同時に動きます。
- 分岐は、元の branch が計算中のときだけ断ります。
- 取消し（`POST …/cancel`）は、`branch_id` を渡すとその branch だけを止めます。渡さなければ、その Run のすべての計算を止めます。
- 計算・分岐の worker プロセス、スレッド方式、`TimelineStore.advance`、CLI の再開は、branch の書き込み権を取り、branch の状態を記録します。
- 履歴索引に書く接続は、ほかの branch の書き込みを最大120秒まで待ちます（これまでは10秒）。分岐で親の行をまとめて写す間も待てるようにするためです。

## 結果（ローカル、WSL2）

同じ Run の2本の branch（1200分の main と、1200分で分岐した child）を、ProjectAPI の別プロセス方式で1440分まで計算しました（2回ずつ）。

| 上限 | 2本の計算が終わるまで |
|---|---|
| 1（順番） | 41.3 / 39.9秒 |
| 2（同時） | 21.4 / 22.0秒 |

両方の head の Checkpoint のハッシュは、順番でも同時でも同じでした。
