フォームで入れた施設の停止・設備の故障・停電が、その時刻に使用中だと失敗し、最後まで効かなかった不具合を直します。相談のとおり、案C（すぐ止め、今の人は使い終わる）で直します。係数は変えていません。

## 変更

停止は、予定の時刻に稼働数を下げます。その時刻にサービスを受けている人は使い終わるまで続け、止まった台では新しいサービスを始めません。

- `events/handlers.py`
  - 施設の停止（`FacilityOutageHandler`）：使用中の人数を確かめて失敗させる検査をやめた。
  - インフラの停止（`_recalculate_infrastructure_capacity`。設備の故障・停電）：同じ検査をやめた。
- `core/world.py`：状態の検証の不変条件を「使用中 ≤ 稼働数」から「使用中 ≤ 設置数」に緩めた。トイレと、水・食料の配布所の両方。使い終わるまでの間、使用中の人数が稼働数を上回るため。

介入（EffectProgram）と分岐のコマンドで稼働数を下げる場合は、今までどおり計画の段階で使用中の人数を確かめます（そのときの状態が分かるため）。

## 不変条件を緩めてよい理由（点検の結果）

新しいサービスを始めるかの判定は、どれも「使用中が稼働数（から決まる上限）より少ないときだけ始める」形でした。使用中が稼働数を上回っても、新しいサービスは始まりません。

- トイレ：`domain/facilities.py` の201行、313行
- 配布所：`domain/resource_service.py` の220行、378行

稼働数で割る計算は、検証スクリプトの稼働率だけで、0除算を避け、1を上限にしています。指標と画面は、使用中の人数と稼働数を別々に持ち、割り算をしていません。

## 確かめた結果

生成Scenarioで、`toilet_01` に10〜40分の停止を入れました（10分に A012 が使用中）。

| 分 | 稼働数 | 使用中 |
|---|---|---|
| 10 | 1 | A012 |
| 11〜12 | 0 | A012（使い終わるまで続ける） |
| 13〜40 | 0 | なし（新しく使い始める人はいない） |
| 41 | 1 | なし（復旧） |

- 停止と復旧のイベントは、どちらも「適用」になった。
- 設備の故障（`equipment_failure`）でも同じ結果だった。
- 使用中の人数が稼働数を上回る11分のCheckpointから再開しても、続けて実行したのと同じworldになる。
