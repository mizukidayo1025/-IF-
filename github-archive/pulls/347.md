## 概要

手順 4 の計画を `docs/rust-port/step4-plan.md` に入れ、kernel の拒否を実測する道具を足しました。規則は動かしていないので、結果は変わりません。

**一番大きい発見：** `Unsupported` の 1,854 か所のうち、**1,360 か所は全テスト、ゲート、7 日間のどれでも一度も作られませんでした。** 手順 4 でエラー文を移すときに比べる相手がないので、テストを書く仕事が中心になります。

## 内容

- `docs/rust-port/step4-plan.md`：棚卸し、決定、実測、レーン L0〜L14
- `docs/rust-port/step4-refusal-sites.md`：一度も届かない全か所
- `docs/rust-port/lanes/l0-refusals.md`
- `benchmarks/rule_shadow/refusal_census.py`、`native/src/core/census.rs`、`tests/integration/test_refusal_census.py`
- `Unsupported` を `lib.rs` の型 1 つにしました。`#[track_caller]` で行を数えるので、これから足す拒否も自動で数えます。Python から見た例外のクラスは同じです。

## 拒否の内訳

| 区分 | か所 |
|---|--:|
| Run（ゲートか 7 日間で届く） | 36 |
| Run（判定のみ） | 8 |

| テスト・直接 | 153 |
| 示せず | 265 |
| 印（patch やシャドーへの拒否） | 25 |

7 日間の拒否は 724 回で、そのうち 718 回が職員の割り当てです（`a free worker can take a request` 712 など）。上位の表は計画の文書にあります。

計測ありで失敗する 1 件は `test_a_registered_kernel_is_used_and_can_turn_the_state_down` です。`validate` の確認が登録した検証をもう 1 回呼ぶためと見ています。確認なしの計測では通り、計測なしでも通ります。

計測の数え漏れは、`or_rule!` の合計と driver 自身の数（ゲート 6,280、7 日間 720、テスト 55,924）、`after_tick.stats()` のゲート 1,296 回で確かめました。

## 分かっている弱点

- **「一度も届かない」は「有効な状態から届かない」ではありません。** たとえば `a policy value is not an int` は、有効な Scenario でも書かれていないだけで 0 回です。
- 「テスト・tick」と「テスト・直接」は上限です。テスト自身のソースしか読まず、fixture の中は見えません。「示せず」は証明ではありません。
- 表の数は、この commit に `rust/m6-handlers-rest` を試しにマージした木で数えました。そのマージは公開していません。
- 3 節以降の行数などは棚卸しの木のままで、#346 を含めて数え直していません。
- `the namespace has no row` がどの名前空間かは分かりません。kill された worker の分と、`PYTHONPATH` を消す子プロセスの分は数えられません。
- `Unsupported` の型の変更は、他の OS では CI で初めて通ります。
