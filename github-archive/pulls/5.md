## 背景

#4 でシミュレーション中のAI呼出しを直したあと、初期条件の入力側（準備stage）を確認しました。live（30人・1日）で4つの呼出しがすべて失敗していました。

| 呼出し | 修正前の結果 |
|---|---|
| CLI 初期ニーズ生成（`prepare --generate-initial-needs`） | コマンドがエラーで停止（`thinking_without_text`） |
| CLI シナリオ下書き（`prepare --generate-scenario`） | 出力上限で切れ、警告なしでルールの下書きになる |
| Web 自由文の読み取り | schema検証で必ず不合格になり、明示された値だけを使用 |
| Web 地域情報の検索 | 候補なし（`thinking_without_text`） |

さらに、この確認中の地域検索がPC全体で共有する累積上限の利用記録（`task-global-v1`）を凍結させ、以後すべての有料呼出しが拒否される状態になりました。

## 変更内容

1. **Opusのthinking**：`src/sheltersim/llm/provider.py`
   - Opus 5.5はthinkingを無効にできず、thinkingのtokenは`max_tokens`に含まれます。
   - runtime以外の呼出しでは、各taskの回答上限に**thinking用の余裕4,096 token**を足して要求し、その費用も予約します。
   - 準備stageの呼出しには`output_config.effort: "low"`を指定します。
   - taskの`max_output_tokens`（回答の大きさ）は変えないので、記録済みの応答（tape）の照合キーは変わりません。
2. **回答上限の見直し**：初期ニーズを`人数×24`から`人数×48+256`へ、シナリオ下書きを`人数×72+256`から`人数×128+512`へ変更しました（実測した1人あたりの出力量に基づく）。
3. **schema検証**：`src/sheltersim/llm/contracts.py`
   - Pydanticが生成するschemaの構文に対応しました（`$ref`/`$defs`、`oneOf`、`const`、schemaとして与えた`additionalProperties`、`exclusiveMinimum`/`exclusiveMaximum`、`minLength`、`pattern`）。
   - 以前は`$ref`を解決できず、Web自由文の読み取りでは応答の内容にかかわらず必ず不合格になっていました（コード自身のfallbackも不合格でした）。
   - schemaにない項目は、従来どおり拒否します。
4. **server toolの予約**：web searchを使う呼出しでは、APIが検索の前後でモデルを複数回実行し、`usage.output_tokens`はその合計で返ります。予約を「`max_tokens`×（検索回数＋1）」に変更しました（routerの予算確認と、利用記録への予約の両方）。新しい利用枠の出力token上限にも、thinking用の余裕を含めました。
5. **凍結の解除コマンド**：`sheltersim usage --unfreeze ID --confirm ID --reason TEXT`
   - 対象は`task-global-v1`、`cli-*`、`legacy_demo`の利用記録です。
   - 確認入力（IDの再入力）と理由を必須とし、未決着の予約が残っている間は解除できません。
   - 変更するのは凍結フラグだけで、記録済みの利用量は残します。
   - 利用記録の形式は**v1のまま**です。PC全体で共有する記録なので、古い版のShelterSimからも読めるようにしています。解除の記録は別ファイル（`usage-audit/<account>.json`）に残し、usage summaryの`unfreeze_events`に表示します。
6. **警告**：`prepare`がfallbackしたときにstderrへ警告を出します。Webの自由文読み取りは、既存の処理ですでに警告が出ていました。router側のfallback時にも同じ警告を追加しています。

## 互換性・影響

- Opus呼出し1回の事前予約額は、既定設定で約$0.2〜0.4に増えます（実際の請求額は変わりません）。runの予算がこれより小さいと、Opusの呼出しは`budget_exceeded`でfallbackします。
- 既存の利用枠の上限は、作成時の値のまま変わりません。
- runtime（Haiku）の呼出しは変更していません。offline Runの結果も変わりません。
- 100人規模のシナリオ下書きは、回答が既定の出力上限（8,192 token）を超える見込みです。`SHELTERSIM_LLM_MAX_OUTPUT_TOKENS`を上げる必要があります（文書に記載）。
- 予約額の増加に合わせて、既存テスト6件の予算・上限値を広げました。各テストの確認内容は変えていません。
