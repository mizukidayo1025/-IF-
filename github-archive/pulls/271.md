## 元の本文

#48 の段階2です。Web サーバーで、異なる Run の計算と分岐を同時に行えるようにします。

## 変更

- `ProjectAPI`：サーバー全体で1つだった job（`_active`・`_cancel`・`_watcher`）を、Run ごとの job の表（`_jobs`）にしました。
  - 同じ Run の計算・分岐・削除は、これまでどおり1つずつです（Run の書き込み権のとおり）。
  - 異なる Run は、上限（`max_jobs`）まで同時に受け付けます。上限に達しているときの要求（計算・分岐）は、`background workers are busy` で断ります。
  - 取消し（`POST …/cancel`）は、その Run の job だけを止めます。
  - ほかの Run が計算中でも、計算していない Run の分岐はできます。
  - `wait_idle` と `close` は、すべての job を待ちます。
  - テストと CLI のスレッド方式（`worker="thread"`）は、これまでどおり1本です。スレッドは GIL を共有するので、同時に動かしても速くなりません。
- `serve_inspector(max_parallel_runs=2)` と `sheltersim web --max-parallel-runs N`（既定2、1以上の整数）を足しました。
- `docs/architecture.md` と `docs/demo-guide.md` に追記しました。計算1本で、1日分の Run（100人）なら約0.5〜0.9 GB のメモリを使います。そのため、上限は CPU の数ではなくメモリに合わせて決めるよう書いています。

保存データの形式は変えていません。同じ Run の複数の branch を同時に計算するには、書き込み権と Run の状態を branch ごとにする必要があります。こちらは段階3として、#48 の設計案で相談中です。

## 結果（ローカル、WSL2・16コア）

生成Scenario（100人）の2つの Run を、それぞれ0分から360分まで計算しました（ProjectAPI の別プロセス方式、2回ずつ）。

| 上限 | 2つの Run の計算が終わるまで |
|---|---|
| 1（順番） | 29.5 / 31.9秒 |
| 2（同時） | 15.4 / 17.0秒 |

両方の Run の head の Checkpoint のハッシュは、どちらの場合も同じでした（`717ab2b289d3`）。

## テスト

- `tests/integration/test_process_worker.py`（追加分）
  - 上限2では、2つの Run が同時に running になり、それぞれ別のプロセスで計算され、同じ head になること。
  - 上限1では、ほかの Run の計算中に、別の Run の計算と分岐を `workers are busy` で断り、状態を変えないこと。
  - 計算中の Run の分岐は断るが、ほかの Run の分岐はできること。
  - 計算中の Run の取消しは、その Run だけを止めること。
- `sheltersim web --max-parallel-runs 0` は、引数の検証で断ります。
