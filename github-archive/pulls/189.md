## 元の本文

Refs #178

イベントの処理（`events/handlers.py`）のうち、利用者の経路から届く処理を、生成ScenarioのRunで確かめるテストを足します。調べる途中で不具合が2つ見つかったので、それぞれIssueにし、`xfail(strict=True)` のテストとして置きます。コードは変えていません。

## 調べたこと

#176 の計測で通っていなかった行の多くは、壊れたpayloadを拒否する防御的な検査でした（不正な値で `EventApplicationError` を出す分岐）。私たちのコードが作るイベントへの改ざんの検査で、利用者の経路からは届きません。これらにテストを足すことはしていません。

利用者の経路として意味があるのは、次の2つでした。

- **近接接触のモデル**（`ProximityContactHandler`）：Project画面のフォームで選べる（`social_proximity_policy_id`）のに、テストが1つもなかった。
- **運営の条件**（施設の停止・復旧、職員の不在、断水）：Project画面のフォームで入れる。地域の調査をテストでは空の結果に置き換えているので、この経路を通っていなかった。

| 試したこと | 結果 |
|---|---|
| 近接接触のモデルを選んだ生成ScenarioのRun（Project） | **最初のCheckpointの保存で止まる（#187）** |
| 同じRunをCLI（`run_scenario`）で実行 | 進む（120分で接触の更新が597回、関係が318件）。ただし manifest の署名が `[REDACTED]` になる（#187） |
| 施設の停止の条件（`toilet_01`、10〜40分） | **10分に使用中だと失敗し、最後まで効かない（#188）** |
| 施設の停止と設備の故障を重ねる | 両方とも同じ理由で失敗（#188）。重なり自体を拒否するのは仕様 |
| 断水の条件（給水設備） | 正しく動く（既存のテストあり） |
| 断水の対象にトイレを指定 | previewで「既知の給水設備を指定してください」と止める（正しい） |
| 職員の不在の条件（繰り返しあり） | 正しく動く |
| 職員の自律的な作業中の不在 | 生成Scenarioの6時間で、自律的な作業（清掃・巡回）が一度も始まらず、届かなかった |

## 見つかった不具合

- **#187**：近接接触のモデルの署名 `distance-sampled-proximity-v1@1:state1:distance=1.5:…` が、保存の内容検査でメールアドレスとみなされる（「@」のあとに小数点がある）。伏せ字になるため、Checkpointの保存が拒否される。
- **#188**：フォームで入れた施設の停止・設備の故障は、その時刻に使用中だと失敗し、延期も再試行もされない。復旧も失敗する。previewは `can_start: true` のまま。生成Scenarioの施設はどれも1台なので、起きやすい。
