## 元の本文

## 概要

資源の台帳 `resource_ledger_v1` を Rust の行で持つようにしました。在庫の操作はその場で書くので、名前空間を丸ごと置き換える処理は tick からなくなりました。結果は変わりません。

`resource_service.py` と `care_receipts.py` の規則は Python に残しています。

詳細は `docs/rust-port/lanes/m4-resources.md` にあります。

## 移した処理

- 行：`native/src/state/resource_ledger.rs`。口座は型付きで、監査記録は1件ごとの正準バイト列です。資源ごとの最新の記録だけ型付きで持ちます。
- kernel：`native/src/rules/resources.rs` の `apply_operation`、`metric_values`、`reservation_id_was_used`。毎 tick の検証 `validate` は行のファイルにあります。
- 保存時の監査の再生は Python のままです。`core/world.py` が Python の検査を省くのは tick の経路だけです。

## Python に残した処理

| 処理 | 理由 |
|---|---|
| `arbitrate` | 大半が列の処理で、このレーンの開始時には未移植でした。#333、#334 で移せるようになりました |
| `complete`、`request` | 各 tick の約 0.5%。`arbitrate` と一緒に移します |
| `resource_service_v1` | 使う kernel がなく、持つと転送の費用だけ増えます |
| `care_receipt_for_request` | 1 回約 1 µs で、kernel 呼び出しのほうが高くつきます |
| ほかのケアの受領 | 費用は pydantic と `record_shared_operation` で、`common_operations` と一緒に移します |
| 保存時の再生、`care_history_by_agent`、エラー文 | tick の経路の外、または手順 4 の対象 |

## 分かっている弱点

- **7 日間のシャドーは台帳のものだけです。** 全シャドーの実行は、制限の 7,000 秒に分 9,570 で達して結果が残りませんでした。ゲートでは全シャドーを動かしました。
- **持ち続けた参照の動きが変わります。** `world.model_state[KEY]` を持ち続けると、これまでは古い値のままでしたが、今後は以後の操作が見えます。`src/` にそのような使い方はありませんでした（目視で、網羅的な走査ではありません）。
- **操作後の検査は kernel で省いています。** 前の検査から導けるという論証によるもので、kernel では実行しません。ランダムな操作列のテストと全シャドーの操作で裏づけています。
- ハッシュは監査のバイト列だけの変化を検出しません（シャドーは検出します）。`validate` の最新の記録の比較は、ゲートが正しい状態しか作らないため見えず、テスト 2 件で検出します。
- 7 日間の `release` と `loss`、`reservation_id_was_used` が `True` を返す場合、拒否の経路は、主にテストだけで確かめています（ゲートは `release` と `loss` を各 1 回通ります）。
- `dict.__setitem__` が木の節点に直接書くと行に届きません。T のレーンと同じ既知の穴です。
- RSS は測っていません。監査の記録 1 件につき行が約 400 バイト増えます。
- 既存のテスト 2 件（`test_resources.py`）は Python の規則の置き換えとメモを書いていたので、Python の規則を直接呼ぶように変えました。
- Linux 以外は CI に任せます。新しい C API はありません（`PyDict_DelItem` は #333 で入っています）。
- マージで、#333 と同じ処理の関数ができていたので `NamespaceMirror::remove_through` に統一しました。木にパスがないときのエラーは `Unsupported` から `RuntimeError` に変わります。行を書いた後に Python の規則へ戻ると二重に実行されるためです。
