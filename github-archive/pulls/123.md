## 元の本文

## 概要

給水所・配食所の提供地点ごとに独立した列があり、容量が提供地点の数より少ない場合に、状態の検証でシミュレーションが止まる不具合を直しました。

Closes #118

## 原因

- 独立した列では、列ごとに先頭が止まった理由を記録します。
- 一方、`WorldState.validate` は、止まった記録が施設全体の列の先頭を指すことだけを認めていました。そのため、2本目の列の先頭が記録されると止まっていました。

## もう1つ見つかったこと

検証をゆるめて調べたところ、2本の列が同時に待っている間、施設の停止記録が分ごとに2人の間で入れ替わっていました。#118 の再現条件では、待っている人は2人なのに、停止の履歴が8件になっていました。

- 停止の履歴（`queue_stall_history`）に同じ待ちが何度も記録されます。
- 停止の理由ごとの回数（`resource_service_wait_*_count`）も数え直されます。断水と在庫不足の回数は KPI（`water_outage_stall_count`、`resource_stock_stall_count`）に出ます。

## 変更

- **検証と古い記録の掃除**：独立した列がある施設では、どの列の先頭を記録していても認めます。施設の列の先頭を返す `queue_head_agent_ids` を `domain/facility_queues.py` に足し、`core/world.py` と `domain/queueing.py` で使います。
- **施設の停止記録**：独立した列の判定を1回終えてから、施設の記録を1件だけ決めます。
  - 記録中の Agent が同じ理由で待ち続けていれば、そのままにします。
  - そうでなければ、列IDの順で最初に止まった列の先頭を記録します。
  - 列ごとの停止は、これまでどおり `facility_queues_v1` の各列の `last_stall` に残ります。
- 保存する状態の形は変えていません。スキーマ版の更新や移行は要りません。
- 生成Scenarioは施設ごとに提供地点を1つしか作らないので、画面から作った Scenario の結果は変わりません。固定済みの結果（`generated_small` など）も一致しています。

## テスト

- `tests/integration/test_facility_queues.py`：#118 の xfail を外しました。容量1・提供地点2で20分進め、3人とも給水を受けることを確かめます。停止の履歴が待った2人について1件ずつ（A003、A002）であることと、容量待ちの回数が2であることも確かめます。
  - 3人目の給水は17分目に終わるため、進める時間を16分から20分にしました。
- `tests/unit/core/test_world.py`：2本目の列の先頭を指す記録は検証を通り、列の先頭でない人を指す記録は拒否されることを確かめます。
- 3人を施設の区画に立たせる準備を、`tests/conftest.py` の fixture `place_three_at_facility` にしました。統合テストのファイルから移したもので、単体テストからも使うためです。
