## 元の本文

## 概要

M4 のうち、物理的な列の毎 tick の処理を3つの kernel にして Rust へ移しました（`native/src/rules/queues.rs`）。結果は変わりません。tick 全体が速くなったとは、この測定では言えません。

`facility_queues_v1` の状態と規則は **Python に残しました**。7 日間では呼び出しが 0 回で名前空間もなく、ゲートでも 31,532 tick のうち 600 tick だけです。手順 4 で Python の実装を消す前には移す必要があります。

詳細は `docs/rust-port/lanes/m4-queues.md` にあります。

## 移した処理と残した処理

| 規則 | 7 日間の呼び出し | ベース → レーン（µs/tick） | 判断 |
|---|---:|---|---|
| `prepare_facility_queue` | 90,720 | 47–64 → 22–24 | kernel |
| `progress_physical_queue_positions` | 18,556 | 46–58 → 21–22 | kernel |
| `progress_physical_queue_head_to_service` | 13,067 | 31–39 → 20–22 | kernel |
| `_schedule_queue_trip` | 9,335 | 上の値に含む | kernel の中へ |
| `shared_passage_edge_loads` | 10,080 | kernel にすると 13–17 → 89–123 | Python に残す |
| `physical_service_capacity` | 19,518 | kernel の効果は 1 µs 未満 | Python に残す |

`shared_passage_edge_loads` は、Python が予定したイベントごとに行を作るため、kernel のほうが遅くなりました。`request`、サービスの開始、`complete_toilet_service`、`_abandon_and_retry`、順序に依存する `_replan_physical_queue_trip` も Python に残ります。残りは cProfile 下で約 105 µs/tick（tick の 1.7%、`resource_service.py` を除く）です。

## 速度

予算（480 tick、3 回）：0.971（A/A 1.023、負荷 8–16）、0.968（A/A 1.030、負荷 3–5）。状態は同一です。差は A/A の揺れの範囲内です。

部品の合計では、3つの kernel で約 80 µs/tick 減り、Python に残した2つの規則が約 6 µs/tick 増えました。増えた原因は `pending()` が Rust の予定した行のオブジェクトを作るためと見ていますが、確認していません。

## 分かっている弱点

- **1% の変更はシャドーでもハッシュでも見えません。** `long_generated` で試した 8 種類（老化の重み、1 日の長さ、各上限、閾値、枠の許容差、枠の歩行距離）はすべて差 0 で、テストだけが検出します。生成された Scenario は既定値を設定に書き込み、重みは僅差の人にしか効かず、整数分への切り上げが残りを隠すためです。枠の歩行距離は最初はテストでも検出できなかったので、テストを足しました。シャドーが比較していること自体は、優先度の反転（差 940）と、あきらめる境界の 1 分のずれ（差 32）で確認しました。
- 7 日間のシャドーは、移動と列のシャドーだけを動かしました。全シャドーの実行は分 4,740 で止めています。ゲートでは全シャドーを動かしました。
- `--reversed-order` では Rust の行の順序は変わりません。タスクの順に読む2か所は、1 人が 1 タスクのときに安全だと、コードから判断しています。
- kernel は同梱の列のモデル ID を2つ認識し、`create_installed_model` を呼びません。`registry.py` が同じ ID の別定義の登録を拒否するので安全と見ています。
- ゲートのあきらめの拒否 167 件と記録 168 件の差は、`independent` FIFO の経路によると見ていますが、追跡していません。
- Linux 以外は CI に任せます。新しい C API はありません。
