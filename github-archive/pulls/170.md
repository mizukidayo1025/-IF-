## 元の本文

Closes #169

`policy_registry` がモデル一式（suite）だけで、領域ごとの指定を省いたScenarioがあります。こうしたScenarioでも、manifestとCheckpointに記録したモデルで実行するようにします。相談のとおり、実行時の解決を `selected_models` に揃えます。直す前に保存した「suiteだけ」のCheckpointは、再開を拒否します。モデルの係数は変えていません。

## 変更

### 実行時の解決（`policies/`）

次の3か所が `policy_registry` の個別のキーを直接読み、キーがないと昔の既定で動いていました。`selected_models` で解決するように直しました。

| 箇所 | 直す前（suiteだけのとき） | 直した後 |
|---|---|---|
| `relationships.py` の `create_relationship_policy` | `DurationOnlyTrustPolicy` | `distance-duration-repeat-trust-v1` |
| `queueing.py` の `create_queue_policy` | 図面なし：`StrictFIFOQueuePolicy` | `need-weighted-physical-queue-v1` |
| `behavior.py` の `WorldView.from_world`（誤情報の圧力） | `causal-stress-v1` とみなし、圧力0 | `mean-reverting-life-state-v1` として圧力を計算 |

`selected_models` は、個別の指定があればそれを返し、registry がなければ今までと同じ既定を返します。そのため、結果が変わるのは「suiteだけ」の registry を持つScenarioに限られます。例：旧UIのdemoの8プリセット、registry のない入力を `prepare` したもの。

`selected_models` の呼び出しは1回あたり約0.006 msです。

### Checkpointの署名（`contracts/policies.py`）

relationship・queue・psychology のどれかを省いたsuiteは、署名を `model_suite: <suite_id>@2` にしました。`@1` で記録したCheckpointは、既存の照合で「explicit migration required」として再開を拒否します。署名が同じまま、途中から別のモデルで進むことを防ぐためです。

- Project画面の「記録と実装の違い」には、`model_suite` の違いとして表示される
- 個別のキーをすべて書いたsuite（UIの生成Scenario）は `@1` のまま。動作も署名も変わらない

### 行動Policyの比較（`experiments/comparison.py`）

実行時が宣言どおりになったので、#157 で入れた「実行時に読まれる個別の指定」の比較をやめました。比べるのは、行動以外の宣言上のモデルと、registry のschema（3を2として扱う）です。

ただし、`application_version` は変更ごとには変わりません。そのため、個別の指定を省いているのに `model_suite@1` で記録されたRun（#169 より前に、昔の既定で動いたもの）は、はっきりしたエラーで拒否します。

  - `test_a_checkpoint_from_before_implicit_suite_selectors_ran_is_refused`：`@1` で記録したCheckpointの再開を拒否する

直す前のコードで失敗することを、部分ごとに確かめました。
- 実行時の修正を外す → `test_a_suite_runs_...` が失敗する。`behavior.py` だけを外しても、`assert 0.0 == 0.8` で失敗する

- `src/` をすべて戻す → e2e が `inputs differ` で失敗する
