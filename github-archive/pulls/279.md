## 元の本文

## 概要

5倍高速化（100人・7日分を画面から計算、約26分 → 約5分）の1つ目です。

Checkpoint の chunk を、保存1回につき1つの pack ファイルにまとめて書きます。これまでは chunk 1つを1ファイルにして、1つずつ fsync していました。7日分では、chunk のファイルが約6.5万個になり、保存1回で約200回 fsync していました。さらに、容量の計測のたびにそのファイルを全部数え直していて、これも日を追って重くなっていました。

## 変更

- **目録の版：** `checkpoint_archive_v3` を足しました（`storage/checkpoints.py`）。
  - 1回の保存で新しく増えた chunk を、`checkpoints/packs/{SHA-256}.pack` に書きます。
  - 目録の `locations` に、各 chunk の pack・開始位置・長さを記録します。`manifest_hash` は `locations` も含みます。
  - 読むときは、これまでどおり chunk ごとに名前の SHA-256 と照合します。
- **前の保存の chunk：** 書き直さず、場所を参照します。保存するときは、Branch の前の head（または同じ Checkpoint がすでにあればその目録）の `locations` と、同じ計算でそれまでに書いたすべての chunk の場所（`CanonicalEncoder.pack_locations`）を引き継ぎます。一度消えて後の保存で戻ってきた chunk も、書き直しません。
- **`locations` の形：** `{"packs": [pack 名…], "chunks": {chunk の SHA-256: [pack の番号, 開始位置, 長さ]}}`。pack 名を1回ずつ書きます。
- **古い Run：** v1/v2（1 chunk 1ファイル）の Run はそのまま読めます。続けて計算すると、既存の chunk ファイルを参照し、増えた分だけを pack に書きます。
- **変えないもの：** Checkpoint v1 の内容とハッシュ、保存間隔、fsync の対象（書いたファイルはすべて同期します）。
- **古いコードとの関係：** v3 の目録は、v3 に対応する前のコードでは `unsupported checkpoint archive version` になり、黙って読み違えることはありません。
- **書いたバイト数の記録：** `checkpoint-write-ledger` は pack のバイト数を数えます。台帳のない Run を数え直すときも、pack を含めます。
