## 元の本文

保存ごとのハッシュ計算で、巨大な履歴の byte 列を一度につなげずに、少しずつ hasher に渡します。

## 変更

- `CanonicalEncoder.digest`（`core/checkpoint_cache.py`）は、履歴キャッシュ（#44）が使い回す履歴（EventLog など）の項目のbyte列を、1つのbytesにつなげてからハッシュに渡していました。
- 1440分の EventLog では約45MBになり、Checkpoint の保存ごとに2回（`state_hash` と `checkpoint_hash`）作っていました。
- ハッシュをとるときだけ、512項目ずつつないで渡すようにしました（`parts(..., joined=False)`）。渡すbyte列の並びは同じなので、ハッシュは同じです。
- archive の chunk やサイズの計算など、ほかの使い方は変えていません。

## 結果（ローカル、WSL2）

- 1440分の世界でのハッシュ1回: 世界 96〜131ミリ秒 → 27〜39ミリ秒、本体 85〜122ミリ秒 → 30〜36ミリ秒
- 100人・生成Scenario・1440分・ProjectAPI経路: Checkpoint 作成の CPU時間 15.94秒 → 14.65秒
- world・events・metrics のハッシュと、保存された Checkpoint のファイル（manifest と chunk のすべて）は、develop の計算と byte 単位で同じでした。

## テスト

既存の `tests/unit/core/test_checkpoint_cache.py`（キャッシュの `digest` が文書全体の SHA-256 と同じであること）と、保存ごとに全体の変換と一致することを確かめる統合テストで確かめています。offline全体テスト（ローカル）: `SHELTERSIM_LLM_MODE=offline .venv/bin/python -m pytest -n auto` が 1286 passed、4 skipped。`ruff check` と `ruff format --check` も通っています。PRではCIが動かないため、結果はすべてローカルのものです。
