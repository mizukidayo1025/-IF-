## 変更

PR #268 で履歴索引を WAL 方式にしましたが、これを戻します（#269）。

- **WAL の取り消し**：#268 のマージ（`5b95fa2`）を `git revert` で取り消しました。コード・テスト・文書の変更をまとめて戻しています。
- **WAL のまま残った索引**：SQLite の journal mode はファイルに残るので、#268 の間に書き込まれた索引は WAL のままです。そこで、書き込みの接続で `PRAGMA journal_mode=DELETE` を実行し、従来の方式に戻します。ほかの接続が開いている間は SQLite がモードを変えないので、その次の書き込みで戻ります。従来の方式のファイルでは何もしません。
- `docs/project-persistence.md` に、従来のジャーナル方式で書くことと、戻した理由を書きました。

## 戻す理由（#269 の切り分け）

WSL2 上で、1日分の計算（100人・生成Scenario・1440分）の索引への登録を、保存ごとに分けて測りました。

| 版 | 回数 | commit の合計（遅くない回） | 遅い回（commit の合計） |
|---|---|---|---|
| WAL の前（`a0e3ff6`） | 15 | 2.3〜3.4秒 | 0 |
| WAL・`TRUNCATE`（#268） | 10 | 約5.4秒 | 4回（8.7〜15.7秒） |
| WAL・`RESTART` | 6 | 約5.6秒 | 3回 |
| WAL・`synchronous=NORMAL` | 6 | 約5.5秒 | 2回 |
| WAL・`RESTART`・ログの上限 64 MiB | 6 | 約5.5秒 | 3回 |

- WAL は同じページをログと本体に2回書きます。そのため、commit がいつも約2倍かかり、WSL では時々10〜15秒長くなります。書き戻しの方式や同期の設定では解消しませんでした。
- WAL を残す代わりに、分岐の間だけ SQLite のキャッシュを大きくして、分岐中の読み取りの待ちを減らす案も試しました。結果は次のとおりで、どちらも採用しませんでした。
  - 1 GiB：待ちは 0.7〜1.0秒になりましたが、分岐の子プロセスのピークRSS が 0.9 GB 増えました。
  - 256 MiB：待ちは 4.3〜4.4秒で、ほとんど減りませんでした。
- 戻すと、1440分の分岐の約17秒の間、frame の読み取りが最大5〜6秒待たされる状態に戻ります。その間も、Run の状態の確認と「分岐を作成しています…」の表示は続きます（#263）。

## 確認

- この PR で1日分の計算を2回測りました。commit の合計は 4.0 / 2.4秒、登録の CPU 時間は 15.2 / 15.0秒で、WAL の前と同じ水準です。world のハッシュも同じでした。
- `tests/unit/storage/test_history_index.py`：WAL 方式にした索引が、次の書き込みで従来の方式（`delete`）に戻り、`-wal` ファイルが残らず、書き込んだ行が読めること。戻す処理を外すと、このテストは `'wal' == 'delete'` で失敗します。
- offline全体テスト（ローカル）：`SHELTERSIM_LLM_MODE=offline .venv/bin/python -m pytest -n auto` が 1338 passed、4 skipped です。`ruff check` と `ruff format --check` も通っています。PR では CI が動かないため、結果はすべてローカルのものです。
