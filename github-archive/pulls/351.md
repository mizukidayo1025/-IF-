## 元の本文

## 概要

職員の割り当ての残りを Rust へ移しました。7 日間の kernel の拒否は 724 回から 6 回に減り、このレーンの拒否の理由はゲートと 7 日間で 0 回です。結果は変わらず、新しい係数はありません。

詳細は `docs/rust-port/lanes/l2-staff.md` にあります。

## 移した処理

- `assign_none` は拒否せず `None` を返し、手順を `assign_work` に渡します。
- `assign_operations` と `relief` に本体を入れました。行から計画し、記録を 1 件ずつ書きます。
- 経路による待ちの理由、`shared_passage_edge_loads`、`_active_route_edge_loads`
- 辺の容量がある `_route`。容量待ちは計画の間持ち、順序番号を `EventWriter` で予約するので、拒否しても二重に記録されません。
- driver が受領と苦情を直接呼びます。`_schedule_staff_support_travel` に kernel を足しました。
- 区域の `FxHashMap` のループを `BTreeMap` にしました。残る 2 つの `FxHashMap` は引くだけで、順に回しません。

| 理由（ゲート / 7 日間） | 前 | 後 |
|---|---:|---:|
| `a free worker can take a request` | 3,139 / 712 | 0 / 0 |
| `a qualified worker is free` | 2,313 / 4 | 0 / 0 |
| `a free worker can patrol` | 0 / 2 | 0 / 0 |
| `a staff member has a task` | 265 / 0 | 0 / 0 |
| `a free worker may repair` | 7 / 0 | 0 / 0 |
| 辺の容量 | 3 / 0 | 0 / 0 |

driver の `kernels_refused` はゲート 6,280 → 2,734、7 日間 720 → 6 です。残る 6 回は列 4（L4）、名前空間の行 1（L1）、その場で閉じる依頼 1（L3）です。

## 分かっている弱点

- **7 日間には職員の仕事の開始がありません。** ゲートでも開始 7 件、relief の予定 0 件、容量待ちの記録 0 件です。`preempt` はテストだけで、Scenario の優先度は Provider の境界からしか来ないのでゲートのシナリオを足していません。
- 7 日間の `assign_work` 712 回はシャドーで比較していません。ハッシュと、M6 の 3 日分の 315 回の比較だけです。
- 容量待ちの後の移動はトイレの経路でしかテストしていません。資源の経路はありません。
- 最後の native のビルドでは、ゲートで `staff` と `handlers_rest` のシャドーだけ動かしました（`1b294c4` の後の native の変更は、ゲートが通らない `preempt_worker` の呼び出しだけです）。
- 感度：14 通りの 1 行の変更はすべてテストが検出します（シナリオは絞りました）。4 通りは最初どれにも検出されなかったので、テストを足しました。係数の 1% の変更はハッシュにもシャドーにも届かず、テストだけが見ます。
- `--reversed-order` は Python の経路なので、逆順で driver は通していません。行の網羅と全テスト下の計測はしていません。Linux 以外は CI に任せます。
