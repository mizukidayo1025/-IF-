## 変更

自然文の介入で追加先の Zone を書かないと、トイレ追加・スタッフ追加・避難者の到着・帰宅のどれもが、全 Zone で聞き返しになっていました（#35）。相談のうえ、次のように決めました。

- **ルール処理**（`llm/natural_language.py` の `_resolve_target`）：追加先を書かない指示は、操作ごとに Scenario のデータで候補を絞ります。

  | 操作 | 候補 |
  |---|---|
  | トイレ追加 | 既存トイレのある Zone |
  | 避難者の到着 | 受付（`intake`）のある Zone |
  | スタッフ追加 | スタッフの配置されている Zone |
  | 避難者の帰宅 | 避難者のいる Zone |

  - 候補が1つなら自動で選び、その理由を仮定（assumption）として Preview に示します。反映には従来どおり承認が要ります。
  - 該当する Zone がない Scenario では、これまでどおり全 Zone を候補にします。
  - Zone を名前・ID・`zone_id:` で明示した指示は、そのまま使います。
  - 「トイレゾーン」「トイレエリア」は、トイレの Zone を指します。これまでは、一般名として照合から外していました。
- **compiler に渡す要約**（`ZoneTarget`）：Zone ごとのスタッフ数（`staff_count`）と避難者数（`evacuee_count`）を足しました。要約は保存せず、変わるのは compiler への入力だけです。
- **Opus 経路**（#35 の案B-2）
  - Opus が追加先の Zone を聞き返しても、上の規則で1つに決まり、規則が文全体を解釈できる場合は、規則の案で補います。`fallback_used: true` で、理由を limitations に書きます。
  - Opus の聞き返しの選択肢は、1種類の対象（Zone だけ、設備だけ、など）の ID に限ります。混ざっていれば検証で拒否し、従来の修正依頼と fallback の流れになります。
- **Project 画面**（`static/project.js`・`index.html`・`project.css`）
  - 聞き返しの選択肢をボタンで示します。押すと、指示文に `zone_id: <ID>` の行を足して再 Preview します。Zone 以外の ID は `対象ID: <ID>` の行にします。
  - /demo-v2 と同じ方式で、API は変えていません。
- `docs/adaptive-event-compiler.md` に、候補の規則を追記しました。

#35 のうち、次のものはこの PR では扱っていません。

- 設備の停止を AI 経路でトイレ以外に広げるか
- 選んだ対象を専用の項目で渡す方式（案C）
- ライブ API での Opus の聞き返しの確認

## 確認

1440分まで計算した生成 Scenario の Project（1410分）で、オフラインの Preview を確かめました。

| 指示 | 結果 |
|---|---|
| トイレを1つ追加 | `toilet`。仮定「追加先が書かれていないため、既存トイレのあるZone「トイレ」（toilet）を対象にしました。」 |
| 避難者が5人到着 | `intake`。仮定付き |
| トイレゾーンにトイレを1基追加 | `toilet` |
| 静養スペースに多目的トイレを1基追加 | `quiet`（明示のまま） |
| スタッフを2人追加 | `food`・`staff` の2択で聞き返し（これまでは8択） |
| 避難者が3人帰宅 | 避難者のいる4つの Zone で聞き返し（これまでは8択） |

ヘッドレスの Chromium（Playwright）で Project 画面も確かめました。「スタッフを2人追加」で「食事・給水スペース (food)」「運営本部 (staff)」の2つのボタンが出ました。「運営本部」を押すと、指示文に `zone_id: staff` が足されて再 Preview され、`compiled`・`can_apply: true`（対象 `staff`）になりました。ページの JavaScript エラーはありませんでした。
