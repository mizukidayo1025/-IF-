## 概要

5倍高速化の手順の A2 です。長い計算では、索引への登録を別のプロセスで計算と並行して行います。

これまでは、30分ごとの保存のたびに索引に登録し終えてから、計算を続けていました。7日目近くでは登録が1回約0.6秒かかり、7日分で約180秒、計算を止めていました。

## 変更

- **`storage/index_writer.py`（新しいモジュール、`BackgroundIndexer`）：**
  - 登録用のプロセスを1つ起こします（spawn 方式で、Windows・macOS・Linux で同じ作りです）。
  - 保存のたびに、`HistoryIndex.ingest` が読む分だけを送ります。
    - 前の保存から増えた EventLog の記録、KPI の標本、資源の標本
    - 履歴（体調・職員・人口）のうち、前の保存の1分前以後の項目（体調の履歴は、新しいイベントの最初の時刻以後）
    - model_state の名前と、model_configs
  - 登録用のプロセスは、保存の順に1つずつ、今と同じ `ingest` で登録します。
  - 送った分の先頭が、索引の記録している位置（`heads.counts`）と合わなければ、`history_index_out_of_step` で断ります。計算は失敗になり、ずれたまま登録することはありません。
  - 登録が2回分より遅れると、計算側が待ちます。メモリと遅れを抑えるためです。
- **`experiments/timeline.py`：**
  - 保存が8回以上ある計算（`BACKGROUND_INDEX_MIN_SAVES`）で使います。
  - 計算の終わり（取り消しを含む）には、登録が追いつくのを待ってから戻ります。そのため、状態が `paused`・`completed` になった時点で、索引は Branch の head に追いついています。
  - 登録の誤りは、計算の誤りとして伝えます。
  - 短い計算と分岐は、今までどおり保存のたびに同じ場で登録します。
- **変えないもの：** 索引の中身、Checkpoint、保存の間隔、計算の結果。

## 読み取りへの影響

索引がポインタより後れている間の読み取りは、もともと索引の head の時点で答えます（#259、#262）。長い計算の間は、この遅れが最大で保存2回分になります。計算のプロセスが途中で止まった場合、まだ登録していない保存の Checkpoint は、索引の一覧（`checkpoints`）に載りません。次の計算は索引の記録している位置から登録を続けるので記録は欠けませんが、その時刻の過去の参照は、一覧にある前の Checkpoint から計算し直します。`docs/project-persistence.md` に書きました。
