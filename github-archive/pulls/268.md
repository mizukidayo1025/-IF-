## 変更

計算中や分岐中に、子プロセスが履歴索引（`runs/{run}/history.sqlite`）へ長く書き込んでいる間、frame の読み取りが待たされていました。1440分の分岐では最大5〜6秒です。索引の SQLite が従来のジャーナル方式で、書き込みの間は読み取りを止めるためです（#48 のコメントで記録）。

- `HistoryIndex.connect(write=True)` で、`PRAGMA journal_mode=WAL` にします。
  - 書き込みの途中でも、読み取りは最後に commit された内容を待たずに読めます。
  - モードはファイルに残るので、既存の索引は次の書き込みで切り替わります。
  - `synchronous` は今のまま（FULL）です。相談のうえ、停電時に書き込みを失いうる NORMAL は使いません。
- commit のあと、`PRAGMA wal_checkpoint(TRUNCATE)` で、ログ（`-wal`）の中身を本体へ書き戻して空にします。読み取りの接続が開いていると、最後の書き込み1回分（分岐なら数十〜数百 MB）が次の書き込みまで残るためです。
- 自動の書き戻しのあと、ログを 16 MiB まで縮めます（`journal_size_limit`）。
- 読み取りの接続は、索引の横に `history.sqlite-shm`（32 KB）と空の `history.sqlite-wal` を作ります。読み取り専用の接続にはこれを消す権限がないので、次の書き込みまで残ります。どちらも容量に数えます。
- `tests/integration/test_timeline_frame_cache.py` は、「frame の読み取りがファイルを書き換えない」ことを確かめています。その比較から、SQLite の `-shm`・`-wal` を外しました。保存データではなく、WAL の索引を読む接続が開くファイルだからです。
- `docs/project-persistence.md` に追記しました。WAL 方式はネットワーク上のフォルダーでは使えないことも書いています。
