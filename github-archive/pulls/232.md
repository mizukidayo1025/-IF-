## 元の本文

Checkpoint の検証（読込、`restore_state`、`to_dict` など）で、世界の正準JSONを1回だけ作ります。

## 修正前

`Checkpoint._validate` は、ハッシュを確かめる場合、次の3つを別々に行っていました。

- `state_hash` のために世界全体を JSON にする
- `checkpoint_hash` のために、世界を含む本体全体をもう一度 JSON にする
- 復元のために世界全体を `deepcopy` する

1200分時点の読込（2.9秒）では、それぞれ 0.36秒、0.39秒、0.72秒でした。

## 変更

- 世界の正準JSONを1回だけ作り、`state_hash` を確かめます。
- 本体のハッシュは、そのbyte列を差し込んで計算します（`CanonicalEncoder.remember`）。
- 復元用のコピーは、そのbyte列を `json.loads` で読み直して作ります。保存済み・作成直後の Checkpoint の世界の文書は、どれも正準JSON（キーを整列したもの）から読んだものなので、読み直したコピーはキーの順番も含めて `deepcopy` と同じです。
- ハッシュの確認を省く経路（`capture()` 直後の確認）は、これまでどおり `deepcopy` を使います。

## 結果（ローカル、WSL2）

- 1200分まで計算した Run の head の読込（`load_restored_branch`）: 2.9秒 → 2.4〜2.5秒（3回）
- 1200分から1230分への再開: 7.4秒 → 6.3秒
- 1425分（保存境界の間）での分岐の `seek`: 4.9秒 → 4.0秒
- 再開後の head と、分岐の応答・子branchの Checkpoint のハッシュは develop `4e7ed6d` と一致しました。

## テスト

- `tests/unit/core/test_checkpoint.py`: Checkpoint を検証して復元するとき、世界（単独、または本体の中）を JSON にするのが1回だけであること。復元した世界が元の世界と同じで、それを変えても Checkpoint が変わらないこと。本体のハッシュで世界を差し込まない実装では、このテストが失敗することを確かめました。
- 世界や本体を書き換えた Checkpoint を拒否する既存のテスト（`test_capture_hashes_once_and_later_reads_still_detect_mutation` など）も成功しています。
- offline全体テスト（ローカル）: `SHELTERSIM_LLM_MODE=offline .venv/bin/python -m pytest -n auto` が 1278 passed、4 skipped。`ruff check` と `ruff format --check` も通っています。PRではCIが動かないため、結果はすべてローカルのものです。
