## 元の本文

## 背景

#25 のマージ後、ランダムに作った生成Scenarioを60件offlineで実行したところ、4件（12人・1日、150人・2日、1人・6時間、2人・1.5日）が最初のtickで次のエラーで止まりました。

```
StateInvariantError: invalid operational events state: operational events require operational_events_v1 state
```

4件とも、運営条件に資源の損失（`resource_loss`）が入っていて、断水・職員不在などのH03イベントは入っていませんでした。

## 原因

運用イベントの状態（`operational_events_v1`）について、3か所の判定が一致していませんでした。

| 場所 | 状態が必要と判断する条件 |
|---|---|
| 状態の作成（`core/world.py` → `uses_operational_events`） | H03イベント、または`shipment_id`付きの納入 |
| 完全検証（`validate_operational_events_state`、履歴あり） | 同上（`uses_operational_events`） |
| tickごとの軽い検証（同関数、`validate_event_history=False`） | `resource_delivery`・`resource_loss`・`resource_reserve`・`resource_release`・`resource_consume`・`staff_unavailable`・`staff_available`のいずれか |

`resource_loss`だけのScenarioでは状態が作られず、完全検証も状態なしを認めます。しかし、エンジンが毎分呼ぶ軽い検証だけが状態を要求するため、最初のtickで止まっていました。#20では、運営条件の納入に`shipment_id`を付けて同じ問題を避けましたが、`resource_loss`のpayloadには`shipment_id`を付けられないため、損失では残っていました。

`resource_loss`の処理（`ResourceLedgerHandler`）は在庫台帳だけを使い、運用イベントの状態を参照しません。

## 変更内容

- `src/sheltersim/domain/operational.py`：軽い検証でも、状態の作成・完全検証と同じ`uses_operational_events(pending_events)`で判定します。
- H03イベントや`shipment_id`付きの納入が予定にあるのに状態がない場合は、これまでどおり拒否します。

## 互換性

- Checkpointとartifactの形式は変えていません。状態の作成条件も変えていません。
- 変わるのは、これまで最初のtickで止まっていたRunだけです。止まらずに実行できていたRunでは、軽い検証が通る条件は変わりません。全件テスト（回帰契約とデモ再生を含む）も変更なしで通っています。
