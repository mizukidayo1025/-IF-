## 元の本文

文字列に `@` がないとき、秘密情報の正規表現からメールアドレスの部分を外して検査します。PR #230 の続きです。

## 原因

- PR #230 では、`@`・`sk-`・`bearer` のどれかを含む文字列にだけ秘密情報の正規表現（`_SECRET`）をかけるようにしました。
- ところが、`staff-task-12` のようなIDは `ta**sk-**` を含みます。そのため、KPIの標本ごとの `source_ids_json`（約3KB、空白なし）はこの確認を通り、正規表現全体が走っていました。
- メールアドレスの部分は、空白のない長い文字列では単語の境目ごとに読み直すので、1つあたり約1.8ミリ秒かかります。
- Checkpointの保存では、追記途中のchunkに入っているKPIの標本（最大128件）を、保存のたびに検査し直します。

## 変更

- `@` がない文字列では、メールアドレスの部分はどこにも一致しえません。
- 正規表現は、各位置で最初に一致した候補を選ぶので、一致しえない候補を外しても結果は変わりません。
- そこで、`@` を含む文字列にはこれまでどおり `_SECRET` を、含まない文字列には APIキーと `Bearer` の部分だけの正規表現（`_SECRET_WITHOUT_ADDRESS`）をかけます。
- 電話番号の正規表現は、これまでどおりすべての文字列にかけます。
