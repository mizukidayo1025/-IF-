## 概要

M4 のうち移動の規則を Rust へ移しました。結果は変わらず、tick は約 15% 速くなりました。

詳細は `docs/rust-port/lanes/m4-movement.md` にあります。

## 移した処理

- `native/src/rules/movement.rs`：`advance_movement`、`start_movement`、`finish_movement`、`route_with_movement_time`、`route_is_physically_clear`、`plan_in_room_route`、`_queue_slot_position`、`facility_approach_route`、`movement_v1` の検証
- `native/src/rules/movement_geometry.rs`：データとしての間取りと幾何

順序に依存する枝は再現せず、拒否します。列の旅の引き直し（`_replan_physical_queue_trip` の4か所）と、歩く途中で列の枠に置く人がいる tick では、`advance_movement` は何も変えずに `Unsupported` を返し、その tick は全部 Python の規則が動きます。

## 分かっている弱点

- **シャドーの穴：** 1% の変更のうち、辺の進み、混雑時間、列の間隔はシャドーとハッシュで検出できましたが、既定の密度、既定の速さ 72、占有域の余裕、部屋の進み 1 未満、余裕 0.25 はシャドーで差 0、ハッシュも通りました。比較に使ったシナリオがこれらを通らないためです。テストを足し、密度、占有域の余裕、部屋の進み、余裕 0.25、既定の速さ 36 で失敗することを確認しました。速さ 72 そのものはテストで試していません。
- 拒否する枝は、ゲートと 7 日間では通らず、テストでしか比較していません。
- `SHELTERSIM_MOVEMENT_REVERSED=1` は Python の規則だけを逆順にします。kernel に順序がないことは、tick の開始時の行から計画するという設計によるもので、逆順で実行してはいません。この枝は手順 4 の並列化の障害として残ります。
- 値が変わらない記録は差し替えなくなり、復元した記録は次に書かれるまで JSON のキー順を保ちます。tick をまたいで記録を持つコードは検索で見つかりませんでしたが、検索しただけです。
- `Geo` の計画キャッシュは、行の外のプロセス共通のリストに、最大 8 件の Python ハンドルを持ちます。
- Linux 以外は CI に任せます。新しい C API は `PyDict_DelItem`（stable ABI）だけです。

## 残り

`domain/movement.py` に残る Python は tick の約 2%（約 140 µs/tick、呼ぶ kernel を含む）です。`progress_physical_queue_positions`、`progress_physical_queue_head_to_service`、`shared_passage_edge_loads`、`physical_service_capacity`、イベントを割り当てる `_schedule_queue_trip` と `_replan_physical_queue_trip`、`independent` FIFO の枠、測量済みのサービス地点の経路などです。
