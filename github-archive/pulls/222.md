## 元の本文

Issue #46 の後半（分岐の作成で、全履歴のCheckpoint作成が何度も走る）に対応します。前半の「保存境界以外の時刻の表示（`TimelineStore.seek`）」は扱わないため、#46 は閉じません。

## 修正前に分岐1回で走っていた処理

`TimelineStore.fork` の中で、同じ状態に対して次の処理が走っていました。

- `source.fork()` の中で Checkpoint を作成（変換・ハッシュ・復元検証）し、そこから子branchを**もう一度**復元
- `fork_origin` の `state_hash` 用に `digest(source.world.to_dict())`（検証・変換・ハッシュ）
- `fork_origin` の `checkpoint_hash` 用に `source.checkpoint()`（2回目の Checkpoint 作成）
- 応答テープを引き継ぐためだけに、分岐元の head Checkpoint を `load_branch` で全体展開・復元
- 応答の `state_hash` 用に、Project API と CLI で `digest(child.world.to_dict())`

## 変更

- `Checkpoint.capture_restored()` を追加しました。`capture()` と同じ Checkpoint を作り、作成時の復元検証で組み立てた世界と指標も返します。これは `restore_state()` が返すものと同じで、Checkpoint とも元の世界とも何も共有しません。履歴キャッシュ（#44）を使う保存では、復元した世界が保存文書のリストを共有するため、この経路は使いません。
- `BranchRuntime.fork_with_checkpoint()` を追加しました。上の1回の作成から、子branchと Checkpoint を返します。`fork()` はこれを使います。
- `TimelineStore.fork` は、`fork_origin` の2つのハッシュをこの Checkpoint から取ります。応答テープは、head Checkpoint の `runtime_state` だけを `checkpoint_fields` で読みます（`seek` と同じ読み方）。
- Project API と CLI の分岐の応答は、`state_hash` を子branchの保存済み head から読みます。保存直後の子の世界のハッシュなので、値は同じです。

## 結果（ローカル、WSL2・CPython 3.12、1回ずつ）

100人・生成Scenario を ProjectAPI 経路で1440分まで計算した Project のコピーに対し、Project API の分岐（介入なし）を1回実行しました。

| 分岐する時刻 | 修正前 | 修正後 |
|---|---:|---:|
| 1440分 | 50.4秒 | 32.0秒 |
| 720分 | 25.7秒 | 14.5秒 |

1440分の内訳（修正前 → 修正後）:

- Checkpoint 作成: 3回 15.3秒 → 子の作成時1回と保存時1回
- 子branchの復元: 2回 7.1秒 → 1回 3.4秒（`seek` の分だけ）
- head Checkpoint の全体展開: 1回 → 0回
- `WorldState.to_dict`: 5回 6.8秒 → 2回 2.8秒

両方の時刻で、応答（`branch_id`・`minute`・`state_hash`）、`fork_origin`、子branchの保存 Checkpoint のハッシュが修正前（develop `92695f8`）と一致しました。

## まだ残る処理（1440分、修正後の32秒の内訳）

- **子branchの履歴索引の作成（約12秒）**: 新しいbranchの索引は、分岐元と同じ記録も含めて全履歴を最初から登録します。分岐元の行を写すには履歴索引の作り方を変える必要があるため、このPRでは扱いません。
- **`seek`（約8秒）**: 保存境界の時刻でも、Checkpoint の読み込み時の検証で一度復元し、`from_checkpoint` でもう一度復元します。#46 の前半（`seek`）と合わせて扱うのが自然だと考え、このPRでは変えていません。
- **子branchの最初の保存（約5秒）**: 子の世界は新しいオブジェクトなので、#44 の履歴キャッシュは効きません。

## テスト

- `tests/integration/test_exact_timeline.py`: 分岐で保存される子の Checkpoint、`fork_origin`、Project API の応答が、修正前の手順（別に `seek` した分岐元から、作成・復元・ハッシュを1つずつ行う）で作ったものと一致すること。保存境界（30分）、保存境界以外（40分）、介入つき（40分）の3通りで確かめます。**このテストは修正前のコードで先に通しました。**
- `tests/unit/core/test_checkpoint.py`: `capture_restored()` は復元を1回だけ行い、`capture()` と同じ Checkpoint と `restore_state()` と同じ世界・指標を返すこと。返した世界・指標を変えても、Checkpoint と元の世界が変わらないこと。
- `tests/unit/experiments/test_branch.py`: `fork_with_checkpoint()` の Checkpoint が `checkpoint()` と一致し、子がそこから復元したものと一致すること。子を変えても Checkpoint と分岐元が変わらないこと。
