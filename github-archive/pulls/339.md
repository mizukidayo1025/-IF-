## 概要

イベントの dispatch のループを Rust へ移し、イベントの種類から Rust の関数か Python のハンドラーを選ぶ表を入れました。`AgentTravelCompletionHandler` の大部分と抑止の文も移しました。結果は変わりません。

**速度の効果はまだほとんどありません。** ループ自身の費用はほぼ 0（約 30 µs/tick）になりましたが、もともと段階の小さな部分でした。段階で 7〜11%、tick で約 2% の減りで、`tick_budget.py` で見える差はありません。残りの Python が移るとこの土台が効くと見ていますが、見積もりです。

詳細は `docs/rust-port/lanes/m3-dispatch.md` にあります。

## 移した処理

- `rules/dispatch.rs`：ループ、種類ごとの表、`_sync_movement_after_events` の列の目的の 4 つ
- `rules/travel_completion.rs`：移動の完了の確認（目的ごとのタスクの種類、列の確認）、到着後の活動、`resource_for_facility` の種類
- `rules/social_interaction.rs`：抑止の文。Python の手順でその文より前にある確認がすべて通ったときだけ返します。

`settle` は E のレーンの版を直しました。`Ok(false)` が「行がない」と「列にない」を区別できず、今の列の行を記録していて、ハンドラーが書いた記録との比較もありませんでした。今は渡された行を記録し、列にあれば外し、記録がすでにあれば `false` を返し、呼ぶ側が比べます。テストを 3 件足しました。

## 分かっている弱点

- 行だけのイベントが Rust の関数に来る経路は本番では通らず、テスト 1 件だけが通します。
- 社会の kernel はまだ `ScheduledEvent` を読みます。
- シャドーの実行は各規則の Python の入口を通るので、直接呼ぶ実行そのものの比較ではありません。同じ kernel を呼ぶこと、ハッシュ、240 分の一致テストで確かめています。
- Python の記録を持たなくなった分のメモリと、`events_realized.jsonl` を書くときの記録を作る費用は測っていません。
- 既存のテストの意味を変えました。`test_another_object_of_an_event_is_left_to_the_python_rule` を 2 件に分け、同じ行の別オブジェクトは kernel が受け取り、1 と 1.0 のように行で区別できない値は Python に任せます。社会のレーンの抑止のテスト 3 件は、kernel が Python と同じ文を出す形に書き直しました。
- Linux 以外は CI に任せます。新しい C API はありません。
