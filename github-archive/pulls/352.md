## 概要

提案と移動の残りを Rust へ移しました。`advance_movement` の順序に依存する枝も、今の順序のまま移しています。ゲートと 7 日間でこのレーンの拒否の理由は 0 になり、結果は変わりません。

詳細は `docs/rust-port/lanes/l3-movement.md` にあります。

## 移した処理

- `advance_movement`：通常の歩行が列の旅の引き直しか、枠に置く人に当たると、何も書かずに止まります。続いて同じ順序で 2 回目の歩行が動き、更新し続ける位置の写しを読んで、順にイベント番号を取ります。`_queue_slot_position` はその写しを読みます。順序は変えていません。
- `_replan_journeys`、`_replan_staff_support_trip`（`rules/replan.rs`）。人の停止を書かないと新しい経路を計画できないので、拒否の後に動くものは進み具合で変わります：最初の停止の前は Python の手順全体、後の人の停止の前は残りを `_replan_in_python`、停止の後はその人を `_replan_stopped`。
- `_apply_effect`：その場の依頼はトイレとサービスの列の kernel を通ります（`independent`、時間なしの移動、間取りなしを含む）。
- 閉じた依頼、資源サービスのない世界、`agent_is_at_*`、`staff_position_snapshots`。

## #351 とのマージで足した拒否

L2 の容量待ち（順序番号を `EventWriter` で予約し、書き込みの段階で書く）と、L3 のその場の依頼（書き込みの前に列の kernel が書く）を合わせると、容量待ちのある `at_once` では、列のイベントが先に順序番号を取ってしまいます。Python では容量待ちが先です。

そこで、この組み合わせでは kernel は書く前に `a capacity wait comes before a request at once` で拒否し、Python の規則が動くようにしました。ゲートと 7 日間でこの理由に届くかは数えていません。手順 4 までに Rust の道が要るので、拒否の一覧に残ります。テストはまだありません。

## 分かっている弱点

- **順序に依存する枝はテストだけで比較しています。** ゲートも 7 日間も届きません。`independent` の引き直しは決まったテストだけで、ランダムな 40 回の歩行は設備自身の列を使います。資源の `independent` の列の引き直しのテストはありません。到達のテストは、枠に置かれる回数までは数えません。
- `_replan_journeys` のシャドーの比較は支援の枝の 1 回だけで、ほかの枝はテストだけです。
- `ARRIVED_WITHIN` はテストだけが検出します。`arrived` と `closed` の変更のゲートは負荷で時間切れになり、ハッシュは確認できていません。
- 7 日間の全シャドーは分 1,230 の時点で完走の見込みがなく止めました。
- 全シャドーのゲートの `the world has no core` の拒否（5,089 件、8,711 件）は、シャドーのコピー上の Python の規則からの呼び出しと読んでいますが、確かめていません。
- 感度：歩行の順序の逆転はテストとシャドーで検出します。`walk` の指標はテスト 7 件だけが検出します（ゲートの 1 回の引き直しは支援の枝）。
- Linux 以外は CI に任せます。

**レーン中に直した不具合：** `agent_is_at_queue_trip_destination` の kernel が dict の派生型で誤って False を返していました。`test_tracked_mirror` が検出し、テストを足しました。
