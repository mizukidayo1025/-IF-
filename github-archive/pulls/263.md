## 元の本文

#48 の残りの1つです。Web サーバーで、分岐（`POST …/branches/{branch}/fork`）と intervention-apply を、計算と同じく別プロセスで行います。

## なぜ
分岐は HTTP の処理の中で、復元、Checkpoint の作成、子 branch の保存と索引への登録まで行っていました。Web サーバー（`HTTPServer`）は要求を1件ずつ処理するので、1440分の分岐の約15秒の間、状態の確認を含むほかの要求に一切応えられませんでした。

## 変更
- `ProjectAPI.fork`（`worker="process"`）
  - 復元の要らない確認は、その場で行います。時刻の範囲、子 ID の重複、program hash の不一致です。
  - そのあと、worker のプロセスで分岐を作り、すぐに `{"status": "running", "branch_id": 子, "minute": 分岐時刻}` を返します。
  - intervention-apply は `ProjectAPI.fork` を通るので、同じ扱いになります。
- `web/worker_process.py`：job を `{"kind": "advance" | "fork", …}` で受け取るようにしました。
  - 分岐の job は、Run の書き込み権を取ったうえで状態を `running` にし、子プロセスの中で従来どおりの分岐（スレッド方式の `ProjectAPI.fork`）を行います。
  - 結果（成功なら子の `branch_id`・`minute`・`state_hash`、失敗ならメッセージ）は pipe で返します。
- サーバーの見張りのスレッドは、結果を Run の参照（`GET …/runs/{run}`）の `last_fork` に載せてから、Run の状態を元に戻します。
  - 画面が「`running` でなくなった」のを見たときに、結果も読めるようにするためです。
  - 子プロセスが強制終了した場合も、元の状態に戻し、`last_fork` は `run_worker_ended` の失敗になります。
  - サーバーがなくなっていた場合は、子プロセスが自分で状態を戻します。
  - `last_fork` は、そのサーバーのプロセスで最後に始めた分岐の結果だけで、保存はしません。
- 画面（`static/project.js`）
  - 分岐の応答が `running` なら、状態の確認を続けて「分岐 … を作成しています…」と表示します。
  - 子 branch ができたら、それを開きます。
  - できなかった場合は、`last_fork.error` を表示します。
  - Run を開き直したときは、待っている分岐を忘れます。
- テストと CLI（`worker="thread"`）は、これまでどおり子 branch を作り終えてから `{"branch_id", "minute", "state_hash"}` を返します。
- `docs/api-reference.md`・`docs/architecture.md` を更新しました。

## 結果（ローカル、WSL2）
1440分まで計算した Project（100人・生成Scenario）を、`serve_inspector` で動かしました。HTTP で1440分の分岐を送り、その間、Run の状態と1410分の frame を交互に読み続けました。

| | develop | この PR（2回） |
|---|---|---|
| 分岐の要求が返るまで | 15.11秒 | 0.26 / 0.26秒 |
| 子 branch ができるまで | 15.2秒 | 15.9 / 16.0秒 |
| 分岐中の Run の状態の読み取り | 14.9秒待たされた（1回だけ送れた） | 最大 60 / 56 ms |
| 分岐中の frame の読み取り | — | 中央値 42 ms、最大 5.5 / 5.2秒 |

- 子 branch の `state_hash`（`d1ca12438bb4…`）は develop と同じでした。
- frame の読み取りが1回だけ約5秒待たされるのは、子プロセスが履歴索引にまとめて書き込む間、SQLite が読み取りを待たせるためです。索引は WAL ではなく、従来のジャーナル方式です。計算中の保存でも、同じ待ちが小さく起きます。この PR では変えていません。

## テスト
- `tests/integration/test_process_worker.py`（追加分）
  - 別プロセスの分岐がすぐに `running` を返し、終わると `last_fork` が、スレッドでの分岐の結果と同じになること。子 branch の head も同じであること。Run の状態は元に戻ること。
  - 失敗する分岐（元の state hash が違う）では、`last_fork` が失敗とその理由になり、子 branch はできず、Run の状態も元に戻ること。
