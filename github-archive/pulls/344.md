## 元の本文

## 概要

tick の段階を `TickEngine.step` から Rust で順に回す driver を入れました。比較した範囲で結果は変わりません。

**7 日間の経路では速くなりません。** tick は約 1〜2%、Run 全体は 0.3% 以下の差で、揺れの範囲です。価値は手順 4 に向けて段階の順序を Rust に持つことです。

詳細は `docs/rust-port/lanes/m6-driver.md` にあります。

## 変更

- `native/src/rules/tick.rs` が段階を順に回し、`experiments/phases/driver.py` が接続を持ちます。kernel は直接呼び、Python の部分はそれぞれ 1 つの入口から呼びます。
- 次のときは、何も変える前に driver が tick を拒否し、Python の経路が動きます：trace、Provider を呼べる router、シャドー、`tick_probe`、差し替えた `phase_handler`、patch された手順や規則。`SHELTERSIM_NATIVE=0` でも Python の経路です。
- offline の router は driver のままです。フックは kernel の中の同じ箇所で動き、順序と引数が Python の経路と同じことをテストで比較しています。
- トイレと資源の `arbitrate` のループ、提案のループ、`arbitrate` と `update` の手順の呼び出しを移しました。
- Python：`_replan_journeys`、`_record_assigned_support`、`_refresh_config_scopes`、`_config_scopes` を分けました（本体は同じ）。`TickEngine.phase_observer` を追加しました。

**`benchmarks/investigate_performance.py` を直しました。** `__call__` と `_record_outcome` を patch していたため、7 日間のツールではどの tick も driver に拒否され、Python の経路を通っていました。ハッシュは一致するので気づきにくい問題で、プロファイルの回数で分かりました。今は `phase_observer` で段階を計ります。`result.json` から `_record_outcome` の行がなくなります。

## 分かっている弱点

- **シャドーと `--reversed-order` は Python の経路を通るので、driver を確かめません。** driver の直接の経路は、ハッシュ、段階ごとの比較（ゲートのみ）、テストで確かめています。driver に dict の順序への依存はないという論証で、逆順で driver を通したことはありません。7 日間は段階ごとに比較していません。3 つのハッシュだけです。
- 7 日間のシャドーは dispatch、queues、service、tick だけです（広げると約 1.7 時間の見積もりで止めました）。
- 感度：段階の順序の入れ替えのうち、苦情と relief、`apply_deltas` と `update_long_term` は結果の比較では見えません。`tick.rs` の順序を各段階の Python メソッドの AST と比べるテストを足し、この 2 つで失敗することを確認しました。sample と arbitrate の入れ替えは `first_difference` とテストで検出しますが、`generated_project` のハッシュは同じです。
- patch の表（`DRIVEN_STEPS`、`DRIVEN_RULES`）は手で管理しています。driver が飛ばすようになった規則を表に足し忘れると、patch を黙って見逃します。
- 順序のテストは段階の手順を見ますが、`arbitrate` の変更は見ません。段階や `arbitrate` を変えるレーンは `rules/tick.rs` と `driver.py` の表も更新する必要があります。
- Provider を呼べる router の Run と `measure_performance` の Run は、Python の経路のままで効果がありません。
- Rust の行の網羅は測っていません。Linux 以外は CI に任せます。新しい C API はありません。
