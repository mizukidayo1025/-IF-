## 元の本文

## 概要
ブラウザーで途中介入を自然言語で入力しても、AI（Opus）が使われない不具合を修正します。

## 原因
生成Scenarioでは、介入compilerの送信内容がrouterの汎用入力上限（16,384バイト）を必ず超えていました。導入済みprimitiveの説明だけで約13 KBあり、避難者10人で18,573バイト、100人で20,705バイトでした。このため、APIを一度も呼ばずに`input_token_limit`でruleの結果になっていました。利用者には「Opusが利用できないため」としか表示されず、理由が分かりませんでした。

## 変更
- `LLMTask`に`input_byte_limit`を追加しました。routerは、設定値とtaskの宣言値の大きい方を上限として使い、呼出し前の予算確認もその上限で予約します。cache keyには含めないため、既存のresponse tapeとCheckpointには影響しません。`max_input_tokens`の既定値は変えていません。この設定はCheckpointの互換判定に使われるためです。
- 介入compilerは64 KiBを宣言します（約1,500人分）。
- compilerがruleの結果になったときは、Opusを使わなかった理由を日本語の固定文と理由コードで`limitations`に入れます。対象は、offline mode、入力上限、呼出し上限、予算、429、応答不正などです。offline modeなのに「Opusの出力または予算に問題があり」と表示されていた誤りも直しました。
- `docs/llm-integration.md`と`docs/api-reference.md`を更新しました。介入compiler 1回の呼出し前の予約額は、約$0.30から約$0.69になります。

## 確認（すべてローカル）
- `SHELTERSIM_LLM_MODE=offline .venv/bin/python -m pytest -n auto`：794 passed、3 skipped（live API test）
- 追加したテスト（Project経路で生成Scenarioの60分時点に介入するテストを含む）は、修正前のコードで失敗することを確認しました。修正前はProviderの呼出しが0回です。
- 変更した5ファイルのruff check指摘は17件で、mainと同数です。
- 実APIは呼んでいません。Opusの実際の応答が検証を通るかは、live確認が必要です。

## 範囲外
- `SHELTERSIM_LLM_ERROR_POLICY=stop`でも、compilerは`LLMExecutionError`を捕まえてruleの結果を返します（従来どおり）。今回の変更で理由は表示されますが、/demo-v2の「fallbackしない」方針と合わせるかどうかは別途判断が必要です。
- 約1,500人を超える規模では、引き続き上限を超えてfallbackします（理由は表示されます）。
- offline parserの小さな不具合（例：「toilet-1を故障させる」に避難者数のエラーが返る）は未対応です。
